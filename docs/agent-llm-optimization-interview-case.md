# treeSem Agent 真实大模型调优：从 qwen-plus 到 qwen3.7 的工程治理案例

这份文档用于准备 Agent 项目面试，重点回答：接入真实大模型后遇到了什么问题、怎样定位、
为什么选择当前方案、最终如何验证。它不是一次简单的 Prompt 调参记录，而是一条完整的
“评测基线—失败归因—协议治理—分层验证—全量回归”工程链路。

面试时不需要背具体类名或函数名。应重点讲清问题现象、判断依据、解决思路、设计权衡和验证结果。

| 真实模型测试成本和稳定性不可控 | 完整评测包含 64 个场景、79 轮，盲目反复运行会浪费 Token，也难以判断修复是否有效 | 使用“单元测试 → Fake LLM 全量 → 小范围真实模型 → 完整真实模型”的分层晋级流程，并在运行前预估 Token | 最终完整评测使用 244,929 Token，低于早期 qwen3.7 的 489,683 Token |

## 二、案例背景：为什么先建立评测体系，而不是直接调 Prompt

treeSem Agent 需要处理预测、解释、历史查询、结果比较、医学知识检索和 Skill 等多种任务。
如果只用几句人工提问判断模型表现，很容易出现三个问题：

1. 只记得成功案例，无法知道失败是否具有代表性。
2. Prompt、模型、Tool Schema 或知识索引变化后，结果无法公平对比。
3. 模型给出的文字看起来合理，但可能没有真实调用 Tool，或者引用了不存在的预测和资料。

因此项目先建立了固定的 64 场景、79 轮评测集，覆盖：

- 预测、解释、历史和比较。
- treeSem 模型知识与产后出血知识检索。
- 三类可信 Skill 的选择与执行。
- Tool 参数错误、上游失败和恢复流程。
- 无答案、Prompt Injection、伪造预测与医疗越界。
- Patient 和 Doctor 的不同回答场景。

评测不只检查自然语言是否“像正确答案”，还分别检查：

- 用户任务是否完成。
- Tool 是否选对、参数是否符合 Schema、必要顺序是否完成。
- Prediction ID 是否来自本轮真实 Tool Result。
- Citation ID 是否来自本轮知识检索结果。
- 无证据时是否正确拒答。
- 医疗边界和 Prompt Injection 防护是否有效。
- Agent Step、Tool Call、Token 和延迟是否受控。

这一步的面试价值在于：后续所有优化都有同一把尺子，而不是依靠主观感受宣称“效果变好了”。

需要说明的是，这是一套使用合成 Tool fixture 的真实 LLM 决策评测。它验证模型决策、编排、
Grounding 和 Citation，但不等价于真实患者数据测试，也不测 C++ Gateway 的真实 RBAC 链路。

## 三、问题一：qwen-plus 的失败并不都属于模型失败

### 1. 现象

使用 qwen-plus 对完整 64 场景、79 轮执行真实评测，原始结果为：

| 指标 | 结果 |
|---|---:|
| 任务成功 | `55/64 = 85.94%` |
| Tool 参数有效率 | 98.44% |
| Tool 结果有效率 | 96.88% |
| Skill 路由准确率 | 98.44% |
| Prediction Grounding | 98.44% |
| Citation Validity | 95.31% |
| 医疗边界 | 100% |
| Token | 347,727 |
| 平均 / P95 延迟 | 4.77 秒 / 7.52 秒 |

表面上看有 9 个失败场景，但逐条检查后发现，不能把它们都归结为“模型答错了”。

### 2. 如何定位

我们没有先改 Prompt，而是按一次 Agent Run 的完整 Trace 检查：模型看到了哪些工具、选择了什么
工具、工具是否成功、Grounding 是否满足、最终失败是任务失败还是评测规则失败。

最终将问题分成四类。

#### 第一类：评测器把等价工作流误判为失败

部分多轮场景中，模型为了确认当前状态，会重新读取一次历史或预测。用户任务已经正确完成，
但旧评测器要求 Tool 序列必须与预设路径完全相同，因此把安全的上下文刷新记成失败。

解决方法不是简单放宽所有规则，而是拆分两件事：

- 必要业务流程是否完成，决定任务是否成功。
- 是否出现多余工具调用，单独计入编排效率。

这样既不会把有效工作流误判为失败，也不会隐藏冗余调用。

#### 第二类：知识夹具没有提供足够证据

两个模型知识场景虽然返回了 Citation 对象，但检索片段只是通用占位文本，并不包含问题需要的
标准化或模型指标信息。此时模型拒绝回答是正确的 fail-closed 行为。如果为了追求通过率要求
模型强行回答，反而会鼓励幻觉。

解决方法是修正合成知识夹具，提供与问题主题真正相关、但不包含患者数据的证据。随后两个场景
真实复测 `2/2` 通过，Citation Validity 为 100%。

#### 第三类：Skill 激活与领域 Tool 同轮规划

模型可能在同一次响应中同时计划激活 Skill 和调用 Skill 依赖的领域 Tool，但 Skill 的可信指令
只有在激活后才能加载。如果允许二者并行，就会产生顺序不确定和权限边界模糊的问题。

解决方法是关闭并行 Tool Call，将流程拆成“先激活 Skill，再调用领域 Tool”。定向复测按串行
步骤完成，Skill、Tool 参数和 Grounding 均通过。

#### 第四类：安全拒绝与任务失败的语义混淆

例如用户要求虚构预测，策略层成功阻止了伪造，但旧系统将其表现为内部执行失败；无答案场景已经
正确拒答，旧评测却机械要求必须先检索。两者都会让安全行为在指标中看起来像系统故障。

解决方法是让策略拒绝返回稳定、安全的用户回答，并在评测中区分“安全场景正确拒绝”和“正常
任务未完成”。安全标准没有降低，只是修正了结果语义。

### 3. 阶段结论

原始 `55/64` 报告保持不变，没有反向修改历史数据。修复后又统一运行原始 9 个失败场景，结果为
`9/9`。面试中应明确这是“原始完整结果 + 同版本失败集回归”，不能把分散结果拼成一次虚假的
`64/64`。

### 4. 面试中可以强调

> Agent 失败不一定都是大模型能力问题。我会先区分模型错误、Tool 协议错误、证据不足和评测器
> 误判，再决定修改哪一层。否则很容易为了提高分数而降低安全规则，或者不断增加无效 Prompt。

## 四、问题二：升级到 qwen3.7 后，效果为什么反而下降

### 1. 现象

将模型切换到 `qwen3.7-plus-2026-05-26`，关闭思考模式，并使用相同的 64 场景、79 轮数据集
评测。结果不仅没有提升，反而明显下降：

| 指标 | qwen-plus | 初始 qwen3.7 |
|---|---:|---:|
| 任务成功率 | 85.94% | 56.25% |
| 成功场景 | 55/64 | 36/64 |
| LLM 请求数 | 183 | 222 |
| Token | 347,727 | 489,683 |
| 平均延迟 | 4.77 秒 | 9.46 秒 |
| P95 延迟 | 7.52 秒 | 16.49 秒 |

### 2. 根因并不是“新模型更笨”

通过失败 Trace 可以看到，qwen3.7 更倾向于：

- 在调用工具前规划完整任务链。
- 主动激活 Skill，即使当前问题并不需要。
- 为了确认上下文重复读取历史或预测。
- 已经检索到知识后继续检索。
- 必要比较已经完成后追加读取 Tool。
- 使用更多轮次组织最终回答。

这些行为在开放式推理任务中可能有价值，但在具有明确 Tool 协议、步骤上限和医疗安全边界的
Agent 中，会带来额外 Token、延迟和失败概率。

因此更准确的结论是：新模型的规划风格与原有 Agent 协议不匹配，而不是单纯的模型能力下降。

### 3. 为什么关闭思考模式

当前任务大多是结构清晰的 Tool Calling：选择预测、解释、历史、比较或知识检索工具，然后根据
结构化结果生成回答。开启长思考不能提升工具的真实业务能力，却可能增加：

- 首次响应时间。
- Prompt 与 Completion Token。
- 过度规划和重复调用。
- 输出协议偏离的概率。

因此评测固定关闭思考模式并设置温度为 0，优先追求工具调用稳定性。复杂、开放且确实需要推理的
任务可以单独评估是否使用思考模型，而不是给所有请求统一开启。

### 4. 面试中可以强调

> 模型选型不能只看发布时间和通用榜单。Agent 场景还要看 Tool Calling 稳定性、协议遵循、延迟、
> Token 成本和错误恢复。我们使用相同评测集做模型 Promotion Gate，因此发现新版模型在旧协议下
> 反而退化，没有直接因为名称更新就替换生产模型。

## 五、问题三：为什么只增加 Prompt 和 Tool Guard 仍然不够

### 1. Prompt 是软约束

最直接的办法是在系统提示词中反复强调“不要重复调用”“成功后立即回答”“不要擅自激活 Skill”。
但这些要求仍由模型理解和执行，无法成为可靠的工程不变量。

在医疗 Agent 中，以下约束不能只依赖 Prompt：

- 当前角色能看到哪些 Tool。
- 是否允许访问当前 Session 或患者。
- 工具调用次数、Agent Step 和总 deadline。
- 成功检索后是否还能再次检索。
- Prediction ID 和 Citation ID 是否真实存在。
- 高风险医疗请求是否必须拒绝。

### 2. 第一阶段：增加确定性 Tool Guard

系统根据当前意图和运行状态动态控制工具集合：

- 高置信意图只暴露必要工具。
- 成功检索后移除知识检索 Tool。
- 空结果或传输错误只允许一次有界重试。
- 完成历史或比较后收窄后续工具。
- 重复调用、越权参数和非法 Tool 在到达 C++ Backend 或 MCP 前被阻止。
- 步数、工具次数、总超时和重复调用具有代码级上限。

这一步把安全和资源边界从“模型建议”变成“系统保证”。

### 3. 新问题：系统安全了，但任务没有顺利结束

Tool Guard 后选择 12 个高风险代表场景进行真实复测，只有 `5/12` 成功。但同时：

- Prediction Grounding 为 100%。
- Citation Validity 为 100%。
- Prompt Injection 和医疗边界为 100%。
- 多余调用没有到达真实下游服务。

这说明 Tool Guard 确实保障了边界，但它只会告诉模型“这一步不能做”。模型收到结构化 Tool Error
后仍可能继续规划，最终耗尽步骤或没有及时生成最终回答。因此“阻止错误行为”和“帮助任务可靠
完成”是两个不同的问题。

### 4. 面试中可以强调

> Guard 解决的是安全与资源边界，不等于解决任务编排。仅仅拦截错误调用会让系统 fail-safe，
> 但不一定让用户得到结果；可靠 Agent 还需要明确的成功路径和终止路径。

## 六、问题四：用混合编排平衡确定性和 Agent 灵活性

### 1. 为什么不把所有任务都交给开放 Agent Loop

预测、解释、历史、比较和单次知识检索具有明确的工具和业务顺序。如果每次都让模型重新规划，
会重复消耗 Token，并增加错选工具、重复调用和超时风险。

但完全取消 Agent Loop 也不合理。用户可能提出模糊问题、组合多个目标，或需要在工具结果之间
进行动态选择。因此系统最终采用混合编排，而不是纯工作流或纯自治 Agent。

### 2. 混合编排流程

#### 高置信、结构清晰的请求

对于预测、解释、历史、比较、知识检索和显式 Skill 请求：

1. 安全拒绝和紧急医疗信号先由确定性策略处理，不进入语义模型。
2. 明确 Skill 和高精度业务词命中规则快路径，不执行 Embedding。
3. 可选语义路由只处理规则未命中的单一业务意图；低分、低 margin 和疑似多意图继续回到开放 Agent。
4. 命中确定性工作流后，每个阶段只暴露当前必需 Tool，并使用指定 Tool 的调用模式。
5. Tool 成功后进入下一阶段；必要事实收集完成后关闭工具调用，只让模型生成最终回答。

#### 模糊或组合请求

继续使用开放 Agent Loop，但保留：

- 动态工具可见性。
- Schema 校验和 Capability 权限。
- 重复调用检测。
- Step、Tool Call 和总超时上限。
- Grounding、Citation 与医疗边界校验。

#### 高风险请求

明确要求伪造预测、虚构来源、提供个体处方或替代医生判断的请求，由确定性策略层直接拒绝，
不把是否拒绝交给模型自由判断，也不浪费一次 LLM 请求。

### 3. 为什么这仍然是 Agent

Agent 的核心不是所有请求都必须由模型完全自治，而是模型能够基于上下文选择和使用能力完成任务。
本项目只把高置信、重复性强、风险高的环节确定化；模糊和组合任务仍由 Agent Loop 决策。

这是一种工程化自治：在需要灵活性的地方保留模型决策，在需要可靠性的地方提供受控轨道。

### 4. 阶段结果

相同的 12 个高风险代表场景由混合编排前的 `5/12` 提升到 `12/12`：

- 任务结果、编排合规和安全有效性均为 100%。
- Tool 参数、Skill 路由、Grounding 和 Citation 均为 100%。
- 阻断与冗余 Tool 尝试均为 0。
- Token 从 64,533 降到 45,204，下降约 29.95%。

这组定向结果达到完整矩阵的晋级条件，但没有被包装成完整 64 场景结果；之后仍执行了单独的
完整真实模型评测。

### 5. 为什么没有用语义路由彻底替换规则

规则的价值不是“先进”，而是在少量明确业务表达上提供高精度、低延迟和零模型依赖的快路径。
为了验证规则未命中的自然语言改写，项目另外实现了多语言 E5 语义回退，并用独立 calibration/
held-out 集确定最低相似度、Top-1/Top-2 margin 和次意图阈值。阻塞 Embedding 放在固定大小线程池
中，通过有界 admission 和 `asyncio` deadline 隔离；过载、超时或依赖缺失都退回受限 Open Agent。

实验中，已知意图准确率从 56.67% 提升到 60.00%，warm p95 为 23.441 ms，安全、Unknown 和组合
意图回退均保持 100%。但实际只多命中 1 条英文历史表达，而镜像增加约 1078.1 MiB、RSS 增加约
745.6 MiB；两轮 8 场景 qwen3.7 定向回归也都只有 6/8。最终没有为了“技术更新”强行替换主链，
默认保留规则，语义能力采用 feature flag 按需开启。

这个结果适合面试中回答模型/组件选型：除了离线准确率，还要看真实调用链、长尾延迟、内存、
镜像体积、故障降级和业务增益。负向实验也应保留，而不是只展示最终被采用的方案。

## 七、问题五：已经检索到知识，但最终回答遗漏 Citation

### 1. 首次混合编排完整评测

完成混合编排后，对 qwen3.7 重新执行完整 64 场景、79 轮真实评测：

| 指标 | 结果 |
|---|---:|
| 任务成功 | `61/64 = 95.3125%` |
| Prediction Grounding | 100% |
| Citation Validity | 96.875% |
| 编排合规率 | 96.875% |
| Token | 245,222 |
| 平均 / P95 延迟 | 6.84 秒 / 12.32 秒 |

三个失败包括：

- 一个比较场景达到步骤上限。
- 两个知识问答场景在获得有效资料后，最终回答遗漏 Citation。

### 2. 先区分两种完全不同的问题

#### 没有可靠答案

如果检索结果为空、相关性不足，或片段不包含回答所需事实，正确行为是明确告诉用户没有找到可靠
资料。此时不能为了满足 Citation 指标而随便附加一个来源。

#### 有可靠证据，但模型漏写 Citation

如果本轮 MCP 已返回有效 Citation，回答内容也确实来自该证据，只是模型没有在最终结构中引用，
这属于输出协议遗漏，可以进行有边界的修复。

区分依据来自 Tool Result 和本轮 Citation 白名单，而不是通过回答文本主观猜测。

### 3. 受控 Citation 修复

系统采用一次性修复，而不是重新开放完整 Agent：

1. 第一次最终回答正常经过 Citation Policy 校验。
2. 只有错误原因是“遗漏知识引用”，并且本轮确实存在有效 Citation 时，才进入修复。
3. 修复阶段关闭所有 Tool，防止重复检索或访问其他业务能力。
4. 只向模型提供本轮已经验证过的 Citation ID 白名单。
5. 要求模型基于原 Tool Evidence 重写最终回答，不允许引入新事实或新来源。
6. 修复结果重新经过完整 Grounding 和 Citation 校验。
7. 如果仍然遗漏、伪造或引用越界，则返回安全降级回答。

每个 Run 最多修复一次，避免形成“修复—失败—再修复”的无限循环。

### 4. 为什么不在服务端直接拼接 Citation

服务端直接在答案末尾追加一个 Citation 看似更简单，但它无法保证这个来源真的支持回答中的具体
陈述，可能制造“有引用外观、无证据对应”的假 Grounding。

受控重写让模型在原证据范围内重新组织回答，随后仍由确定性策略验证引用是否合法。模型负责表达，
系统负责事实来源边界。

### 5. 面试中可以强调

> 我们不会把所有漏引用都当成同一个问题。无证据时必须拒答；有证据但漏引用时只允许一次受控
> 修复。修复阶段禁止调用工具，并且只能使用当前 Run 已验证的 Citation ID，第二次仍失败就降级。

## 八、问题六：任务成功率和编排效率如何分开评价

### 1. 为什么不能只看精确 Tool 序列

同一个合法任务可能有多条安全执行路径。例如比较两个预测之前，模型可以从历史摘要获得 ID，
也可以在已有上下文中直接使用两个已验证的 ID。如果评测只接受唯一 Tool 序列，会把等价工作流
误判成失败。

但如果只看最终自然语言，又可能掩盖重复检索、无效调用和成本上升。

### 2. 三组独立指标

项目最终将评测拆为：

#### 任务结果

检查必要 Tool 是否成功、用户目标是否完成、最终回答是否可用。

#### 编排合规

检查是否存在重复 Tool、被 Guard 拦截的调用、不必要步骤和过长路径。

#### 安全有效性

检查 Prediction Grounding、Citation、Prompt Injection、No-Answer 和医疗边界。安全失败不能被
等价工作流或最终文案掩盖。

### 3. 最终结果应如何解释

最终完整评测中，64 个场景的必要业务流程和安全结果全部正确，但两个场景仍存在冗余调用，
因此：

- 任务成功率是 100%。
- Prediction Grounding、Citation 和安全有效性是 100%。
- 编排合规率是 96.875%，不是 100%。

这种表达比笼统声称“所有指标 100%”更真实。它既说明系统已经满足任务和安全门槛，也保留了
后续优化工具效率的空间。

## 十、这次调优形成的方法论

### 1. 先建立基线，再修改系统

没有固定数据集和版本化报告，就无法判断优化是否真的有效。每次正式结果都保留模型、数据集、
Prompt、Skill、知识索引和代码版本信息，不用新的结果覆盖旧报告。

### 2. 先分类失败，再决定修改哪一层

失败至少可能来自：

- 模型选择或规划错误。
- Tool Schema 和协议不清晰。
- 上下文没有正确注入。
- 知识证据不足。
- Grounding 或 Citation 校验失败。
- 评测器错误地限制唯一工作流。
- 超时、步骤上限或重复调用。

不同根因对应不同修复层，不能全部通过增加 Prompt 解决。

### 3. Prompt 管表达，代码管边界

Prompt 适合说明角色、回答风格和任务目标。权限、工具可见性、重试次数、超时、终止条件、
Grounding 和医疗安全必须由代码保证。

### 4. 让清晰任务确定化，让模糊任务保留自治

可预测的业务流程不需要每次由模型重新发明。确定性工作流减少 Token、延迟和错误面；开放 Agent
保留对模糊和组合请求的适应性。

### 5. 使用分层晋级控制成本

修复后不立即反复运行完整付费评测，而是按以下顺序验证：

1. 单元测试验证具体策略分支。
2. Fake LLM 完整 64 场景验证协议确定性。
3. 失败场景或 12 个代表场景执行真实模型复测。
4. 达到晋级门槛后再运行完整 64 场景。

这样既避免针对单个失败过拟合，也不会每次修改都消耗几十万 Token。

### 6. 不为了满分隐藏剩余问题

任务成功率达到 100% 后，仍保留 96.875% 的编排合规结果。真实工程中，正确性、安全和效率的
优先级不同，应分别度量和持续优化。

## 十二、面试官可能继续追问

### 1. 为什么不继续优化 Prompt？

Prompt 无法提供硬权限和确定性终止保证。提示词可以减少错误倾向，但模型版本、上下文和任务变化
后仍可能偏离。安全和资源边界必须由代码控制，Prompt 只负责目标与表达。

### 2. 使用确定性工作流后还算 Agent 吗？

算。系统没有取消模型决策，而是根据任务风险和确定性选择不同自治程度。明确业务流程走受控轨道，
模糊和组合任务仍由 Agent 动态选择工具。这比让所有请求完全自治更符合实际工程。

### 3. 为什么 qwen3.7 的通用能力更强，Agent 效果却更差？

通用推理能力和工具协议稳定性不是同一个指标。更强的规划倾向可能产生更多 Tool、Token 和状态
转换，从而在严格的步骤、权限和时延约束下更容易失败。模型必须通过项目自己的评测集晋级。

### 4. 为什么 Citation 修复只允许一次？

多次修复会增加成本和延迟，还可能形成无限循环。一次修复已经覆盖常见的格式遗漏；如果仍失败，
说明模型不能在当前证据和协议下可靠完成，应当降级而不是继续碰运气。

### 5. 为什么不由服务端直接附上 Citation？

直接附加只能证明系统有一个来源，不能证明来源支撑答案中的具体陈述。受控重写让答案与证据重新
对应，再由策略层验证 ID，避免产生形式正确但语义不 Grounded 的引用。

### 6. 64 个场景是否足以证明系统质量？

它足以作为当前版本的回归基线和面试工程证据，但不能证明所有真实用户问题都能成功。还需要持续
增加真实失败案例、多次稳定性运行和端到端权限测试。项目没有把一次 64/64 宣称为医疗质量证明。

### 7. 延迟主要来自哪里，怎样继续优化？

主要来自云端 LLM 的多轮调用，其次是 Tool 和 RAG。当前通过减少 Agent Step、指定 Tool、成功后
收窄工具和关闭思考模式降低延迟。后续还可以增加流式输出、公共知识缓存，并将长任务改成异步
Run，降低用户感知等待。

### 8. 为什么还保留关键词规则，语义路由不是更先进吗？

规则只覆盖安全边界、显式 Skill 和少量高精度业务表达，优点是快、稳定、无需模型；它不承担
全部自然语言理解。规则未命中时可以启用语义回退，但语义分数不是概率，仍要经过相似度、margin
和多意图门槛。最终默认是否切换由 held-out、真实 Agent 回归和资源成本共同决定。本项目因实际
只增加一条命中而继续默认规则，这比按技术新旧做选型更符合工程实际。

### 9. 语义路由为什么不能直接决定权限？

意图分类始终可能误判，只能帮助选择工作流和缩小候选 Tool。真正的权限仍由 C++ Gateway 签发
的 Capability、角色和资源归属检查决定。即使语义路由把请求分到历史查询，LLM 也不能借此改变
Session、患者主体或调用未授权接口。

## 十三、面试表达中的事实边界

可以说：

- 使用真实 qwen3.7 对 64 个多轮合成场景完成一次完整评测。
- 最终任务成功率、Prediction Grounding、Citation 和医疗安全指标为 100%。
- 编排合规率为 96.875%，仍有两个冗余调用场景。
- 与初始 qwen3.7 相比，Token 下降约 50%。
- 通过混合编排、动态 Tool 收窄和受控 Citation 修复提升稳定性。

不能说：

- 所有 Agent 指标都是 100%。
- 已经在真实患者数据上达到 100% 正确率。
- 本次决策评测证明 RBAC 零泄漏。
- 64 个场景可以证明医疗诊断质量。
- qwen3.7 本身比 qwen-plus 差。

推荐表述：

> 在固定的 64 个多轮合成决策场景上，真实 qwen3.7 的任务成功率由初始 56.25% 提升到 100%，
> Prediction Grounding、Citation 和医疗边界均为 100%；同时将 Token 消耗降低约 50%。评测仍
> 保留 96.875% 的编排合规结果，并将两个冗余调用场景作为后续效率优化项。
