# treeSem Agent 真实大模型调优：从 qwen-plus 到 qwen3.7 的工程治理案例

这份文档用于准备 Agent 项目面试，重点回答：接入真实大模型后遇到了什么问题、怎样定位、
为什么选择当前方案、最终如何验证。它不是一次简单的 Prompt 调参记录，而是一条完整的
“评测基线—失败归因—协议治理—分层验证—全量回归”工程链路。

面试时不需要背具体类名或函数名。应重点讲清问题现象、判断依据、解决思路、设计权衡和验证结果。

## 一、问题与解决方案导览

| 阶段与问题 | 关键现象与判断 | 主要解决方法 | 阶段结果 |
|---|---|---|---:|
| qwen-plus 首次完整评测存在失败 | 64 个场景只通过 55 个；失败同时来自模型行为、证据夹具和评测口径，不能统一归因为模型能力不足 | 逐条审计失败 Trace；区分任务失败与等价工作流；补充主题相关证据；约束 Skill 与 Tool 的执行顺序 | 原始结果保持 `55/64`，原始 9 个失败场景在同版本统一回归 `9/9` |
| 升级 qwen3.7 后效果反而下降 | 成功率从 85.94% 降到 56.25%，Token 和延迟同时上升；新模型更倾向完整规划、重复读取和追加工具 | 不按模型名称判断优劣；建立模型晋级门槛；通过 Trace 将失败拆成评测误差、冗余规划和实质失败 | 确认根因是模型规划风格与旧 Agent 协议不匹配 |
| 只靠 Prompt 无法稳定限制工具行为 | 模型可能理解约束但仍重复检索、激活不需要的 Skill，甚至在任务完成后继续调用 Tool | 把工具权限、重复调用、步数、超时和高风险拒绝下沉到确定性策略层 | Grounding 与安全保持 100%，但代表集仅 `5/12`，说明“只拦截”还不足以保证任务完成 |

| 模型已经获得资料却在回答中遗漏 Citation | 首次混合编排全量评测为 `61/64`；两个知识场景有证据但最终回答漏引用，另一个比较场景存在步骤与冗余问题 | 区分“没有证据”和“有证据但漏引用”；只对后者执行一次无 Tool、限定 Citation ID 的受控修复 | Citation 从 96.875% 提升到 100% |
| 成功率与工具效率混在一起 | 必要工作流已经完成，但额外只读调用会让严格 Tool 序列失败；直接记作任务失败不能反映真实用户结果 | 将任务结果、编排合规和安全有效性拆成独立指标；冗余调用继续保留为效率问题 | 最终任务成功率 100%，编排合规率 96.875%，没有掩盖剩余冗余 |
| 真实模型测试成本和稳定性不可控 | 完整评测包含 64 个场景、79 轮，盲目反复运行会浪费 Token，也难以判断修复是否有效 | 使用“单元测试 → Fake LLM 全量 → 小范围真实模型 → 完整真实模型”的分层晋级流程，并在运行前预估 Token | 最终完整评测使用 244,929 Token，低于早期 qwen3.7 的 489,683 Token |
| 小型路由集通过，但独立 Heldout 失败 | Calibration 上安全达到 100%、Hybrid 已知意图提升一倍；240 条 Heldout 中安全仅 20%、组合回退 52.5%、Hybrid Unknown 召回降到 85% | 冻结候选后只评一次，不用 Heldout 补词调参；区分 ONNX parity 与策略泛化，拒绝推广 Hybrid，并为下一版重新建立隔离数据周期 | 默认继续使用 Rule；保留 ONNX 候选和完整失败证据，没有用平均 F1 覆盖安全硬门槛 |

## 二、案例背景：为什么先建立评测体系，而不是直接调 Prompt

treeSem Agent 需要处理预测、解释、历史查询、结果比较、医学知识检索和 Skill 等多种任务。
如果只用几句人工提问判断模型表现，很容易出现三个问题：

1. 只记得成功案例，无法知道失败是否具有代表性。
2. Prompt、模型、Tool Schema 或知识索引变化后，结果无法公平对比。
3. 模型给出的文字看起来合理，但可能没有真实调用 Tool，或者引用了不存在的预测和资料。

因此项目先建立了固定的 64 场景、79 轮评测集，覆盖：

- 预测、解释、历史和比较。
- treeSem 模型知识与产后出血知识检索。
- 三类可信 Skill 的选择与执行。
- Tool 参数错误、上游失败和恢复流程。
- 无答案、Prompt Injection、伪造预测与医疗越界。
- Patient 和 Doctor 的不同回答场景。

评测不只检查自然语言是否“像正确答案”，还分别检查：

- 用户任务是否完成。
- Tool 是否选对、参数是否符合 Schema、必要顺序是否完成。
- Prediction ID 是否来自本轮真实 Tool Result。
- Citation ID 是否来自本轮知识检索结果。
- 无证据时是否正确拒答。
- 医疗边界和 Prompt Injection 防护是否有效。
- Agent Step、Tool Call、Token 和延迟是否受控。

这一步的面试价值在于：后续所有优化都有同一把尺子，而不是依靠主观感受宣称“效果变好了”。

需要说明的是，这是一套使用合成 Tool fixture 的真实 LLM 决策评测。它验证模型决策、编排、
Grounding 和 Citation，但不等价于真实患者数据测试，也不测 C++ Gateway 的真实 RBAC 链路。

## 三、问题一：qwen-plus 的失败并不都属于模型失败

### 1. 现象

使用 qwen-plus 对完整 64 场景、79 轮执行真实评测，原始结果为：

| 指标 | 结果 |
|---|---:|
| 任务成功 | `55/64 = 85.94%` |
| Tool 参数有效率 | 98.44% |
| Tool 结果有效率 | 96.88% |
| Skill 路由准确率 | 98.44% |
| Prediction Grounding | 98.44% |
| Citation Validity | 95.31% |
| 医疗边界 | 100% |
| Token | 347,727 |
| 平均 / P95 延迟 | 4.77 秒 / 7.52 秒 |

表面上看有 9 个失败场景，但逐条检查后发现，不能把它们都归结为“模型答错了”。

### 2. 如何定位

我们没有先改 Prompt，而是按一次 Agent Run 的完整 Trace 检查：模型看到了哪些工具、选择了什么
工具、工具是否成功、Grounding 是否满足、最终失败是任务失败还是评测规则失败。

最终将问题分成四类。

#### 第一类：评测器把等价工作流误判为失败

部分多轮场景中，模型为了确认当前状态，会重新读取一次历史或预测。用户任务已经正确完成，
但旧评测器要求 Tool 序列必须与预设路径完全相同，因此把安全的上下文刷新记成失败。

解决方法不是简单放宽所有规则，而是拆分两件事：

- 必要业务流程是否完成，决定任务是否成功。
- 是否出现多余工具调用，单独计入编排效率。

这样既不会把有效工作流误判为失败，也不会隐藏冗余调用。

#### 第二类：知识夹具没有提供足够证据

两个模型知识场景虽然返回了 Citation 对象，但检索片段只是通用占位文本，并不包含问题需要的
标准化或模型指标信息。此时模型拒绝回答是正确的 fail-closed 行为。如果为了追求通过率要求
模型强行回答，反而会鼓励幻觉。

解决方法是修正合成知识夹具，提供与问题主题真正相关、但不包含患者数据的证据。随后两个场景
真实复测 `2/2` 通过，Citation Validity 为 100%。

#### 第三类：Skill 激活与领域 Tool 同轮规划

模型可能在同一次响应中同时计划激活 Skill 和调用 Skill 依赖的领域 Tool，但 Skill 的可信指令
只有在激活后才能加载。如果允许二者并行，就会产生顺序不确定和权限边界模糊的问题。

解决方法是关闭并行 Tool Call，将流程拆成“先激活 Skill，再调用领域 Tool”。定向复测按串行
步骤完成，Skill、Tool 参数和 Grounding 均通过。

#### 第四类：安全拒绝与任务失败的语义混淆

例如用户要求虚构预测，策略层成功阻止了伪造，但旧系统将其表现为内部执行失败；无答案场景已经
正确拒答，旧评测却机械要求必须先检索。两者都会让安全行为在指标中看起来像系统故障。

解决方法是让策略拒绝返回稳定、安全的用户回答，并在评测中区分“安全场景正确拒绝”和“正常
任务未完成”。安全标准没有降低，只是修正了结果语义。

### 3. 阶段结论

原始 `55/64` 报告保持不变，没有反向修改历史数据。修复后又统一运行原始 9 个失败场景，结果为
`9/9`。面试中应明确这是“原始完整结果 + 同版本失败集回归”，不能把分散结果拼成一次虚假的
`64/64`。

### 4. 面试中可以强调

> Agent 失败不一定都是大模型能力问题。我会先区分模型错误、Tool 协议错误、证据不足和评测器
> 误判，再决定修改哪一层。否则很容易为了提高分数而降低安全规则，或者不断增加无效 Prompt。

## 四、问题二：升级到 qwen3.7 后，效果为什么反而下降

### 1. 现象

将模型切换到 `qwen3.7-plus-2026-05-26`，关闭思考模式，并使用相同的 64 场景、79 轮数据集
评测。结果不仅没有提升，反而明显下降：

| 指标 | qwen-plus | 初始 qwen3.7 |
|---|---:|---:|
| 任务成功率 | 85.94% | 56.25% |
| 成功场景 | 55/64 | 36/64 |
| LLM 请求数 | 183 | 222 |
| Token | 347,727 | 489,683 |
| 平均延迟 | 4.77 秒 | 9.46 秒 |
| P95 延迟 | 7.52 秒 | 16.49 秒 |

### 2. 根因并不是“新模型更笨”

通过失败 Trace 可以看到，qwen3.7 更倾向于：

- 在调用工具前规划完整任务链。
- 主动激活 Skill，即使当前问题并不需要。
- 为了确认上下文重复读取历史或预测。
- 已经检索到知识后继续检索。
- 必要比较已经完成后追加读取 Tool。
- 使用更多轮次组织最终回答。

这些行为在开放式推理任务中可能有价值，但在具有明确 Tool 协议、步骤上限和医疗安全边界的
Agent 中，会带来额外 Token、延迟和失败概率。

因此更准确的结论是：新模型的规划风格与原有 Agent 协议不匹配，而不是单纯的模型能力下降。

### 3. 为什么关闭思考模式

当前任务大多是结构清晰的 Tool Calling：选择预测、解释、历史、比较或知识检索工具，然后根据
结构化结果生成回答。开启长思考不能提升工具的真实业务能力，却可能增加：

- 首次响应时间。
- Prompt 与 Completion Token。
- 过度规划和重复调用。
- 输出协议偏离的概率。

因此评测固定关闭思考模式并设置温度为 0，优先追求工具调用稳定性。复杂、开放且确实需要推理的
任务可以单独评估是否使用思考模型，而不是给所有请求统一开启。

### 4. 面试中可以强调

> 模型选型不能只看发布时间和通用榜单。Agent 场景还要看 Tool Calling 稳定性、协议遵循、延迟、
> Token 成本和错误恢复。我们使用相同评测集做模型 Promotion Gate，因此发现新版模型在旧协议下
> 反而退化，没有直接因为名称更新就替换生产模型。

## 五、问题三：为什么只增加 Prompt 和 Tool Guard 仍然不够

### 1. Prompt 是软约束

最直接的办法是在系统提示词中反复强调“不要重复调用”“成功后立即回答”“不要擅自激活 Skill”。
但这些要求仍由模型理解和执行，无法成为可靠的工程不变量。

在医疗 Agent 中，以下约束不能只依赖 Prompt：

- 当前角色能看到哪些 Tool。
- 是否允许访问当前 Session 或患者。
- 工具调用次数、Agent Step 和总 deadline。
- 成功检索后是否还能再次检索。
- Prediction ID 和 Citation ID 是否真实存在。
- 高风险医疗请求是否必须拒绝。

### 2. 第一阶段：增加确定性 Tool Guard

系统根据当前意图和运行状态动态控制工具集合：

- 高置信意图只暴露必要工具。
- 成功检索后移除知识检索 Tool。
- 空结果或传输错误只允许一次有界重试。
- 完成历史或比较后收窄后续工具。
- 重复调用、越权参数和非法 Tool 在到达 C++ Backend 或 MCP 前被阻止。
- 步数、工具次数、总超时和重复调用具有代码级上限。

这一步把安全和资源边界从“模型建议”变成“系统保证”。

### 3. 新问题：系统安全了，但任务没有顺利结束

Tool Guard 后选择 12 个高风险代表场景进行真实复测，只有 `5/12` 成功。但同时：

- Prediction Grounding 为 100%。
- Citation Validity 为 100%。
- Prompt Injection 和医疗边界为 100%。
- 多余调用没有到达真实下游服务。

这说明 Tool Guard 确实保障了边界，但它只会告诉模型“这一步不能做”。模型收到结构化 Tool Error
后仍可能继续规划，最终耗尽步骤或没有及时生成最终回答。因此“阻止错误行为”和“帮助任务可靠
完成”是两个不同的问题。

### 4. 面试中可以强调

> Guard 解决的是安全与资源边界，不等于解决任务编排。仅仅拦截错误调用会让系统 fail-safe，
> 但不一定让用户得到结果；可靠 Agent 还需要明确的成功路径和终止路径。

## 六、问题四：用混合编排平衡确定性和 Agent 灵活性

### 1. 为什么不把所有任务都交给开放 Agent Loop

预测、解释、历史、比较和单次知识检索具有明确的工具和业务顺序。如果每次都让模型重新规划，
会重复消耗 Token，并增加错选工具、重复调用和超时风险。

但完全取消 Agent Loop 也不合理。用户可能提出模糊问题、组合多个目标，或需要在工具结果之间
进行动态选择。因此系统最终采用混合编排，而不是纯工作流或纯自治 Agent。

### 2. 混合编排流程

#### 高置信、结构清晰的请求

对于预测、解释、历史、比较、知识检索和显式 Skill 请求：

1. 安全拒绝和紧急医疗信号先由确定性策略处理，不进入语义模型。
2. 明确 Skill 和高精度业务词命中规则快路径，不执行 Embedding。
3. 可选语义路由只处理规则未命中的单一业务意图；低分、低 margin 和疑似多意图继续回到开放 Agent。
4. 命中确定性工作流后，每个阶段只暴露当前必需 Tool，并使用指定 Tool 的调用模式。
5. Tool 成功后进入下一阶段；必要事实收集完成后关闭工具调用，只让模型生成最终回答。

#### 模糊或组合请求

继续使用开放 Agent Loop，但保留：

- 动态工具可见性。
- Schema 校验和 Capability 权限。
- 重复调用检测。
- Step、Tool Call 和总超时上限。
- Grounding、Citation 与医疗边界校验。

#### 高风险请求

明确要求伪造预测、虚构来源、提供个体处方或替代医生判断的请求，由确定性策略层直接拒绝，
不把是否拒绝交给模型自由判断，也不浪费一次 LLM 请求。

### 3. 为什么这仍然是 Agent

Agent 的核心不是所有请求都必须由模型完全自治，而是模型能够基于上下文选择和使用能力完成任务。
本项目只把高置信、重复性强、风险高的环节确定化；模糊和组合任务仍由 Agent Loop 决策。

这是一种工程化自治：在需要灵活性的地方保留模型决策，在需要可靠性的地方提供受控轨道。

### 4. 阶段结果

相同的 12 个高风险代表场景由混合编排前的 `5/12` 提升到 `12/12`：

- 任务结果、编排合规和安全有效性均为 100%。
- Tool 参数、Skill 路由、Grounding 和 Citation 均为 100%。
- 阻断与冗余 Tool 尝试均为 0。
- Token 从 64,533 降到 45,204，下降约 29.95%。

这组定向结果达到完整矩阵的晋级条件，但没有被包装成完整 64 场景结果；之后仍执行了单独的
完整真实模型评测。

### 5. 为什么没有用语义路由彻底替换规则

规则的价值不是“先进”，而是在少量明确业务表达上提供高精度、低延迟和零模型依赖的快路径。
为了验证规则未命中的自然语言改写，项目另外实现了多语言 E5 语义回退，并用独立 calibration/
held-out 集确定最低相似度、Top-1/Top-2 margin 和次意图阈值。阻塞 Embedding 放在固定大小线程池
中，通过有界 admission 和 `asyncio` deadline 隔离；过载、超时或依赖缺失都退回受限 Open Agent。

实验中，已知意图准确率从 56.67% 提升到 60.00%，warm p95 为 23.441 ms，安全、Unknown 和组合
意图回退均保持 100%。但实际只多命中 1 条英文历史表达，而镜像增加约 1078.1 MiB、RSS 增加约
745.6 MiB；两轮 8 场景 qwen3.7 定向回归也都只有 6/8。最终没有为了“技术更新”强行替换主链，
默认保留规则，语义能力采用 feature flag 按需开启。

这个结果适合面试中回答模型/组件选型：除了离线准确率，还要看真实调用链、长尾延迟、内存、
镜像体积、故障降级和业务增益。负向实验也应保留，而不是只展示最终被采用的方案。

## 七、问题五：已经检索到知识，但最终回答遗漏 Citation

### 1. 首次混合编排完整评测

完成混合编排后，对 qwen3.7 重新执行完整 64 场景、79 轮真实评测：

| 指标 | 结果 |
|---|---:|
| 任务成功 | `61/64 = 95.3125%` |
| Prediction Grounding | 100% |
| Citation Validity | 96.875% |
| 编排合规率 | 96.875% |
| Token | 245,222 |
| 平均 / P95 延迟 | 6.84 秒 / 12.32 秒 |

三个失败包括：

- 一个比较场景达到步骤上限。
- 两个知识问答场景在获得有效资料后，最终回答遗漏 Citation。

### 2. 先区分两种完全不同的问题

#### 没有可靠答案

如果检索结果为空、相关性不足，或片段不包含回答所需事实，正确行为是明确告诉用户没有找到可靠
资料。此时不能为了满足 Citation 指标而随便附加一个来源。

#### 有可靠证据，但模型漏写 Citation

如果本轮 MCP 已返回有效 Citation，回答内容也确实来自该证据，只是模型没有在最终结构中引用，
这属于输出协议遗漏，可以进行有边界的修复。

区分依据来自 Tool Result 和本轮 Citation 白名单，而不是通过回答文本主观猜测。

### 3. 受控 Citation 修复

系统采用一次性修复，而不是重新开放完整 Agent：

1. 第一次最终回答正常经过 Citation Policy 校验。
2. 只有错误原因是“遗漏知识引用”，并且本轮确实存在有效 Citation 时，才进入修复。
3. 修复阶段关闭所有 Tool，防止重复检索或访问其他业务能力。
4. 只向模型提供本轮已经验证过的 Citation ID 白名单。
5. 要求模型基于原 Tool Evidence 重写最终回答，不允许引入新事实或新来源。
6. 修复结果重新经过完整 Grounding 和 Citation 校验。
7. 如果仍然遗漏、伪造或引用越界，则返回安全降级回答。

每个 Run 最多修复一次，避免形成“修复—失败—再修复”的无限循环。

### 4. 为什么不在服务端直接拼接 Citation

服务端直接在答案末尾追加一个 Citation 看似更简单，但它无法保证这个来源真的支持回答中的具体
陈述，可能制造“有引用外观、无证据对应”的假 Grounding。

受控重写让模型在原证据范围内重新组织回答，随后仍由确定性策略验证引用是否合法。模型负责表达，
系统负责事实来源边界。

### 5. 面试中可以强调

> 我们不会把所有漏引用都当成同一个问题。无证据时必须拒答；有证据但漏引用时只允许一次受控
> 修复。修复阶段禁止调用工具，并且只能使用当前 Run 已验证的 Citation ID，第二次仍失败就降级。

## 八、问题六：任务成功率和编排效率如何分开评价

### 1. 为什么不能只看精确 Tool 序列

同一个合法任务可能有多条安全执行路径。例如比较两个预测之前，模型可以从历史摘要获得 ID，
也可以在已有上下文中直接使用两个已验证的 ID。如果评测只接受唯一 Tool 序列，会把等价工作流
误判成失败。

但如果只看最终自然语言，又可能掩盖重复检索、无效调用和成本上升。

### 2. 三组独立指标

项目最终将评测拆为：

#### 任务结果

检查必要 Tool 是否成功、用户目标是否完成、最终回答是否可用。

#### 编排合规

检查是否存在重复 Tool、被 Guard 拦截的调用、不必要步骤和过长路径。

#### 安全有效性

检查 Prediction Grounding、Citation、Prompt Injection、No-Answer 和医疗边界。安全失败不能被
等价工作流或最终文案掩盖。

### 3. 最终结果应如何解释

最终完整评测中，64 个场景的必要业务流程和安全结果全部正确，但两个场景仍存在冗余调用，
因此：

- 任务成功率是 100%。
- Prediction Grounding、Citation 和安全有效性是 100%。
- 编排合规率是 96.875%，不是 100%。

这种表达比笼统声称“所有指标 100%”更真实。它既说明系统已经满足任务和安全门槛，也保留了
后续优化工具效率的空间。

## 十、这次调优形成的方法论

### 1. 先建立基线，再修改系统

没有固定数据集和版本化报告，就无法判断优化是否真的有效。每次正式结果都保留模型、数据集、
Prompt、Skill、知识索引和代码版本信息，不用新的结果覆盖旧报告。

### 2. 先分类失败，再决定修改哪一层

失败至少可能来自：

- 模型选择或规划错误。
- Tool Schema 和协议不清晰。
- 上下文没有正确注入。
- 知识证据不足。
- Grounding 或 Citation 校验失败。
- 评测器错误地限制唯一工作流。
- 超时、步骤上限或重复调用。

不同根因对应不同修复层，不能全部通过增加 Prompt 解决。

### 3. Prompt 管表达，代码管边界

Prompt 适合说明角色、回答风格和任务目标。权限、工具可见性、重试次数、超时、终止条件、
Grounding 和医疗安全必须由代码保证。

### 4. 让清晰任务确定化，让模糊任务保留自治

可预测的业务流程不需要每次由模型重新发明。确定性工作流减少 Token、延迟和错误面；开放 Agent
保留对模糊和组合请求的适应性。

### 5. 使用分层晋级控制成本

修复后不立即反复运行完整付费评测，而是按以下顺序验证：

1. 单元测试验证具体策略分支。
2. Fake LLM 完整 64 场景验证协议确定性。
3. 失败场景或 12 个代表场景执行真实模型复测。
4. 达到晋级门槛后再运行完整 64 场景。

这样既避免针对单个失败过拟合，也不会每次修改都消耗几十万 Token。

### 6. 不为了满分隐藏剩余问题

任务成功率达到 100% 后，仍保留 96.875% 的编排合规结果。真实工程中，正确性、安全和效率的
优先级不同，应分别度量和持续优化。

## 十一、问题七：Calibration 达标后，为什么路由仍未晋级

### 1. 现象

早期 150 条小型合成集上，E5 语义回退能够增加少量业务意图覆盖，并且 FP32 ONNX 与
SentenceTransformer 达到 150/150 最终路由一致。为了避免被小型数据误导，项目又冻结了 360 条
独立 Routing Quality Set：120 条用于 Calibration，240 条只用于最终 Heldout。

初次 Calibration 暴露出安全和组合表达覆盖不足。我们只使用 Calibration 将安全策略改为有限的
“危险动作 + 目标 + 上下文”概念组合，将独立业务意图、工作流依赖和跨工作流组合分开，并重新
选择语义阈值。冻结前结果为：

| Calibration 指标 | Rule | Hybrid |
|---|---:|---:|
| 已知单意图准确率 | 15.00% | 30.00% |
| 业务 Macro F1 | 23.67% | 41.20% |
| Unknown 召回率 | 95.00% | 95.00% |
| 组合请求回退率 | 95.00% | 95.00% |
| 安全准确率 | 100.00% | 100.00% |

如果只看 Calibration，Hybrid 已经满足预先设置的门槛。但冻结代码、Task Registry、阈值和 ONNX
Artifact 后，对 240 条 Heldout 只执行了一次正式对照，结果出现明显退化：

| Heldout 指标 | Rule | Hybrid |
|---|---:|---:|
| 已知单意图准确率 | 18.33% | 22.50% |
| 业务 Macro F1 | 25.64% | 31.15% |
| Unknown 召回率 | 97.50% | 85.00% |
| 组合请求回退率 | 52.50% | 52.50% |
| 安全准确率 | 20.00% | 20.00% |

Hybrid 的已知意图和 Macro F1 确实提高了，但 Unknown、安全和组合意图触碰了硬门槛，因此最终
没有晋级，默认路由继续使用 Rule。

### 2. 为什么 Calibration 看起来很好，Heldout 却失败

第一，安全概念词表仍然是有限的。Calibration 覆盖了角色伪造、凭据泄露、停药、手术决定和
紧急症状等概念，但 Heldout 使用了更多同义表达和概念组合，例如“关闭审计后读取患者记录”或
“忽略访问控制后读取另一位患者历史”。规则覆盖一个危险概念，不等于覆盖这个概念的全部自然
语言表达。

第二，语义路由器只包含预测、摘要、解释、历史、比较和知识六个业务 scope。它按设计不能产生
安全拒绝，也不能授予权限。因此安全规则漏判后，E5 只能把请求送入某个业务工作流或 Unknown，
不会自动补上安全判断。这个分层保证语义分类器不能扩权，但也说明安全召回必须独立解决。

第三，组合意图存在“多个独立任务”和“一个工作流的必要步骤”两种语义。例如“展示置信度并与
上一条比较”，实现认为摘要是 Comparison 的依赖，可以直接进入比较流程；语料却把所有显式双
意图统一标成 Unknown。这个失败不仅是规则漏词，也暴露了标注规范与工作流定义不完全一致。

第四，旧 150 条数据主要适合验证后端替换是否改变既有行为，不能证明新表达的泛化质量。
ONNX 150/150 parity 说明部署实现正确，但“实现与 PyTorch 一致”和“策略本身正确”是两个不同
问题。后端一致性不能替代独立质量评测。

### 3. 为什么没有针对 Heldout 继续补规则再测一次

Heldout 的价值在于模拟未见分布。如果看到失败后逐句补同义词、调阈值，再在同一批数据上宣布
通过，它就已经变成新的训练集，最终指标会失去可信度。因此项目保留原始失败结果，并执行以下
决策：

- 不把 Hybrid 切成默认主链。
- ONNX Artifact 作为可选实验后端保留，因为 parity 已单独通过。
- 本次 Heldout 只用于失败归因，不再用于当前版本调参。
- 下一版如继续挑战晋级，必须重新生成独立训练、Calibration 和 Heldout。
- 安全方向优先考虑“明确规则 + 召回优先的独立风险分类器 + 执行层 RBAC/Capability 兜底”，
  而不是无限扩充整句关键词。

### 4. 为什么这个失败对面试有价值

这个案例能够说明我不是只挑最好看的平均指标。路由策略即使提高 Macro F1，只要 Unknown 或安全
请求被错误确定化，就可能让 Agent 进入错误工作流，失败代价远高于少覆盖几个已知意图。因此发布
门槛必须区分收益指标和不可退化的安全指标。

面试中可以概括为：

> 我们先在 Calibration 上完成策略和阈值选择，冻结版本后只运行一次 Heldout。Hybrid 虽提高
> 业务 F1，但安全、组合意图和 Unknown 召回没有通过预先设定的硬门槛，所以没有推广。我保留
> 了 ONNX 部署成果，但没有把后端 parity 包装成路由质量。这次失败进一步推动我们把自然语言
> 安全召回与最终权限执行分层，并为下一版重新建立独立数据周期。

### 5. 问题—解决：为什么把“关键词路由”改成类型化规则

**遇到的问题：** 原实现虽然不是简单的单关键词等于一个意图，但动作词、对象词、上下文引用和
工作流依赖都混在同一个条件表达式里。它容易出现两类问题：一是看到“历史、置信度、比较”等
多个信号时，无法清楚区分它们是 Comparison 的必要步骤，还是两个真正独立的任务；二是评测只
给出总体准确率，无法区分“谨慎返回 Unknown”和“自信地走错 Workflow”。

**解决方法：** 保留有限词面匹配作为低成本证据提取，但先把证据归一化为三类结构：用户要执行
的动作、作用对象、引用的是当前/上一条/多条记录。独立 Taxonomy Resolver 只读取这些类型化证据，
按照六个业务 Scope 的必要条件和依赖关系决策。例如 Comparison 可以吸收读取历史和摘要，但
Comparison 与知识检索同时成立时必须拒识；证据不足或指代未绑定时也返回 Unknown。SafetyPolicy、
Tool Registry、Capability 和 RBAC 仍是独立边界，业务路由不能扩权。

**结果：** 在 150 条兼容集上，已知意图准确率为 55.56%，与旧实现的 56.67% 接近，但确定性
路由精度达到 100%，Unknown、组合请求和安全准确率均为 100%。在允许诊断的 120 条 Calibration
上，已知意图准确率由旧实现的 15.00% 提升到 20.00%，确定性精度为 75.00%，Unknown、组合和
安全保持 95%、95%、100%。已经揭晓的 240 条 Heldout 没有被再次用于调参或宣称晋级。

**工程结论：** 关键词并不是最终架构判断，而是可替换的低成本证据来源。真正稳定的是后面的
Taxonomy、拒识语义、Tool 权限和评测口径。以后即使把证据来源换成分类模型或 LLM Router，也不
需要推翻 Workflow 与安全执行层。

## 十三、面试官可能继续追问

### 1. 为什么不继续优化 Prompt？

Prompt 无法提供硬权限和确定性终止保证。提示词可以减少错误倾向，但模型版本、上下文和任务变化
后仍可能偏离。安全和资源边界必须由代码控制，Prompt 只负责目标与表达。

### 2. 使用确定性工作流后还算 Agent 吗？

算。系统没有取消模型决策，而是根据任务风险和确定性选择不同自治程度。明确业务流程走受控轨道，
模糊和组合任务仍由 Agent 动态选择工具。这比让所有请求完全自治更符合实际工程。

### 3. 为什么 qwen3.7 的通用能力更强，Agent 效果却更差？

通用推理能力和工具协议稳定性不是同一个指标。更强的规划倾向可能产生更多 Tool、Token 和状态
转换，从而在严格的步骤、权限和时延约束下更容易失败。模型必须通过项目自己的评测集晋级。

### 4. 为什么 Citation 修复只允许一次？

多次修复会增加成本和延迟，还可能形成无限循环。一次修复已经覆盖常见的格式遗漏；如果仍失败，
说明模型不能在当前证据和协议下可靠完成，应当降级而不是继续碰运气。

### 5. 为什么不由服务端直接附上 Citation？

直接附加只能证明系统有一个来源，不能证明来源支撑答案中的具体陈述。受控重写让答案与证据重新
对应，再由策略层验证 ID，避免产生形式正确但语义不 Grounded 的引用。

### 6. 64 个场景是否足以证明系统质量？

它足以作为当前版本的回归基线和面试工程证据，但不能证明所有真实用户问题都能成功。还需要持续
增加真实失败案例、多次稳定性运行和端到端权限测试。项目没有把一次 64/64 宣称为医疗质量证明。

### 7. 延迟主要来自哪里，怎样继续优化？

主要来自云端 LLM 的多轮调用，其次是 Tool 和 RAG。当前通过减少 Agent Step、指定 Tool、成功后
收窄工具和关闭思考模式降低延迟。后续还可以增加流式输出、公共知识缓存，并将长任务改成异步
Run，降低用户感知等待。

### 8. 为什么还保留关键词规则，语义路由不是更先进吗？

规则只覆盖安全边界、显式 Skill 和少量高精度业务表达，优点是快、稳定、无需模型；它不承担
全部自然语言理解。规则未命中时可以启用语义回退，但语义分数不是概率，仍要经过相似度、margin
和多意图门槛。最终默认是否切换由 held-out、真实 Agent 回归和资源成本共同决定。独立 Heldout
中 Hybrid 虽提高业务 Macro F1，却让 Unknown 召回降到 85%，安全和组合门槛也失败，因此继续
默认规则。这比按技术新旧或只看平均指标做选型更符合工程实际。

### 9. 语义路由为什么不能直接决定权限？

意图分类始终可能误判，只能帮助选择工作流和缩小候选 Tool。真正的权限仍由 C++ Gateway 签发
的 Capability、角色和资源归属检查决定。即使语义路由把请求分到历史查询，LLM 也不能借此改变
Session、患者主体或调用未授权接口。

### 10. 你的规则路由是不是传统关键词匹配，为什么还值得保留？

底层仍使用有限词面信号，因为它延迟低、可测试且不需要额外模型，但不是“命中一个词就选择一个
Workflow”。系统先抽取动作、对象和引用，再由类型化 Taxonomy 判断必要条件、工作流依赖和组合
冲突；证据不完整就拒识。它只承担高精度快路径，开放 Agent 负责长尾表达，权限仍由执行层保证。
评测也同时看精度、覆盖率、放弃率、误路由率和 OOD/组合强制路由率，而不是只看关键词命中数。

## 十四、面试表达中的事实边界

可以说：

- 使用真实 qwen3.7 对 64 个多轮合成场景完成一次完整评测。
- 最终任务成功率、Prediction Grounding、Citation 和医疗安全指标为 100%。
- 编排合规率为 96.875%，仍有两个冗余调用场景。
- 与初始 qwen3.7 相比，Token 下降约 50%。
- 通过混合编排、动态 Tool 收窄和受控 Citation 修复提升稳定性。
- FP32 ONNX 路由后端通过 parity，但 Hybrid 策略没有通过独立 Heldout 晋级门槛。

不能说：

- 所有 Agent 指标都是 100%。
- 已经在真实患者数据上达到 100% 正确率。
- 本次决策评测证明 RBAC 零泄漏。
- 64 个场景可以证明医疗诊断质量。
- qwen3.7 本身比 qwen-plus 差。
- 当前 Hybrid 语义路由已经进入默认主链。
- ONNX parity 可以证明路由策略具有未见表达泛化能力。

推荐表述：

> 在固定的 64 个多轮合成决策场景上，真实 qwen3.7 的任务成功率由初始 56.25% 提升到 100%，
> Prediction Grounding、Citation 和医疗边界均为 100%；同时将 Token 消耗降低约 50%。评测仍
> 保留 96.875% 的编排合规结果，并将两个冗余调用场景作为后续效率优化项。

## 十六、后续：组合请求的执行收敛与输出治理

2026-09-13 的独立试验继续验证一个问题：**工具都成功，不代表最终回答完整。**
同一“比较加知识解释”切片中，开放规划每次需要 5 次 API 请求，改为复用现有只读 Workflow
依赖后每次只需 1 次；三次重复的平均 Token 减少约 82.6%。这是局部切片效果，不外推为整站指标。

本轮将最后一步保留给无 Tool Finalizer，加入请求级 completed/pending 和裁剪证据，
同时最多进行一次最终协议修复。没有扩大 Router Schema，也没有增加独立 Reflection Agent。
审查特别补测了批量 Tool 配额、相对目标误用历史旧页和部分执行错误宣称成功。

新的 36 条冻结集首轮按固定流程口径通过 34/36；然而综合子目标/约束仅通过 22/36。
14 条引用在响应数组中合法存在，却没有出现在正文，说明引用合法率和回答完整性必须分开。
另外两条顺序失配实际已取得全部证据，暴露固定序列评分与用户真实要求之间的差异。
本轮不在揭晓后改评分提高原成绩；正文引用修复后的同集成绩只作为回归证据。

面试可重点讲：“我没有继续扩大路由模型，而是先区分语义解析、执行收敛和输出完整性。
程序负责预算、目标事实和数据裁剪，模型负责表达；再分别验证工具、引用、约束和最终答案。”
详细数据、局限和后续回归见[执行收敛与最终回答协议试验](reports/agent-execution-finalization-trial.md)。

### 比较差值正确，为什么自然语言仍会说反？

原始接口的差值定义是 B-A，调用时 A 是本次、B 是上一次。评测夹具中，前次概率 0.34、本次 0.82，
所以接口的 -0.48 正确，但按时间应描述为上升 0.48。有的回答直接把负号解释为风险下降，
甚至说“从 0.34 降至 0.82”。这不是预测模型数值问题，而是接口排序与时间语义之间的转换没有固定下来。

继续提醒 Prompt 仍不能稳定解决。因此程序在给模型的证据副本中直接规范为“上一次→本次”，
统一转换概率、置信度和特征差，并提供增加/减少/不变及百分点表示；不同时暴露方向相反的 A/B 数据。
原始业务结果保持不变。无法确认时间顺序的显式 ID 比较只说明指定顺序，不推断本次/上次。
开放执行稍后才取得历史时，最终作答前从原始事实刷新证据，避免二次取反。

确定性回归覆盖上升、下降、不变及未知目标；相同模型的 12 条定向真实回归中，逐条检查的概率方向均正确，
原来确认矛盾的 3 条没有再出现。该结果只是已揭晓集合的一次定向回归，不包装成整体质量 100%。

面试可概括为：“能由程序确定的业务方向和数值转换，不交给模型自由推理。
我让业务层负责事实，证据表达层负责顺序与单位口径，LLM 负责自然语言组织，并分别验证这三层。”

## 十七、真实语义路由对照：为什么执行成功不等于用户任务完成

### 问题一：标准答案 Router 会不会让评测看起来更好？

会。此前定向执行回归由夹具提供正确 Router Frame，适合验证依赖、裁剪和比较方向，不能证明真实模型理解了用户。
因此另冻 48 条指代、否定、组合、缺失与安全场景，让正式 Structured Router 真实调用云模型；Gold 只用于评分，不放入 Prompt。
Tool 按请求 ID 返回独立记录，比较按实际参数计算 B-A，避免“调用错记录但夹具仍给正确结果”的假通过。
两套模式共享同一试验代码与合成记录，每条交替运行顺序。该设计测真实模型编排，不冒充真实 MySQL、RBAC 或 ONNX 进程级 A/B。

### 问题二：全是路由超时，是否应该先改 Prompt？

不应先归因 Prompt。原 3 秒单次预算下七条 Structured 均未进入业务执行，单独探针却在 3.83 秒返回合法结构。
12 条无语义 Gold 的延迟探针均合法，经验 p95 4.605 秒、最大 5.355 秒；据此只在评测里采用 6 秒单次／13 秒总预算。
同时复用正式独立 Router 客户端：384 输出 Token、关闭思考、客户端不嵌套重试。原诊断不并入正式质量成绩，校准后的同集结果也不叫全新 Heldout。
面试回答重点是先区分预算失败、格式失败和语义失败，再决定改哪一层，而不是每次都加 Prompt。

### 问题三：工具成功、有引用，为什么人工评分仍会下降？

legacy 自动最低契约通过 26/48，逐条看答案却只有 20/48 完成任务：合法请求被通用引用兜底替代，缺少历史也不说清需要什么。
Structured 自动与人工都是 41/48，但并非同一批成功：人工剔除未答标签含义和误用“比较”澄清，认可明确安全拒绝。
一个正文把预测 ID 截短，canonical grounding 数组却正确，说明“引用数组合法”和“正文可追溯”不能合并成一个指标。
处理思路是保留原自动分数、另审阅最终语义，分别统计目标、证据、数字方向、用户约束和安全拒绝。不要揭晓后改评分把成绩刷高。

### 问题四：新方案明显更好，为什么不直接上线？

本轮 Structured 已知 Token 减少 15.83%、物理请求减少 28.46%，组合任务和上次目标明显改善；但把大量出血伴晕厥感误判为演示预测，询问样本索引。
这是关键安全失败，不能用平均成功率掩盖。还有 Summary(previous) 的绑定缺口、知识子问题落到非法 Aspect、缺失上次记录时给出比较兜底。
当前先保留隔离分支与全部失败，下一轮做紧急安全、目标相关澄清、正文协议的最小修复，再用已揭晓回归加新表达与真实 Tool smoke 验证。
不新增顶层 Router 字段、不加独立 Reflection Agent、不自动切默认；具体结果与限制见[真实 Router 独立对照](reports/independent-router-execution-evaluation.md)。

### 问题五：断点续跑和成本统计有什么坑？

请求在 HTTP 发起前计数；即使 429、取消或 Tool arguments 非法，也不能把物理尝试和已返回 usage 丢掉。未返回 usage、未 checkpoint 的中断请求单列未知，已知 Token 只报下界。
观察器只能记录 Frame，不能把业务验证移到 Router 阶段，否则改变真实异常路径。续跑还必须冻结实际 attempts/context、回答配置、模型与评测源码，不只比较文件名和模型名。
这一轮修正计量、观察器与未来 checkpoint 校验，但不改写原首轮报告。面试可概括为：“评测工具也要测试；先保证证据可信，再用数据决定是否采纳架构改进。”

## 十八、可靠性修复：为什么不继续把所有问题都交给 Prompt

**紧急表达问题：**“我产后突然大量出血而且快晕倒了”没有“现在”这个字，旧规则放行，Router 随后误当样本预测。
不是继续加一条完整问句，而是修正时间与症状上下文：突发状态、否定、历史、假设作用域分别处理，当前症状在分句之间可有限聚合。
复审发现并补测了两个反方向错误：全句“如果／以前”掩盖真正症状，以及句号把出血与头晕割裂。最终紧急提示在模型前完成，不等待云服务。
这仍是有限安全概念检查，不声称替代医疗审核器；真实权限仍由 C++ 授权决定。

**目标澄清问题：**用户给出来源可校验的预测 ID 后，模型仍填“目标缺失”；用户只有一条记录、要看上一次，却收到“无法比较”的回答。
程序仅消解单一 explicit 候选的 missing 标记，不消解歧义、不猜 ID、不判断数据库存在；随后查真实记录。
历史不足的回答按实际目标生成，依赖 history 中的当前记录不会被引用成上次。自然语言理解和事实定位仍分层。

**输出协议问题：**完整 grounding 数组没有防止正文 ID 截短，协议字段也可能混入正文。
程序先识别候选再校验完整性，畸形 ID 最多进入一次无 Tool 格式修复，不自行补全 ID。
行首、内联、带引号 grounding 字段均被拒绝；只使用已有证据和允许 ID，不重复推理、查询或其他副作用。

6 条已揭晓定向真实回归通过，共 4 次云请求、7,638 Token；14 条新增确定性测试覆盖反例和修复路径。
这里应讲“哪些缺陷被复现、改在哪一层、怎样验证没有反向误判”，而不是讲“系统已经 100% 正确”。详见[可靠性回归证据](reports/agent-reliability-targeted-regression.md)。

## 十九、从修复个例到契约一致性：哪些地方不能靠刷分解决

**上次摘要为什么被拒绝？** 模型已经给出正确的上次目标，但 summary 的允许目标和 Workflow 没有与 explanation 对齐。
处理方式不是为“上一份／前一条”各加规则，而是给摘要补齐同一目标语义，复用历史头部查询及第二条真实 ID 绑定。
在当前、上次、明确 ID 的目标定位之后，再决定读取摘要还是解释；历史不足的文案与引用也要符合实际目标。

**Schema 合法为什么仍报非法结构？** JSON 类型校验不负责所有业务字段组合。旧代码在 Router 外发现非法 Aspect，无法进入格式修复。
这轮抽出一份纯跨字段契约，解析与绑定共用，错误仅反馈允许枚举与安全原因码，仍受原两次总尝试和 deadline 限制。
复审又发现 explicit missing 的提前返回不一致，补了失败测试并共享判定；候选来源、资源存在与权限没有移交模型。
面试应强调“统一可校验的契约和事实来源”，而不是把一次修复包装成独立 Reflection Agent。

**检索成功为什么仍然没回答问题？** 标签含义场景取到了 PPH、AUC 等资料，但资料没有定义标签编码。
Finalizer 现在区分“检索完成”和“答案覆盖未验证”，要求缺证据就指出对应缺口、保留可信业务结果。
真实定向六条的自动最低契约均过，但人工检查原标签问题仍漏答，新问法才明确承认缺口；还有一次无证据技术机制扩展告警。
因此没有改标准答案或宣传 100%，也没有继续逐句增加特殊规则。下一步应补可信元数据，而不是把资料不足都归因 Prompt。

本轮 12 次真实请求、24,462 Token；包括三条已揭晓回归和三条表达变体，不叫新 Heldout。完整证据见[契约一致性回归](reports/agent-contract-consistency-regression.md)。

## 二十、资料不足怎样修：补可信知识，而不是为答案造规则

**问题：** Agent 能拿到比较结果和一些模型资料，却没有回答标签 0/1 的含义；另一次把解释树叶变化说成神经网络概率变化的原因。前者存在知识缺口，后者混淆了输出来源，不能一概用“Prompt 不够强”解释。

**处理：** 先核对训练标签映射、Bundle 数值契约和确定性 predictor，区分可证明的编码与未知临床定义；再把负/正类、概率/置信度、神经分类与原生树的不同来源写成受 checksum 管理的模型知识。通过既有检索接口提供引用，不扩 Router Schema、不为原问题增加关键词规则，也不擅自补临床语义。

**验证：** 同一固定模型与原校准阈值下，患者/医生的三类问题都将对应新章节排第一；临床结局问题只取得缺失说明。原评测 fixture 和分数保留。本轮验证了真实本地检索与执行回归，尚未验证新证据条件下的云端完整回答，所以不写“标签问答全部修复”或“模型准确率提升”。

**面试表达：** “我把问题分成执行契约错误、证据缺失和无依据扩展，再分别修在程序契约、知识治理和回答验证层。检索成功不等于答案有依据，补资料也不等于模型变聪明；评测要冻结证据条件才能公平比较。” 见[标签知识验证报告](reports/agent-label-knowledge-regression.md)。

## 二十一、真实验证又发现什么：安全拒绝不总是正确拒绝

**问题：** 新知识索引通过官方 MCP 返回了概率/置信度资料，但正确带 citation 的术语解释仍降级。只看 API 没抛异常或 Tool success 会漏掉这个问题。

**定位办法：** 冻结原 18 条结果后，额外增加安全响应检查观测，再对照有/无当前预测上下文。两种术语问法都被同一个 `missing_prediction_grounding` 拦住：响应策略把“概率、标签”等词直接当作患者预测事实，而通用模型知识本来只需知识来源。另一条机制问答则附上未由 Native Tool 读取的当前 ID，被拒绝是正确的，不能把两类拒绝一并放宽。

**经验：** 事实防幻觉应区分证据种类。一般模型说明需要知识引用，具体患者结果需要业务 Tool 证据；有知识 citation 不能自动授权患者数值，出现概率术语也不能自动要求患者 ID。这里只完成定位，尚未修复，因此不写成“调优已完全成功”。

**另一项发现：** 三个 Subgoal 均取得证据且原始目标没有丢失，最终模型仍从仅路径证据扩展了“主要特征关联”。说明数据裁剪能减少输入，但不自动保证文本约束。后续应治理回答的证据边界，不急着扩 Router Schema 或放开 Tool 重复。

完整的原条件、新证据条件、诊断对照和计量边界见[四项改动真实验证](reports/agent-four-feature-real-regression.md)。

## 二十二、如何修复证据边界，而不是越修越严格

**问题一：正确的知识解释被当成患者事实。** 用户问概率和置信度的定义，Agent 已检索到资料并给出有效引用，但响应规则看到“概率、标签”就要求患者预测 ID。即使移除当前患者上下文仍会失败，说明根因是证据分类，而不是模型不会回答或 RAG 没有答案。

**解决：** 程序根据已验证任务确定知识-only 范围，并检查本轮实际取得的来源引用。在这个有限范围内，模型输出定义、标签编码和总体指标只需要知识证据，不要求先做患者预测；具体患者结果仍需要业务证据。不能让最终模型自报“我是知识问答”来放宽校验，也不能见到任意 citation 就放过患者数值。

**问题二：为避免 ID 污染删除全部历史，又丢掉了知识追问。** “macro-F1 是什么”之后再问“解释它”，Router 仍有历史，但检索与最终回答没有主题。恢复整段患者聊天会重新引入无关记录与临床值。

**解决：** 只保留闭集公共术语名称作为主题提示，传给明确工作流的检索和最终上下文，不传历史患者值、ID 或原聊天。无法唯一解析时澄清。这不是新增 Semantic Router 或第二个 LLM 调用，而是有限任务域里的上下文最小化。

**问题三：有限患者值检测不能只认一个表达模板。** 审查发现“你的概率升至70%”“你上次的概率”“positive_probability”能漏过，逗号也会把患者主题和数值拆开；另一方面，总体 Accuracy 加上“不是你的预测概率”的免责声明可能误拦。

**解决：** 先把这些真实可复现的表达加入失败测试，再检查患者指代、预测术语与后续数值的归属关系，而不是逐个补“升至、变成”等动词。完整 ID 与可用引用集合检查仍保留。这里的有限 tripwire 不宣称可以证明任意自然语言没有患者事实。

**验证结果与反例保留：** 15 项新边界测试、534 项全部 Agent 测试（4 跳过）及 55 项重点测试连续20轮通过；真实模型分5条阶段验证和3条最终补测，术语/机制说明正确引用、不再误拦。阶段一综合回答仍有无证据的“主要特征影响”，最终补测虽未再出现该句，仍有“百分点”写成“百分比”，以及把模型正类概率扩展为临床风险评分等语义告警。模型类别和树阈值也应与临床结局、异常范围分开。自动契约通过不等于最终语义满分，失败不能被后续一次成功覆盖。

**面试经验：** 事实防幻觉的重点不是一味严格，而是让业务事实、一般知识和定位上下文有不同的证据要求；同时区分“执行取得了全部证据”和“自然语言正确表达了这些证据”。本轮收敛在已有接口的小范围修复，没有扩大 Router Schema、建设逐句审查系统或宣称自由文本绝对可靠。

详细结果、源码版本和用量见[证据边界修复报告](reports/agent-evidence-boundary-fix.md)。

## 二十三、精确事实与自然语言怎样兼得

**问题：** 比较服务已经给出从 0.20 到 0.70、差值 0.50，最终回答仍可能把“增加 50 个百分点”改写成“增加 50%”。这两种表达的数学含义不同；增加 50% 对 20% 而言通常是升至 30%，而从 20% 升至 70% 的相对增幅其实是 250%。同时，模型还可能把正类概率称为临床风险评分，把模型类别称为诊断阴阳性，把超过树阈值称为临床异常高值。

**根因：** 后端虽然完成了计算，但传给最终模型的字段是平铺的浮点数，数值、展示单位和语义边界没有组成一个不可歧义的契约。提示模型“不要重新计算”只能表达意图，不能消除 `%`、百分点、模型编码和临床含义之间的歧义。

**解决：** 保留原比较字段以兼容已有流程，同时增加结构化指标变化块：原值和新值使用 `percent`，绝对差使用非负数和 `percentage_points`，方向单独表示，相对增幅明确标记为未计算。类别变化只声明模型负类/正类编码；解释范围明确说明当前比较不支持临床终点、医学参考范围或因果归因。程序不生成整段回答，LLM 仍可自由调整措辞、顺序和详略，但不能改变结构化事实。

**可靠性处理：** 可选的旧版摘要字段缺失时继续保留旧差值路径，不凭空生成展示块；字段一旦出现，则必须是 0～1 的有限数值，`null`、字符串、NaN 和越界值在 Tool 输出边界拒绝。差值必须是 `[-1,1]` 内有限数值；两侧分数都存在时，还要与后端约定的 `B-A` 在浮点容差内一致。下降场景的绝对差保持非负，由独立方向字段表达下降，避免“负的绝对差”自相矛盾。

**面试表达：** “我没有把 Agent 改成固定话术，而是把精确计算和语言生成解耦。业务层输出带单位和语义范围的事实对象，模型只负责把事实组织成人话。这样保留生成能力，同时避免模型重新计算、偷换指标或把模型相关性扩展成临床结论。”
