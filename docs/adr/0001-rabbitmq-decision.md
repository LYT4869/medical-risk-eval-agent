# ADR-0001：当前不在 treeSem 同步主链引入 RabbitMQ

## 状态

接受，M9。

## 决策

即时预测、查询和交互式 Agent Chat 继续使用 HTTP、隔离的有界 Worker Pool、超时和 503 背压，不接入 RabbitMQ。消息队列不能缩短 ONNX、MySQL 或 LLM 的实际执行时间，反而会把同步调用改造成任务状态、幂等消费、重试、死信与补偿问题。

现有本机基线已经证明 C++ ONNX 单样本主链可以达到约 978 QPS，ONNX 加 MySQL 持久化约 222 QPS；系统的合理失败方式是队列达到容量后快速返回 503，而不是无限堆积请求。M9 的 k6 场景继续记录 p50/p95/p99、队列深度、连接等待、RSS 和拒绝数，以便根据新数据调整线程池与连接池。

## 重新评估条件

只有出现批量离线预测、超过 HTTP 生命周期的长任务、重启后必须继续执行、跨机器扩容 Worker，或明确需要任务状态、死信队列和人工补偿时，才重新评估 RabbitMQ。交互式 Chat 即使很慢，也优先采用流式响应、超时和取消，而不是把消息队列当作降低延迟的手段。
