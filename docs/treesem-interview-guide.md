### 项目题回答公式

1. **场景**：为什么会出现这个问题，直接危害是什么。
2. **方案**：系统在哪一层处理，主流程是什么。
3. **关键不变量**：线程、对象生命周期、超时、数据或模型语义如何保证。
4. **权衡**：为什么采用当前复杂度，没有使用另一种方案。
5. **验证与边界**：怎样证明有效；当前明确不支持什么。

例如不要只回答“我用了线程池”。更好的回答是：“模型调用会阻塞，如果在 I/O 线程中
执行会拖住同一事件循环上的其他连接，所以我把预测投递到独立的有界工作池；队列满时
快速返回 503，完成后再把响应投递回原连接的事件循环。这样保护了网络线程，但目前还
没有端到端 deadline 和按用户优先级调度。”

### 三种回答标签

复习时必须区分下面三种表述：

- **已实现**：代码中存在，并有测试或真实运行证据，可以说“我实现并验证了”。
- **框架原有**：Kama/Muduo 已提供，我们阅读、修复或接入了部分能力，应说“基于该框架
  二次开发”，不能包装成完全从零实现。
- **生产化改进**：当前没有实现，只能回答“如果继续生产化，我会……”。

## 项目事实与表述边界

### 可以主动写入简历的能力

- 基于 Kama/Muduo HTTP Server 进行二次开发，修正并测试 HTTP 请求体解析、异步路由和
  响应回投机制。
- 将阻塞模型调用从 EventLoop 隔离到有界工作线程池，支持队满快速拒绝、异常隔离和
  优雅排空。
- 按 API、应用、模型抽象、基础设施四层重构预测后端，远程 Python 和本地 ONNX 共享
  同一模型接口。
- 设计带 Schema、预处理参数、原生决策树、模型版本和 SHA-256 校验的 Serving Bundle。
- 将确定性神经网络子图导出 ONNX，由 C++ ONNX Runtime 执行；Scaler 和决策树由 C++
  原生实现。
- 支持 ONNX 主链、Python fallback 和 shadow 对比；在 1489 个参考样本上验证连续值、
  label、cluster、叶节点和决策路径一致性。

### 必须谨慎表述的能力

| 主题 | 正确说法 | 不能说 |

| TLS/Session/CORS | 原框架有相关组件，但尚未作为 treeSem 医疗主链完成生产验证 | 当前系统已有完整医疗安全体系 |
| HTTP/1.1 | 支持请求行、Header、Content-Length body 和基本 keep-alive | 完整实现 RFC、chunked 和 pipelining |
| ONNX 加速 | 当前环境下 C++ 主链延迟和吞吐有改善 | 在所有机器和负载下一定更快 |
| 模型一致性 | 证明 C++ 部署没有改变当前模型语义 | 证明模型医学质量优秀或可直接临床使用 |
| SHA-256 | 检测 Bundle 文件被意外修改或版本错配 | 防止有密钥攻击者恶意替换模型；那需要签名 |
| fallback | 本地推理运行异常时进行一次 Python 兜底 | 任意错误都重试，或保证永不失败 |

### 当前明确边界

- 当前 HTTP parser 不支持 `Transfer-Encoding: chunked`。
- 当前不能宣称正确支持 HTTP pipelining；一次读到多个完整请求时，剩余数据可能等待新的
  可读事件，因此生产化前应改为循环消费完整请求。
- 当前未建立完整的请求行、Header、body 大小上限和慢请求读超时，Slowloris、超大 Header
  与超大 body 防护属于必须补强项。
- 当前下游模型调用有连接超时和总请求超时，但没有贯穿排队、推理和回包的端到端 deadline，
  也没有协作式取消正在执行的推理。
- 当前 503 是实例级有界队列的过载保护，不等于完整限流、熔断或多租户配额。
- 当前默认 fallback 是可用性策略，不是医疗安全决策；上线前还需要业务风险分级和人工复核。
- 当前 PPH 指标与论文预期存在差距，另设模型质量审计阶段；不阻塞工程链路完成，但不能把
  当前产物描述为临床可用模型。

## 异常与高并发场景总表

面试官往往不会问“你处理了什么异常”，而会给出故障现象让候选人沿调用链分析。

| 场景 | 主要风险 | 当前项目处理 | 继续生产化 |
|---|---|---|---|
| 模型调用阻塞 | EventLoop 被拖住，所有连接延迟上升 | 投递独立有界工作池 | 端到端 deadline、取消 |
| 瞬时请求洪峰 | 无界排队、内存增长、尾延迟雪崩 | 队满快速返回 503 | 网关限流、优先级、Retry-After |
| Python 连接失败或 5xx | 主请求失败 | 远程模式映射为 502 | 熔断、实例发现、告警 |
| Python 响应超时 | Worker 长期占用 | 连接和总请求超时，返回 504 | deadline 传播、重试预算 |
| ONNX 单次运行异常 | 本地主链不可用 | 默认一次 Python fallback | 熔断/降级开关、容量预留 |
| ONNX 文件或 Bundle 损坏 | 带坏模型提供服务 | 启动校验并 fail fast | 签名、制品仓库、回滚 |
| Python 与 ONNX 结果漂移 | 灰度后语义改变 | shadow 比较，主结果不受影子失败影响 | 指标、采样、自动阻断发布 |
| 下游返回非法 JSON/缺字段 | 错误数据进入业务 | 严格校验并返回 502 | 契约版本、Schema 注册 |
| 客户端提前断开 | 异步完成后访问失效对象 | 回包前检查连接状态，断开则丢弃 | 协作取消，节省无效推理 |
| 多条完成路径竞争 | 重复发送、对象重复释放 | 原子 one-shot 响应门 | 全链路取消状态机 |
| Worker 任务抛异常 | 线程死亡、容量永久下降 | 捕获任务异常，线程继续工作 | 异常指标、熔断坏任务 |
| 服务收到 SIGTERM | 丢任务或悬挂 | 信号转 EventLoop，停止后排空工作池 | readiness 摘流、最大排空期限 |
| 慢客户端只发半个请求 | 连接和缓冲区被长期占用 | 当前基础解析能等待半包 | 读超时、连接上限、缓冲上限 |
| 超大响应或恶意下游 | 内存膨胀 | Python 响应设置最大字节数 | 流式协议、指标和熔断 |
| 非法 NaN/Inf 或维度 | 推理异常、JSON 语义不稳定 | 边界层与模型层双重有限值校验 | 医学范围、枚举字典 |
| ORT 内部线程过多 | 工作池乘内部线程，CPU 过度订阅 | intra-op/inter-op 默认各 1 | 按机器压测调参 |
| 日志泄露患者特征 | 隐私与合规风险 | 不记录原始输入和完整预测响应 | 脱敏、审计、保留策略 |
| 文件描述符耗尽 | 无法接收连接/健康检查失败 | 当前未形成专门治理 | ulimit、连接上限、指标 |
| 重试风暴 | 故障期间流量倍增 | 服务端不自动盲目重试 | 指数退避+jitter+重试预算 |
| 健康检查被下游拖慢 | 实例被误杀，故障放大 | `/health` 不同步探测 Python、不跑推理 | readiness/liveness 分离 |

# A. 项目叙事、架构和所有权

## A1. 请介绍一下你的项目【P0】

**参考回答：**

这是一个面向医生和患者场景的 treeSem 智能服务项目。当前完成的是 C++ HTTP Backend 和
模型 Serving 主链：外部请求先进入基于 Kama/Muduo 二次开发的 HTTP 服务，网络线程负责
解析和路由，预测任务进入有界工作池；业务层通过统一模型接口调用本地 ONNX Runtime，
并由 C++ 完成标准化和决策树解释。Python Adapter 保留为黄金参考和异常兜底，还支持
shadow 模式比较新旧链路。

工程上我重点解决了四类问题：阻塞推理不能占用 EventLoop；请求洪峰要有明确过载边界；
研究模型到 Serving 需要稳定的模型、预处理、特征顺序和版本契约；C++ 与 Python 的结果
必须用全量参考集证明一致，而不是只跑一个样例。后续再在这个入口上增加会话、MySQL、
医疗权限、Agent、RAG/MCP 和 Skill。

**继续追问：** 为什么医疗场景需要 C++ Gateway？最困难的部分是什么？当前离生产还有多远？

## A2. 整体调用链是什么【P0】

**参考回答：**

客户端发送 JSON 预测请求；I/O 线程增量解析 HTTP 并完成输入边界校验；预测请求尝试进入
有界工作池，满了就立即返回 503。Worker 调用无 HTTP 依赖的业务服务，再由可替换的模型
接口选择 ONNX、远程 Python、fallback 或 shadow。ONNX 路径先把原始字段按 Bundle 中的
固定顺序标准化，运行确定性神经网络子图，然后用 C++ 决策树计算叶节点、重要特征和决策
路径。完成后只把一个轻量的响应构造动作投递回连接所属 EventLoop，再由网络线程发送。

## A3. 为什么要做四层分层【P0】

**参考回答：**

协议层只理解 HTTP 和 JSON；应用层只描述“执行一次预测”；模型抽象层定义类型化输入输出；
基础设施层才理解 libcurl、Python、Bundle 和 ONNX。这样 HTTP 错误、业务编排和模型实现
不会相互渗透，可以用假模型测 Controller、用假客户端测远程模型转换，也能在不改业务层
的情况下把 Python 主链替换成 ONNX。

分层不是为了目录好看，而是隔离变化：协议可能换，模型后端会灰度，业务规则也会增加，
它们不应该同时修改同一段代码。

## A4. 为什么 C++ 和 Python 都保留【P0】

**参考回答：**

Python 适合承接研究代码和快速验证，还是最容易与 PyTorch 原结果对照的黄金实现；C++ 本地
ONNX 减少一次进程间 HTTP 调用和 Python 运行时依赖，也能和现有 C++ 网关共享部署与线程
治理。两者不是重复劳动：Python 负责基准和兜底，C++ 负责默认 Serving，shadow 负责证明
切换没有改变语义。

## A5. 项目最难的工程问题是什么【P0】

**参考回答：**

第一是异步生命周期。请求对象、连接和响应对象属于 I/O 线程，而推理在 Worker 中完成，
如果跨线程保存栈指针就会悬空；如果断开、异常和正常完成都能回包，又会重复响应。项目把
请求数据复制到异步任务，Worker 只产生响应构造器，再回投到原 EventLoop，并通过原子门
保证最多完成一次。

第二是模型语义迁移。权重相同不代表 Serving 相同，特征顺序、Scaler、float 精度、树阈值
和输出解释都可能漂移，所以把这些共同放进有校验的 Bundle，并对全量参考集比较连续值和
离散路径。

## A6. 为什么不直接让 Python 提供整个服务【P1】

**参考回答：**

如果只是验证模型，Python 足够；但本项目还要承载连接管理、并发、会话、权限和后续业务
服务，C++ Gateway 能把网络和业务治理集中起来，并展示模型部署能力。代价是跨语言一致性、
依赖管理和 C++ 内存生命周期更复杂，所以必须保留 Python 黄金实现和自动化 parity test。

这不是声称 C++ 一定优于 Python，而是本项目的工程目标和已有 Kama/Muduo 基础使它合理。

## A7. 为什么不用成熟网关或现成推理服务器【P1】

**参考回答：**

生产系统通常优先考虑 Nginx、Envoy、Triton 或成熟业务框架。本项目的目标是亲自实现并理解
HTTP 异步边界、过载保护、模型契约和灰度验证，因此选择可控的二次开发范围。为了不陷入
重复造轮子，TLS、完整 HTTP/2、服务网格、动态模型注册等不作为当前重点。面试时我会明确

# B. HTTP/1.1、Router 与框架能力

## B1. 一个 HTTP 请求在你的框架中怎样被解析【P0】

**参考回答：**

TCP 提供字节流，因此解析器是跨多次读取保存状态的。先找请求行结尾，解析 method、path、
query 和 version；再逐行解析 Header；遇到空行后，根据 Content-Length 判断 body 是否完整。
数据不足不是错误，而是保留状态等待下一次可读事件。完整后才交给路由，避免业务层看到
半个请求。

## B2. TCP 半包和粘包在 HTTP 中怎么处理【P0】

**参考回答：**

一次 `read` 不对应一个 HTTP 请求。半包时请求行、Header 或 body 都可能只到一部分；粘包时
缓冲区可能同时含多个请求。解析必须基于 CRLF 和明确的消息长度消费缓冲区，而不是基于
一次读取大小。当前项目已正确等待 Content-Length body 的半包，但 pipelining 的循环消费
还不完整，因此不能声称完整处理多个连续请求，这是后续要修的边界。

## B3. Content-Length 和 chunked 有什么区别【P0】

**参考回答：**

Content-Length 预先给出 body 的字节数，解析器等到指定长度即可；chunked 把内容拆成十六进制
长度块，直到零长度块结束，适合发送前不知道总长度的响应。HTTP/1.1 对两者并存、重复或
非法长度有严格规则，因为处理不一致会产生请求走私风险。当前框架只支持 Content-Length，
不支持 chunked，生产化要严格实现 RFC 规则或交给成熟反向代理处理。

## B4. 为什么 POST 没有 Content-Length 时当前会拒绝【P1】

**参考回答：**

当前预测接口要求 JSON body，又不支持 chunked，所以必须有确定的 body 边界；缺失长度无法
判断请求何时结束，直接返回语法错误比猜测更安全。更完整的实现应结合方法语义、
Transfer-Encoding 和连接关闭规则，而不是简单认为所有 POST 都必须有 Content-Length。

## B5. HTTP keep-alive 是怎样判断的【P0】

**参考回答：**

HTTP/1.1 默认持久连接，显式 `Connection: close` 才关闭；HTTP/1.0 默认关闭，显式
`Keep-Alive` 才保留。响应必须有可判断的消息边界，否则同一连接上的下一条消息无法解析。
持久连接减少握手和连接建立成本，但会增加连接、文件描述符、空闲超时和慢客户端治理压力。

## B6. keep-alive 和 HTTP pipelining 是一回事吗【P0】

**参考回答：**

不是。keep-alive 只是多个请求复用一条 TCP 连接，客户端仍可等待上一响应后再发下一请求；
pipelining 允许不等待响应就连续发送多个请求，还要求服务端正确处理缓冲区中的多个消息和
响应顺序。当前支持基本 keep-alive，但不宣称完整 pipelining。

## B7. Router 是怎么设计的，为什么路由和业务要分离【P1】

**参考回答：**

Router 按 method 和 path 找静态或动态处理器，并在业务前后经过中间件。它只解决“请求交给
谁”，不负责预测本身。这样 404、方法、路径参数和中间件属于协议基础设施；业务服务可以
脱离网络单测。异步路由单独表达“处理器稍后完成”，避免用同步返回值假装异步。

## B8. 同步路由和异步路由有什么差别【P0】

**参考回答：**

同步路由必须在当前 I/O 回调内构造完成响应，适合健康检查等轻操作；异步路由复制请求所需
数据并立即返回，后续从其他线程提交一个响应构造动作。预测必须走异步路由，否则一次慢
推理会阻塞同一 EventLoop 上的其他连接。异步不是“开个线程”这么简单，还要解决连接归属、
对象生命周期和一次完成语义。

## B9. 为什么健康检查不也进入工作线程【P0】

**参考回答：**

健康检查只读取初始化后不变的元数据，成本很低，直接在 I/O 线程完成能在预测池拥塞时继续
反映进程存活。它不实时调用 Python，也不执行一次推理，否则依赖变慢会拖慢健康检查，
编排系统可能误判并重启实例，进一步放大故障。生产中还会分 liveness 和 readiness。

## B10. 400、404、500、502、503、504 在项目中如何区分【P0】

**参考回答：**

400 表示客户端 JSON、字段或数值非法；404 表示路由不存在；503 表示实例因队列满或停止而
暂时不能接单；502 表示作为网关调用 Python 时连接失败、5xx 或响应契约非法；504 表示下游
调用超时；500 表示本地 ONNX 推理或未分类内部错误。区分它们是为了让调用方知道是改请求、
稍后退避、检查下游，还是服务自身故障。

## B11. GET、POST、PUT、DELETE 的安全性和幂等性是什么【P1】

**参考回答：**

安全方法表示客户端不要求改变服务端状态，GET、HEAD、OPTIONS 属于安全方法；幂等表示同一
请求执行一次和多次的预期效果相同，PUT、DELETE 和安全方法按规范是幂等的，POST 默认不是。
当前预测业务本身是只读计算，相同输入不会写业务状态，但接口使用 POST 承载 JSON，通用
HTTP 客户端不会因此自动把它当作可重试方法。是否重试还必须结合服务语义和过载风险。

## B12. 为什么请求和响应都要限制大小【P0】

**参考回答：**

没有边界时，恶意或错误对端可以让服务不断缓存 body/response，造成内存耗尽。项目已经限制
Python 下游响应大小，但 HTTP 入口的请求行、Header 和 body 上限还没有完整补齐，这是明确
风险。生产化需要分层限制：单行、Header 总量、body、连接累计缓冲和并发连接数，并对超限
快速返回或断开。

## B13. 慢客户端只发送一部分 Header 会怎样【P1】

**参考回答：**

状态机会等待剩余字节，同时连接、缓冲和文件描述符继续被占用；大量这种连接就是 Slowloris
类问题。当前解析正确性不等于资源治理完整，生产化要加入 Header/body 读取 deadline、空闲
连接超时、单 IP/全局连接上限和缓冲高水位，最好由成熟反向代理先承担公网防护。

## B14. Cookie、Session、JWT 有什么区别，项目现在用了什么【P1】

**参考回答：**

Cookie 是浏览器保存并随请求携带的小段数据；Session 通常只把随机 ID 放在 Cookie，状态在
服务端；JWT 把签名声明放在 token 中，服务端可少查一次会话，但撤销、过期和权限变更更复杂。
原 Kama 框架包含内存 Session 组件，但当前 treeSem 主链还没有接入医疗认证。后续会结合
MySQL/RBAC、Secure/HttpOnly/SameSite Cookie、会话过期与审计实现，不能把原组件直接说成
完整安全方案。

## B15. CORS、TLS 和反向代理在这个项目中怎么理解【P1】

**参考回答：**

CORS 是浏览器的跨源访问策略，不是服务端身份认证；TLS 提供传输加密和服务身份验证；反向
代理可以终止 TLS、限制请求、做连接治理和负载均衡。原框架有 CORS/SSL 代码，但 treeSem
当前没有完成生产级验证。医疗服务更合理的落地是公网入口先由成熟代理处理 TLS 和基础防护，
C++ 服务仍校验身份与权限，不能把 CORS 当安全边界。

# C. Reactor、EventLoop 与网络并发模型

## C1. 什么是 Reactor，项目为什么使用它【P0】

**参考回答：**

Reactor 用一个事件分发循环等待多个文件描述符就绪，再调用对应回调处理 accept、read、write
和定时事件。它适合大量连接但每次网络处理较短的场景，避免 thread-per-connection 的大量
线程栈和上下文切换。项目底层使用 Muduo 的 Reactor；我主要保证预测这种阻塞工作不会进入
Reactor 线程。

## C2. epoll 相比 select/poll 的特点是什么【P0】

**参考回答：**

select 有 fd 数量限制且每次传入、扫描整个集合；poll 去掉固定上限但仍线性扫描；epoll 把
关注集合维护在内核，通过就绪列表返回事件，适合连接很多、活跃较少的场景。复杂度并不代表
所有场景都绝对更快，实际还受回调、系统调用和负载分布影响。

## C3. LT 和 ET 有什么区别【P0】

**参考回答：**

LT 只要 fd 仍可读/可写就会继续通知，编程更稳健；ET 只在状态从未就绪变为就绪时通知，通常
要求 non-blocking 并一直读写到 `EAGAIN`，否则可能遗漏后续处理机会。Muduo 封装了底层细节，
项目面试时重点说明自己理解语义，而不是未经核对声称修改了其 epoll 触发模式。

## C4. 为什么不能在 EventLoop 中执行模型推理【P0】

**参考回答：**

一个 EventLoop 同时服务多个连接。若回调同步等待 Python 或执行较慢推理，该线程上的其他
连接即使已经可读，也无法及时处理，健康检查和尾延迟都会恶化。把推理放到 Worker 后，
EventLoop 只做短小的解析、路由和发送；代价是需要处理跨线程回包和过载边界。

## C5. I/O 线程池和推理线程池为什么分开【P0】

**参考回答：**

I/O 工作以短回调为主，等待由 epoll 管理；推理工作消耗 CPU 或同步等待下游。混用会让慢
模型占满网络线程，也难以分别配置容量。分开后可以按连接量配置 I/O 线程，按 CPU、模型
延迟和下游容量配置推理线程，并用推理队列单独做 load shedding。

## C6. 为什么响应必须回到连接所属 EventLoop【P0】

**参考回答：**

网络连接和输出缓冲由其 EventLoop 管理，任意 Worker 直接操作会与 I/O 回调并发，破坏线程
亲和性并产生数据竞争。Worker 只返回不可依赖栈对象的响应构造动作，网络层把它排入原循环；
循环执行时再检查连接仍然有效并发送。

## C7. 客户端断开时，异步任务怎样处理【P0】

**参考回答：**

连接采用共享所有权保证回投闭包执行前对象本身不会悬空，但这不表示连接仍可用；I/O 线程
发送前检查连接状态，若已断开就丢弃结果。当前已经避免 use-after-free 和错误发送，但推理
仍可能做完，生产化可把客户端断开转为取消信号，前提是模型后端支持安全取消。

## C8. 为什么不能把栈上的响应指针传给 Worker【P0】

**参考回答：**

同步回调返回后栈对象已经销毁，Worker 稍后写入就是典型悬空指针。即使偶尔测试不崩溃也只是
未定义行为没有显现。项目跨线程传递值对象和拥有清晰生命周期的 callable，真正的响应对象
在 EventLoop 执行回投时才创建。

## C9. one loop per thread 的好处是什么【P1】

**参考回答：**

连接通常固定归属一个 I/O loop，同一连接的大多数状态只在该线程访问，减少锁和并发推理难度；
跨线程操作统一排队回 loop。缺点是某个回调过慢会影响该 loop 上的所有连接，负载也可能不均，
因此必须保持回调短小并合理分配连接。

## C10. Reactor 和 Proactor 的区别是什么【P1】

**参考回答：**

Reactor 通知“现在可以做 I/O”，应用再执行非阻塞读写；Proactor 通知“异步 I/O 已经完成”，
应用处理结果。Linux 常见 epoll 网络库通常采用 Reactor 语义；Windows IOCP 更接近 Proactor。
线程池里的业务任务异步完成，并不会把整个网络框架变成 Proactor。

## C11. 多个请求并发时如何避免响应串线【P0】

**参考回答：**

每个异步请求创建独立的 responder，闭包中绑定自己的连接、HTTP 版本和关闭策略；Worker 的
输入和输出也是请求私有。完成时投递回对应连接，而不是使用一个全局“当前响应”。测试中用
不同输入并发请求并核对各自输出，验证没有共享请求缓冲导致串数据。

## C12. 慢客户端读取响应会产生什么问题【P2】

**参考回答：**

内核发送缓冲写满后，数据会堆积在用户态输出缓冲；如果没有高水位和写超时，少量慢连接就能
占用大量内存。当前模型响应较小，尚未专门实现这一层治理。生产化应设置连接输出高水位、
写超时、最大响应和必要时断开慢客户端；大结果则考虑流式传输。

## C13. 同步/异步和阻塞/非阻塞有什么区别【P0】

**参考回答：**

同步/异步描述完成结果由谁推进和通知：同步调用者沿当前流程等待结果，异步是调用先返回，结果
稍后通过回调、Future 或事件通知。阻塞/非阻塞描述当前线程在操作未完成时是否睡眠等待。它们
不是同一维度：非阻塞 socket 配合 Reactor 是非阻塞 I/O；预测路由对 EventLoop 是异步的，但
Worker 内调用 libcurl 仍是同步阻塞的，因此才需要独立工作池和超时。

## C14. 进程和线程有什么区别，为什么 Python 用独立进程【P0】

**参考回答：**

进程有独立虚拟地址空间和故障边界，线程共享进程内存、文件描述符和大部分资源，通信便宜但
数据竞争风险更高。Python Adapter 独立进程可以隔离 Python/PyTorch 依赖和崩溃，并允许单独
部署；代价是 HTTP 序列化、网络开销和独立运维。C++ 内部 Worker 用线程共享只读 Session 和
Bundle，避免每份进程重复模型内存。

## C15. TCP 为什么需要三次握手，不是两次【P0】

**参考回答：**

双方需要确认彼此的发送与接收能力，并同步初始序列号。客户端 SYN，服务端 SYN+ACK，客户端
ACK；第三次让服务端确认自己的 SYN 已被客户端收到，也避免旧的失效连接请求让服务端单方面
进入已建立状态。SYN flood 针对的正是半连接资源，生产入口需依赖内核参数、SYN cookies 和
网关防护。

## C16. TCP 为什么通常是四次挥手【P0】

**参考回答：**

TCP 是全双工，收到对端 FIN 只表示对端不再发送，本端可能还有数据要发，所以 ACK 和本端 FIN
通常分开，形成四个报文；若恰好可同时关闭也可能合并。HTTP 的 `Connection: close` 决定应用
层完成后关闭，最终仍由 TCP 状态机完成两个方向的终止。

## C17. TIME_WAIT 为什么存在，哪一方进入【P0】

**参考回答：**

主动关闭方通常进入 TIME_WAIT，等待约 2MSL：一是确保最后 ACK 丢失时还能响应对端重传 FIN；
二是让旧连接的延迟报文从网络中消失，避免污染相同四元组的新连接。大量短连接会产生很多
TIME_WAIT，所以压测必须说明是否复用连接，服务端也不应为了消除它随意修改危险内核参数。

## C18. TCP keepalive 和 HTTP keep-alive 有什么区别【P0】

**参考回答：**

HTTP keep-alive 是应用层在一个 TCP 连接上复用多个请求；TCP keepalive 是连接长时间空闲后由
内核发送探测，判断对端是否已失联。它们的时间尺度、目的和配置都不同。应用仍需要请求 deadline
和空闲连接策略，不能把 TCP keepalive 当业务超时。

## C19. 非阻塞 socket 返回 EAGAIN 表示什么【P1】

**参考回答：**

表示当前没有更多数据可读或缓冲区暂时不能继续写，并非连接发生错误。Reactor 应停止本轮处理，
等待下一次可读/可写事件；ET 模式尤其要求一直处理到 EAGAIN。若把它当异常关闭，会误伤正常
连接；若阻塞等待，又会卡住 EventLoop。

## C20. listen backlog 是什么【P1】

**参考回答：**

它影响内核为监听 socket 保留的待处理连接队列，但实际行为还受系统上限、半连接队列和内核
实现影响。backlog 太小，突发建连可能被丢弃或延迟；调大也不能解决应用 accept/处理能力不足。
容量治理要同时看连接建立、fd、EventLoop 和业务队列。

## C21. Nagle 算法和粘包是什么关系【P1】

**参考回答：**

Nagle 会合并小写入以减少小包，可能增加交互延迟；粘包的根本原因是 TCP 是字节流、没有应用
消息边界，即使关闭 Nagle 也不能依赖一次 read 对应一次 write。HTTP 必须靠协议边界解析，
`TCP_NODELAY` 只是延迟/带宽权衡，不是拆包方案。

## C22. 惊群是什么，Muduo 线程模型如何减轻它【P2】

**参考回答：**

惊群是一个事件唤醒多个等待者，但最终只有少数能处理，造成无效调度。常见 Reactor 设计由一个
acceptor 接收连接，再把连接分配给 I/O loop，连接后续固定归属某个 loop，避免所有线程竞争
同一连接事件。具体 accept 策略由 Muduo 实现，我不会把底层机制包装成自己重写。

# D. 异步、线程池、生命周期和 C++ 并发

## D1. 有界工作池是怎样工作的【P0】

**参考回答：**

固定数量 Worker 从受互斥锁保护的任务队列取任务；队列为空时条件变量休眠，提交时唤醒。
队列容量固定，服务运行时满队列直接拒绝；停机后不再接单，已接收任务排空后 join。每个任务
外层捕获异常，避免一个坏任务永久杀死 Worker。

## D2. 为什么必须有界，不能用无界队列【P0】

**参考回答：**

当到达率持续大于处理率时，无界队列不会增加吞吐，只会增加内存、排队时间和已经失去价值的
请求，最后可能 OOM。有限队列把容量显式化，过载时快速返回 503，给上游退避机会，也保住
健康检查和已接请求。这是一种实例级 load shedding。

## D3. 队列容量和线程数怎么确定【P0】

**参考回答：**

不能凭感觉给固定值。线程数要看任务是 CPU 推理还是下游等待，以及 ORT 内部线程；队列容量
要结合峰值、可接受排队时间和下游容量。我的做法是分别压 1、2、4 个 Worker，观察 QPS、
p95/p99、CPU 和 RSS，在吞吐不再增长或尾延迟明显恶化前选择。生产中还会用 Little's Law
估算在途量，再通过压力和故障测试校准。

## D4. 条件变量为什么必须带谓词循环判断【P0】

**参考回答：**

条件变量允许虚假唤醒，而且唤醒到真正拿锁之间状态可能被其他线程改变，所以不能把“收到
通知”等同于“条件成立”。Worker 必须在锁内检查“队列非空或正在停止”，条件不满足继续等。
通知只是提示重新检查状态。

## D5. mutex 和 atomic 分别适合什么场景【P0】

**参考回答：**

atomic 适合一个简单状态或计数的无数据竞争更新，例如 one-shot 的完成权；队列入队/出队涉及
容器、容量和状态多个变量的一致性，需要 mutex 保护临界区。强行把复杂状态拆成多个 atomic
容易得到单字段原子、组合状态却不一致的程序。

## D6. 怎样保证一个异步请求最多响应一次【P0】

**参考回答：**

正常结果、模型异常和调度失败都可能试图完成请求。项目在最靠近传输的一层放置共享原子标志，
每条完成路径都用 compare-and-swap 竞争从“未完成”到“已完成”；只有获胜者真正回投响应。
这比要求所有上层“记得不要重复调用”更可靠，也适用于并发完成。

## D7. `shared_ptr` 是不是线程安全的【P0】

**参考回答：**

不同 `shared_ptr` 实例对同一控制块的引用计数更新是线程安全的，但它指向的业务对象并不会因此
自动线程安全；并发读写对象仍需同步。项目用共享所有权延长连接和 one-shot 状态的生命周期，
同时仍把连接操作约束在所属 EventLoop。

## D8. 为什么接口使用值和 variant 表达输入【P1】

**参考回答：**

三种输入——参考样本下标、标准化向量、原始字段——是互斥的代数类型，用 variant 可以让
编译器强制调用者明确处理每一种，而不是一个结构里放三个 optional 再依靠运行时组合校验。
跨线程传值也比借用请求对象内部指针更容易管理生命周期。代价是新增类型要更新 visitor。

## D9. C++ 中如何理解 RAII 在这个项目里的价值【P0】

**参考回答：**

资源与对象生命周期绑定，构造成功后资源可用，析构自动释放。线程在停机时 join，curl handle
和 Header 请求后释放，ONNX Session 随服务销毁，锁由守卫退出作用域释放。RAII 能让异常路径
和正常路径共享清理逻辑，减少“某个 return 忘记释放”。第三方 C API 仍要特别确认谁拥有内存。

## D10. 遇到过什么典型生命周期问题【P0】

**参考回答：**

一类是异步代码不能捕获短生命周期的请求/响应地址，因此改为复制必要数据并延迟创建响应。
另一类来自 ONNX Runtime C++ API：某些类型/形状信息是非拥有视图，不能让子视图超过拥有者
生命周期。解决方法是在拥有对象仍存活的同一作用域读取和复制 shape，而不是保存临时 view。
这类问题说明 RAII wrapper 也不代表所有返回对象都独立拥有资源。

## D11. 为什么执行未知代码时不应持有内部锁【P0】

**参考回答：**

未知任务或回调可能耗时、重入线程池、再次取锁或抛异常。持锁调用会扩大临界区，引发死锁和
队头阻塞。正确方式是在锁内只取出任务和更新状态，然后解锁再执行；回调和日志也尽量在锁外。

## D12. Worker 抛异常为什么不能让线程退出【P0】

**参考回答：**

如果未捕获异常越过线程入口会调用终止流程，或让有效 Worker 数悄悄下降；在固定容量系统中
会加重过载。任务边界统一 catch，记录安全错误并继续取下一任务；业务层仍应把预期错误转换为
类型化结果。不能用 catch-all 完全吞掉问题，生产中还要有异常计数和告警。

## D13. 优雅停机怎样设计【P0】

**参考回答：**

信号处理器本身不能做复杂、非异步信号安全操作，所以通过 self-pipe 把信号转成 EventLoop
事件；随后退出网络循环，不再接收新工作，推理调度器停止接单并排空已接任务，最后 join Worker
再销毁模型资源。生产环境还应先把 readiness 置为失败并等待负载均衡摘流，同时设置最大排空
时间，避免某个永久阻塞任务导致进程不能退出。

## D14. 当前有取消吗？超时后推理会立即停止吗【P1】

**参考回答：**

当前没有完整协作式取消。客户端断开后会丢弃结果，下游 HTTP 有超时，但已经进入本地 ONNX
的任务通常会执行完；排队阶段也没有端到端 deadline 淘汰。取消需要在排队、调用、回包各层
传播同一状态，并确认第三方推理是否支持安全终止，不能只把一个布尔值叫作完成取消。

## D15. 如何证明没有明显竞态【P1】

**参考回答：**

除了代码审查所有权和线程亲和性，还要用多请求并发核对响应、重复调用 responder 验证只发送
一次、提前断开验证不崩溃、任务抛异常验证 Worker 存活，并把并发测试连续运行多轮。进一步可
在支持环境下用 ThreadSanitizer，配合 AddressSanitizer/UBSan 检查数据竞争、越界和未定义行为。

# E. 超时、过载、fallback 与通用可靠性

## E1. 项目中有哪些超时【P0】

**参考回答：**

远程 Python 调用区分连接建立超时和整次请求超时。连接超时说明网络或服务不可达；总超时
限制 Worker 最长等待时间，映射为 504。当前缺少入口读取超时、队列等待 deadline、总请求
deadline 和响应写超时，因此我不会说已经有完整超时体系。

## E2. 为什么超时不能只设一个很大的值【P0】

**参考回答：**

超时过大时，故障已经发生但连接、线程、内存和下游槽位仍被占用，积累的在途请求会触发级联
故障；过小则正常长尾请求持续失败。应该基于延迟分布和业务预算，把总 deadline 分配给排队、
连接、执行和回包，并监控超时发生在哪一段。

## E3. 超时后是否应该自动重试【P0】

**参考回答：**

不能无条件重试。超时意味着结果未知，非幂等操作可能重复生效；即使预测是只读计算，故障时
重试也会放大负载。当前 C++ 远程调用不做盲目重试，fallback 也只做一次不同后端切换。生产中
若重试，要限制次数，使用指数退避和 jitter，设置重试预算，并只对明确的暂时性错误执行。

## E4. 大量请求同时涌入，系统会发生什么【P0】

**参考回答：**

先由网络线程解析；预测任务进入固定 Worker 和有界队列。容量以内正常排队，队列满后新请求
立即得到 503，不继续占用推理资源。这样牺牲少部分请求来保护进程、健康检查和已经接收的请求。
但 503 只是最后一道实例保护，公网还需要网关/IP/用户限流、全局容量规划和客户端退避。

## E5. 503 和限流 429 有什么区别【P1】

**参考回答：**

503 通常表示服务当前不可用或过载，与实例整体容量相关；429 表示调用方在某个配额或速率
规则下请求过多。当前有界队列不知道用户或租户，只能返回 503。后续有认证和 RBAC 后，可以
增加按患者、医生或租户的令牌桶并返回 429，同时保留 503 防止全局过载。

## E6. 限流、熔断、降级和负载丢弃分别解决什么【P0】

**参考回答：**

限流控制进入系统的速率；熔断在依赖持续失败时暂时停止调用，避免反复消耗资源；降级用更便宜
或较弱结果维持核心服务；load shedding 在过载时快速丢弃一部分工作。当前实现的是实例队列
load shedding、ONNX 到 Python 的 fallback，以及调试用 shadow；尚未实现完整令牌桶和熔断器。

## E7. fallback 的触发边界是什么【P0】

**参考回答：**

只在本地 ONNX 运行时异常、输出缺失、shape 不合法或出现非有限值等推理失败时触发一次远程
Python。用户输入非法不会 fallback；Bundle、checksum 或 ONNX 文件损坏会在启动时 fail fast；
因为这些不是换一个后端就应掩盖的问题。远程兜底成功时明确标记实际后端，失败则保留 502/504
语义。

## E8. 为什么 fallback 也可能放大故障【P0】

**参考回答：**

如果大量 ONNX 请求同时失败，全部转向平时负载很低的 Python，Python 可能瞬间过载；随后超时
和上游重试又会放大流量。因此 fallback 需要容量预留、并发上限、熔断、指标和演练。当前面试
项目实现了一次切换和有界总 Worker，但还没有独立 fallback 舱壁和熔断器。

## E9. shadow 和双写有什么区别，为什么不影响主结果【P0】

**参考回答：**

shadow 对同一输入执行新旧后端，对外只返回主后端结果，影子用于比较连续值和离散输出；影子
失败只告警，不能改变已经成功的主结果。它类似只读双跑，不涉及数据库双写一致性。当前实现
是 Worker 内顺序调用，因此会增加延迟和 Python 负载，只适合测试与小比例灰度。

## E10. 为什么 Bundle 损坏要启动失败，不运行时 fallback【P0】

**参考回答：**

Bundle 是部署配置和模型契约的一部分，checksum、维度、特征顺序或树拓扑不合法说明发布制品
本身不可相信。若悄悄 fallback，健康检查仍显示正常，错误版本可能长期不被发现。fail fast
让编排系统保留旧实例或回滚。临时运行故障才属于 fallback 的范围。

## E11. 502 和 504 为什么要区分【P0】

**参考回答：**

502 表示网关得到不可用或非法的下游结果，例如连接失败、5xx、空响应、非法 JSON；504 强调
等待下游超过 deadline。两者都不是用户参数错误，但运维定位和客户端退避策略不同。内部错误
文本不能把绝对路径、堆栈和患者数据返回给调用方。

## E12. 是否需要熔断器，如何设计【P1】

**参考回答：**

当 Python 连续失败时，继续每个请求都等到连接超时会占满 Worker，因此生产化值得加入按依赖
统计的熔断器：关闭态正常调用，错误率/连续失败超过阈值进入打开态快速失败，冷却后半开少量
探测。要避免仅凭一次失败打开，也要限制半开并发，并让健康、指标和人工开关可观察。当前尚未
实现，不能把 fallback 当熔断。

## E13. 怎样避免级联故障【P1】

**参考回答：**

核心是限制每层资源和无效工作：入口限流、有界队列、连接/线程/内存上限、明确 deadline、
下游并发舱壁、快速失败、有限重试和退避；健康检查不能依赖慢路径；压测必须覆盖超过容量后的
失败模式，而不只测峰值 QPS。降级和 fallback 也要有容量与开关，否则它们本身会成为级联路径。

## E14. 健康检查、就绪检查和业务探针怎么分【P1】

**参考回答：**

liveness 只回答进程/事件循环是否活着，失败可能触发重启；readiness 回答是否应该接新流量，
初始化失败或正在排空时应失败；业务探针可以异步执行少量真实请求并告警，但不应让每次健康
检查都打到下游。当前 `/health` 是轻量元数据检查，Bundle/ONNX 初始化失败则进程不启动；后续
仍应显式分离 liveness/readiness。

# F. Serving Bundle、ONNX 与模型服务

## F1. 为什么训练产物不能直接拿来 Serving【P0】

**参考回答：**

训练 checkpoint 往往依赖源码、Python 类、原始 CSV 和临时参数，预处理甚至在启动时重建，
很难跨语言复现。Serving 需要明确“输入字段及顺序、Scaler、确定性权重、树、版本、输出契约”。
项目把这些导出成自描述 Bundle，运行时不再读取原始 CSV，也不导入训练代码。

## F2. Serving Bundle 中有哪些内容【P0】

**参考回答：**

包含 manifest、49 维特征 Schema、每维 mean/scale、服务所需神经网络权重、跨语言决策树、
可选参考输入、黄金输出和后续 ONNX 文件。manifest 记录模型/数据集/Schema 版本、文件大小和
SHA-256，以及由原 checkpoint 摘要确定的模型版本。生产 Bundle 默认不带患者派生参考集。

## F3. 为什么要固定特征顺序【P0】

**参考回答：**

模型看到的是位置而不是字段名，两个 49 维数组即使长度相同，只要列交换就会得到完全错误但
形式合法的结果。原始输入采用字段名对象，加载后严格按 Schema 重排；Bundle 同时保存索引、
名称和预处理参数，C++ 和 Python 都以它为唯一真相。

## F4. 反归一化为什么要放入 Serving【P0】

**参考回答：**

决策树阈值和路径在标准化空间中计算，对医生不直观。利用同一 Bundle 的 mean/scale，把样本值
和阈值转换回原始数值，同时保留标准化值便于调试。公式是 `z=(x-mean)/scale`，反变换是
`x=z*scale+mean`。没有权威数据字典时单位保持 null，不能凭列名猜医学单位。

## F5. 为什么不在 Serving 时重新拟合 StandardScaler【P0】

**参考回答：**

重新拟合会依赖原始数据、划分随机种子和 sklearn 版本，既有数据泄露风险，也可能使线上预处理
漂移。导出阶段按可信训练划分一次性得到 mean/scale，写入 Bundle；Serving 只读加载。这样版本
可复现，也避免线上持有原始训练 CSV。

## F6. 如何得到确定性 model version【P1】

**参考回答：**

当前版本由数据集/seed 和可信 checkpoint 的 SHA-256 前缀组成，相同输入重复导出得到相同业务
文件与版本。版本随响应和 shadow 日志传播，便于定位哪份制品产生结果。更完整的制品体系还会
加入导出器版本、代码提交和签名，但不能把时间戳当内容版本。

## F7. checksum 能解决什么，不能解决什么【P0】

**参考回答：**

SHA-256 能发现文件损坏、传输错误和 manifest 与子文件错配；加载时先验证再初始化。若攻击者
能同时替换文件和 manifest，他也能重新计算哈希，所以 checksum 不提供来源认证。生产发布需要
签名制品、受控仓库和密钥验证。

## F8. ONNX 是什么，为什么选择它【P0】

**参考回答：**

ONNX 是跨框架计算图格式，opset 定义算子语义版本；ONNX Runtime 能在 C++ 中加载和优化图。
它让确定性 PyTorch 子图脱离 Python 运行时，适合当前 C++ Backend。代价是导出兼容、算子差异、
动态 shape、精度和依赖部署都要验证，所以 ONNX 不是“导出成功就完成”。

## F9. 为什么只导出一部分网络【P0】

**参考回答：**

在线预测只需要 encoder 均值、分类概率和 cluster logits。训练期 decoder、logvar、随机重参数化、
dropout 和 DeepSHAP buffer 不参与确定性结果，导出它们会扩大图和不确定性。Scaler 在 C++ 明确
实现，sklearn 树转成跨语言结构，便于精确复现叶节点和解释。

## F10. opset 是什么，为什么固定版本【P1】

**参考回答：**

opset 是 ONNX 算子集合的语义版本，同名算子在不同版本可能有属性或行为变化。项目固定 opset 17、
Python ONNX Runtime 和 C++ Runtime 版本，并在 manifest 记录 I/O 名称和 shape；这样能减少
“本机可跑、部署失败”。升级时应重新导出和跑全量 parity，而不是直接替换动态库。

## F11. C++ ONNX 推理流程是什么【P0】

**参考回答：**

启动时验证 Bundle 和 ONNX I/O，创建一次只读 Session。每个请求得到独立 49 维 float buffer，
创建输入 Tensor 并执行 Session；检查两个输出的数量、shape 和有限性，取分类/cluster argmax；
再用同一标准化输入遍历 C++ 决策树，组合概率、叶节点、重要特征和路径。不会每个请求重新加载
模型，也不共享请求级 Tensor buffer。

## F12. ONNX Session 能否多线程共享【P0】

**参考回答：**

ONNX Runtime 设计允许多个线程调用同一个 Session 的 Run，前提是调用方不共享可变输入输出
缓冲，并且自定义算子也满足线程安全。项目在启动时创建一个 Session，Worker 每次使用独立
vector/Tensor。这样避免每请求建 Session 的昂贵开销，也避免多份模型内存。

## F13. 为什么把 ORT intra-op 和 inter-op 线程都设为 1【P0】

**参考回答：**

外层已经有多个推理 Worker；如果每个 Run 再让 ORT 创建或占用多个内部线程，就会形成
Worker 数乘内部并行度，导致 CPU 过度订阅、上下文切换和尾延迟抖动。当前小模型以外层请求
并行为主，所以内部各 1。它是压测起点，不是普遍最优值，大模型需重新调参。

## F14. 为什么决策树不一起导入 ONNX【P1】

**参考回答：**

项目需要的不只是树的最终数值，还要稳定返回 leaf ID、重要特征和完整 decision path。把 sklearn
树转换成显式节点数组后，Python 和 C++ 都能按照同一 `value <= threshold` 规则遍历，解释语义
更可控，也减少 sklearn 运行依赖。代价是必须严格校验拓扑、索引和阈值精度。

## F15. 怎样验证 Python 与 C++ 一致【P0】

**参考回答：**

不是只比较最终 label。对全部 1489 个参考样本依次比较 PyTorch Bundle Reference、Python ORT、
C++ ORT 和 Python Adapter：概率/confidence 看最大绝对误差；label、cluster、tree leaf、完整
decision path 和重要特征顺序要求 100% 一致；Accuracy/F1 一致，AUC 差异限制在阈值内。
任何跨分类阈值或改变树路径的差异都算失败。

## F16. 当前一致性结果如何【P0】

**参考回答：**

在参考集上，Python ORT 相对 PyTorch 的概率最大绝对误差约 `1.19e-7`，C++ ORT 相对 Python
约 `1.79e-7`；label、cluster、叶节点、路径和重要特征顺序全部一致。这证明部署迁移保留了当前
模型语义，但不等于模型本身质量好。

## F17. 一致性和模型质量有什么区别【P0】

**参考回答：**

一致性问的是“新 Serving 是否复现旧模型”；质量问的是“旧模型对真实任务是否准确、泛化并
满足医疗要求”。当前 Accuracy 约 0.902，但 F1 约 0.039、AUC 约 0.432，提示类别不平衡、标签、
划分或 checkpoint 与论文结果需要单独审计。工程项目可以先完成，但简历不能用 Accuracy 单项
掩盖当前质量问题，更不能宣称临床可用。

## F18. 后续怎样单独修模型质量【P0】

**参考回答：**

单独建立模型质量阶段，不破坏 Serving 接口。先复现论文的数据清洗、标签定义、划分和 seed，
检查类别比例、数据泄露和 checkpoint 来源；再比较 confusion matrix、precision/recall/F1、ROC
和 PR-AUC，并做阈值与校准；必要时重新训练。新模型通过同一 Bundle 导出和 parity gate 后，
再用 shadow/灰度切换。这样“模型科学问题”和“Serving 工程问题”解耦。

## F19. raw、preprocessed 和 sample_index 三种输入为什么都保留【P1】

**参考回答：**

raw object 是正式业务接口，字段名可防止位置错乱；preprocessed vector 用于跨语言定位和测试；
sample_index 只为本地演示和全量回归，从可选参考数据读取。生产 Bundle 默认不含参考集，因此
sample_index 不可用。测试便利接口不能变成生产患者数据入口。

## F20. 为什么 bool 不能当普通数字接受【P1】

**参考回答：**

许多 JSON 库和语言中 bool 与整数容易发生隐式转换，但医疗特征契约要求明确 number；接受 true
作为 1 会掩盖调用方 Schema 错误。边界层拒绝 bool、string、null、NaN/Inf，并要求字段全集
完全匹配。医学合理范围和枚举含义则等权威字典后再加，不能凭想象拒绝有效病例。

## F21. 为什么 Python Adapter 仍有价值【P1】

**参考回答：**

它是最接近研究环境的独立黄金实现，可以验证 Bundle、生成黄金输出、调试 ONNX，并在本地
主链运行异常时兜底。若删除它，C++ 结果出错时缺少独立参照。生产中是否长期保留 fallback 要
看容量、运维成本和医疗风险，但参考实现本身仍值得保留。

## F22. 如何做模型灰度发布【P1】

**参考回答：**

先离线全量 parity，再在 shadow 模式小比例复制真实请求，只记录模型版本、差异类型和最大数值
差，不记录患者输入；观察错误、延迟和差异分布。通过后逐步将新版本设为主链，并保留快速回滚
到旧 Bundle/远程模式的开关。当前实现了后端模式和 shadow 基础，尚未实现流量百分比和自动
发布控制器。

# G. 测试、压测、可观测性与工程实践

## G1. 测试为什么要分层【P0】

**参考回答：**

解析、预处理和树适合快速单测；Controller 用假模型验证 HTTP 映射；远程模型用假 Adapter
验证 JSON 契约；集成测试验证 EventLoop/Worker/连接；真实 E2E 才加载 PPH Bundle。若所有
测试都依赖真实 Python 和网络，失败定位慢且难覆盖异常；若只有单测，又发现不了生命周期和
依赖集成问题。

## G2. 你做了哪些故障注入【P0】

**参考回答：**

覆盖 Adapter 宕机、慢响应、5xx、空响应、非法 JSON、字段缺失和超大响应；覆盖队列满、Worker
抛异常、重复完成、客户端提前断开；覆盖 manifest/checksum/tree/ONNX 损坏启动失败；shadow
人为差异和影子失败；并验证 Python 关闭时 ONNX 仍可返回。故障注入重点是证明错误被限制在
预期层，而不是只看返回了非 200。

## G3. 怎样证明 EventLoop 没被模型阻塞【P0】

**参考回答：**

让模型调用故意变慢，同时并发访问 `/health`；如果健康检查仍能快速返回，说明慢工作没有占用
对应 I/O loop。还要在高并发下观察 I/O loop 延迟和预测队列，单次“看起来没卡”不够。当前测试
已覆盖慢模型期间健康检查可响应。

## G4. 压测应该怎么设计【P0】

**参考回答：**

固定机器、版本、输入集和连接方式；先预热，再测足够请求；分别测顺序单请求和 1/2/4 Worker
并发；同时记录 QPS、p50/p95/p99、错误率、CPU、RSS 和 fallback 次数。还要压过容量观察是否
稳定 503，而不是只寻找最高 QPS。结果标明 localhost、新连接还是 keep-alive，不能横向比较
不同条件的数字。

## G5. 为什么不能只看平均延迟【P0】

**参考回答：**

平均值会掩盖少数很慢请求，而用户和超时通常由尾延迟决定。p50 表示典型体验，p95/p99 显示
排队、调度、缓存或下游抖动；还必须一起看错误率，因为快速失败可以让延迟很好看却没有完成
业务。

## G6. 当前性能结果怎样解释【P0】

**参考回答：**

同一机器、本地连接、100 次预热和 1000 次单样本请求下，Python Adapter 顺序 p50 约 2.70 ms、
QPS 约 370、RSS 约 220 MiB；C++ ONNX 顺序 p50 约 2.40 ms、QPS 约 416、RSS 约 28.8 MiB；
C++ ONNX 4 Worker QPS 约 979。它说明当前环境和脚本下 C++ 主链有趋势性优势，不代表公网
生产 SLA，也不能忽略测量噪声和连接建立成本。

## G7. QPS 为什么不随 Worker 线性增长【P1】

**参考回答：**

瓶颈可能转移到 CPU、EventLoop、JSON、连接建立、内存带宽或 ORT；线程增加还会产生调度和
缓存竞争。Amdahl 定律说明串行部分限制总加速比。应该结合 CPU 利用率、队列等待和 profiler
定位，而不是看到不线性就继续加线程。

## G8. 如何做容量规划【P1】

**参考回答：**

先通过真实输入和并发矩阵测单实例饱和点、可接受 p99 下的稳定 QPS 和过载失败模式；再结合峰值、
增长、冗余和单实例故障计算实例数，不能以理论最高 QPS 满配运行。不同请求成本不同时，仅按
QPS 也不够，还需在途量、CPU 时间或优先级等指标。

## G9. 应该监控哪些指标【P0】

**参考回答：**

至少包括请求量、状态码、端到端和分阶段延迟、Worker 活跃数、队列深度/拒绝次数、ONNX/remote/
fallback 数量、下游超时与非法响应、shadow mismatch、进程 CPU/RSS/fd、模型版本。医疗场景
日志只记录 request ID、版本和安全摘要，不记录原始 49 维特征或完整预测。

## G10. 日志、指标和 tracing 分别解决什么【P1】

**参考回答：**

日志适合离散事件和上下文，指标适合聚合趋势、告警和容量，trace 适合一次请求跨 C++、Python、
数据库和 Agent 的耗时链路。三者要通过 request/trace ID 关联，但患者身份和临床特征需最小化、
脱敏和控制保留周期。当前主要有安全日志，完整 metrics/tracing 是后续工程项。

## G11. 配置为什么启动时校验【P0】

**参考回答：**

端口、超时、线程数、队列容量、后端模式和 Bundle 路径若非法，运行到第一条请求才报错会形成
半可用实例。启动时解析一次、检查范围和组合依赖，失败就不监听。运行时配置需要更复杂的快照、
原子切换和回滚，当前没有为了“动态”而引入这类风险。

## G12. 怎样设计发布和回滚【P1】

**参考回答：**

代码、ONNX 和 Bundle 都应有不可变版本；启动先做 checksum/I/O/schema 校验；小流量 shadow/
灰度观察错误、延迟和语义差异；异常时切回旧镜像/旧 Bundle 或 remote 模式。数据库变更还要
向前向后兼容。当前已有确定性模型版本和后端开关，但自动编排、制品签名和百分比灰度尚未实现。

## G13. 如何定位线上延迟突然升高【P1】

**参考回答：**

先按 RED 方法看 rate、errors、duration，并判断是所有请求还是某后端/版本；再拆排队时间、ONNX
Run、Python HTTP 和回包；看队列深度、CPU、RSS、fd、fallback 和下游超时是否同步变化；最后
用 trace/profiler 定位。先确认时间线和最近变更，避免直接根据一个高 CPU 指标猜根因。

## G14. 什么是回归测试的“黄金用例”风险【P2】

**参考回答：**

少量黄金用例易读但覆盖不了阈值附近、异常值和所有树路径；全量参考集覆盖更强，但它仍可能与
真实分布不同，还涉及患者派生数据保护。项目同时保留精选输出和本地全量 1489 样本，生产包
默认删除参考集；模型质量另用独立、合规数据评估。

# H. 与项目强相关的 C++ 八股

## H1. `unique_ptr`、`shared_ptr`、`weak_ptr` 如何选择【P0】

**参考回答：**

默认用 `unique_ptr` 表达唯一所有权，例如组合根持有后端实现；只有多个异步对象确实需要共同
延长生命周期时用 `shared_ptr`；观察共享对象但不延长寿命、打破环时用 `weak_ptr`。智能指针
不是越多越安全，`shared_ptr` 会模糊销毁时机并有原子引用计数成本。

## H2. 左值、右值和移动语义在异步请求中有什么价值【P1】

**参考回答：**

请求 body、JSON 和向量可能较大，把已不再使用的值 move 进任务闭包能转移内部资源而非深拷贝。
但 move 后对象仍有效、值未指定，不能继续依赖原内容。生命周期正确性优先于少一次复制，跨线程
借用局部引用通常比合理复制更危险。

## H3. lambda 捕获最容易出什么问题【P0】

**参考回答：**

异步 lambda 延迟执行，按引用捕获局部变量或 `this` 时，对象可能已经销毁；大对象按值捕获又会
有复制成本。项目明确捕获拥有生命周期的连接共享引用、不可变值和 moved callable，不捕获栈上
响应地址。代码审查时要把 lambda 当一个可能很晚执行的对象分析。

## H4. 虚函数接口为什么适合模型后端【P1】

**参考回答：**

后端实现由运行配置选择，调用方只需要统一的同步预测契约，运行时多态能让 ONNX、远程、fallback
和 fake 共享接口。接口析构必须是 virtual。若类型在编译期固定且性能极敏感，可以考虑模板或
variant，但这里可替换性和测试价值高于一次虚调用成本。

## H5. `const` 成员函数是否意味着线程安全【P0】

**参考回答：**

不意味着。`const` 只限制通过该对象接口修改可见状态，内部可能有 mutable、全局状态、缓存或
第三方库共享状态。项目线程安全依赖更强的不变量：Bundle/树加载后只读，ORT 明确支持并发 Run，
每请求 buffer 私有；不能只看到 `const predict` 就下结论。

## H6. 编译期多态和运行时多态有什么区别【P1】

**参考回答：**

模板/概念在编译期生成具体调用，便于内联但增加编译和二进制复杂度；虚函数运行时通过 vtable
选择实现，有小的间接调用成本，但能在统一 ABI 下动态组合。模型调用本身远重于虚调用，所以
项目选择清晰的运行时接口。

## H7. 异常和错误码如何选择【P1】

**参考回答：**

构造/启动失败和穿过多层的异常路径适合类型化异常，边界统一映射；高频预期分支或无异常环境
可用 `expected`/错误码。项目把模型错误分为输入、超时、不可用、非法下游和本地推理失败，再由
HTTP 边界映射，避免各层重复拼错误 JSON。Worker 最外层仍 catch 未知异常作为隔离网。

## H8. 为什么错误信息要区分内部和外部【P0】

**参考回答：**

内部日志需要足够定位，外部响应只给稳定 code 和安全 message。直接返回 `what()` 可能泄露绝对
路径、依赖版本、模型结构甚至患者数据。当前响应集中构造，日志不打印原始输入和完整结果；
生产中再通过 request ID 关联受控内部日志。

## H9. 静态库、动态库和 ONNX Runtime 部署有什么关系【P1】

**参考回答：**

静态链接部署单一但体积大、许可证和符号处理更复杂；动态链接减少可执行体积并可共享库，但要
保证 `.so` 版本、搜索路径和 ABI。项目通过 CMake 显式指定 ONNX Runtime 根目录，启用时缺头文件
或库直接配置失败，不把第三方二进制提交仓库。部署还需固定来源和 SHA-256。

## H10. ABI 不兼容可能从哪里来【P2】

**参考回答：**

编译器/标准库版本、C++ ABI 开关、结构布局、异常和 RTTI、依赖动态库版本都可能导致运行时问题。
跨边界最好使用稳定 C API 或在同一工具链构建；ONNX Runtime 的 C++ API 本质上包装 C API，但
项目仍固定 Runtime 版本并在目标环境实际加载测试。

## H11. 内存泄漏、悬空指针和数据竞争分别是什么【P0】

**参考回答：**

泄漏是资源不再可达却未释放；悬空指针是仍引用已销毁对象，访问产生未定义行为；数据竞争是
至少两个线程无同步访问同一内存且至少一个写，也是未定义行为。RAII 主要防泄漏，所有权和
线程亲和防悬空，mutex/atomic/消息传递防数据竞争，三者不能互相替代。

## H12. false sharing 是什么，与项目有关吗【P2】

**参考回答：**

不同线程频繁写同一 cache line 上的不同变量，会导致缓存行在核间反复失效，逻辑上无共享也会
变慢。当前模型服务瓶颈尚未证明在共享计数器，因此没有提前做 cache-line padding。若指标表明
并发计数或队列热点，再用 profiler 和硬件计数器验证后优化。

## H13. 为什么开启 `-Wall -Wextra -Wpedantic` 还不够【P1】

**参考回答：**

编译告警能发现不少类型和可疑代码，但发现不了所有越界、use-after-free、数据竞争和协议逻辑
错误。还需要单元/E2E、ASan/UBSan/TSan、静态分析、fuzz parser 和真实压力测试。工具之间是
互补关系。

## H14. CMake 中可选 ONNX 构建为什么有价值【P1】

**参考回答：**

启用 ONNX 时严格要求依赖存在，保证最终演示主链不会悄悄变成 remote；关闭时仍能构建远程兼容
版本，方便没有 Runtime 的开发环境。功能开关必须反映到运行配置校验：一个未编译 ONNX 的
二进制收到 ONNX 模式配置应启动失败，而不是运行到请求时才失败。

## H15. `std::call_once` 适合解决什么【P1】

**参考回答：**

进程级第三方库初始化需要只执行一次，同时可能由多个对象/线程首次触发。`call_once` 配合
`once_flag` 能安全发布初始化结果。它不适合需要反复重载的模型，也不能代替对象自身的生命周期
管理；当前模型 Session 是组合根显式创建一次。

| “框架有 SSL 所以数据安全” | “原框架存在 SSL 组件，但 treeSem 尚未完成生产验证；正式入口应使用成熟 TLS 终止和应用层鉴权。” |
| “Accuracy 90% 很高” | “类别不平衡下 Accuracy 可能误导；当前 F1/AUC 明显异常，已划入独立模型质量审计。” |
