# treeSem 医疗智能服务项目面试问题库

这份文档用于 C++ 后端、模型部署和 Agent 方向的项目面试。题目按照面试官了解项目时的
自然追问顺序组织，而不是按照源码目录、类名或函数名组织。回答时讲清需求、方案、关键
不变量、权衡和验证，不背代码名称。

当前内容覆盖已经完成的 M0～M6：HTTP 服务、异步 C++ Backend、Serving Bundle、ONNX
Runtime、MySQL 业务层、医疗 Agent Core、身份认证、资源授权和安全审计。RAG/MCP、Skill
和完整 Agent 评测尚未完成，只在相关答案中作为后续演进方向出现。

## 一、怎么使用这份题库

- **P0 必会**：简历主动写出的能力，必须能回答主问题和至少两层追问。

- **P2 拓展**：二面、三面深入讨论时再准备，不应挤占 P0 的复习时间。

不建议逐题背全文。先掌握每题的第一句话和主链，再用自己的话补充细节。

### 3. 项目题回答公式

1. **场景**：为什么会出现这个问题，直接风险是什么。
2. **方案**：系统在哪一层处理，主流程是什么。
3. **关键不变量**：线程、生命周期、权限或数据一致性怎样保证。
4. **权衡**：为什么选择当前复杂度，没有选择什么方案。
5. **验证**：用什么测试、故障注入或数据证明它有效。

面试官问“你怎么实现异步预测”，不要从某个函数开始背。应先回答：模型调用会阻塞网络
线程，因此把它放进独立的有界工作池；完成后再回到连接所属事件循环发送，并用一次完成
机制处理断开、异常和正常返回之间的竞争。

### 4. 项目事实边界

- HTTP/TCP/EventLoop 底层来自 Kama/Muduo；本项目是在其上二次开发，不说成完全从零实现。
- 异步路由、有界任务调度、treeSem 业务分层、Bundle、ONNX、MySQL、Agent 和权限体系是
  本项目新增或系统性改造的部分。
- ONNX 一致性证明“部署迁移没有改变当前模型语义”，不等于证明模型医学质量优秀。
- 当前系统是面试项目和本地医疗辅助演示。安全问题应结合已实现机制回答，不主动展开法规
  认证、组织制度等与岗位项目追问关系不大的话题。
- 历史训练源码和产物仍保留旧名称；新服务、接口和文档统一使用 treeSem。

# A. 项目介绍、架构与技术选型

## A1. 请你用两分钟介绍一下项目【P0】

**参考回答：**

这是一个面向医生和患者的 treeSem 医疗辅助智能服务。外部入口是基于 Kama/Muduo 二次
开发的 C++ HTTP 服务，负责网络接入、会话、权限、业务持久化和模型调用；预测默认由
C++ ONNX Runtime 本地执行，Python 模型服务保留为黄金参考和异常兜底；Python Agent
通过受控 Tool 调用 C++ 内部业务 API，不能直接访问模型或数据库。

我重点解决了四类问题：第一，把阻塞推理、数据库和 Agent 调用从 EventLoop 隔离，避免
慢任务拖住连接；第二，用有界队列、超时、舱壁和一次响应语义处理高并发与故障；第三，
把研究模型整理为可校验的 Serving Bundle，并验证 Python 与 C++ 推理一致；第四，把预测、
历史、解释、医生反馈和 Agent 置于 Session、用户、患者和最小权限控制之下。项目通过单元、
进程级 E2E、真实 MySQL、1489 个样本一致性和并发故障测试验证。

**常见追问：** 为什么采用 C++ Gateway？最难的部分是什么？你具体新增了哪些能力？

## A2. 整体调用链是什么【P0】

**参考回答：**

普通预测链路是：HTTP 请求进入 EventLoop，完成基础解析和边界校验后投递预测工作池；业务
层调用统一模型接口，本地 ONNX 完成神经网络推理，C++ 完成预处理和决策树解释；随后在短
数据库事务中保存预测并更新当前 Session，最终把响应投递回原连接的 EventLoop。

Agent 链路是：客户端先进入 C++ Gateway，C++ 加载最近对话和当前预测，签发本次 Run 的
最小权限凭证，再调用 Python Agent；Agent 根据模型输出选择受控 Tool，Tool 回调 C++ 内部
API 获取预测、解释、历史或比较结果，最后答案回到 C++ 持久化并返回客户端。

## A3. 为什么要进行分层【P0】

**参考回答：**

HTTP 层只处理协议、路由和错误响应；应用层负责编排预测、历史和聊天；抽象层定义模型、
存储和 Agent 能力；基础设施层才依赖 ONNX、libcurl、Python 和 MySQL。分层的目的不是目录
整齐，而是隔离变化：模型后端可以灰度切换，存储可以在内存和 MySQL 间替换，业务测试也
不必启动真实网络和模型。

面试官继续追问时，可以说明 HTTP 层用假业务服务测试，模型转换用假 HTTP 下游测试，Agent
状态机用 Fake LLM 测试，从而证明分层确实带来了可测试性。

## A4. 为什么让 C++ 做 Gateway、Python 做 Agent【P0】

**参考回答：**

C++ 已经承载 HTTP 并发、ONNX、Session、MySQL 和权限，是统一业务事实入口；Python 更适合
快速适配大模型协议和 Agent 迭代。Python Agent 只负责任务规划和 Tool 编排，不能直接访问
数据库或模型，所以 LLM 无法绕开事务、权限和审计。

代价是多一次进程间 HTTP 和更长调用链，因此需要独立 Agent 工作池、总超时、响应大小限制
和结构化协议校验。这个拆分是工程边界选择，不是说所有 Agent 都必须采用 C++ 加 Python。

## A5. 为什么 C++ 和 Python 两条模型链都保留【P0】

**参考回答：**

Python 最接近原始研究实现，适合作为黄金参考；C++ ONNX 减少跨进程调用并便于和业务服务
统一部署。两条链并不是重复：Python 用来证明正确性和在本地推理异常时兜底，C++ 是默认
主链，shadow 模式用于灰度期间比较结果但不影响主响应。

## A6. 项目最难的部分是什么【P0】

**参考回答：**

工程上最难的是异步生命周期和跨服务资源闭环。请求在 I/O 线程进入、在 Worker 中执行，
期间客户端可能断开、任务可能超时或抛异常，最终仍必须保证对象不悬空、连接不跨线程误用、
一个请求最多响应一次。Agent 又会回调同一个 C++ 服务，如果调度池不隔离还可能形成环形
等待。

模型侧最难的是语义迁移。权重相同不代表结果相同，特征顺序、Scaler、浮点精度、树阈值
和解释路径都可能漂移，因此需要 Bundle 契约和全量参考集，而不是只比较几个样例。

## A7. 原框架和你自己的工作怎么区分【P0】

**参考回答：**

Kama/Muduo 提供底层 TCP、EventLoop 和基础 HTTP 结构。我在此基础上修正请求体解析，扩展
异步动态路由和跨线程安全回包，并增加有界调度、业务分层、模型 Serving、持久化、Agent、
认证授权和系统测试。面试中我会明确说“基于开源框架二次开发”，同时能说明自己修改的
调用链和验证证据。

## A8. 如何证明项目不是只跑通 Demo【P0】

**参考回答：**

验证分四层：单元测试验证解析、状态机、权限和算法；隔离测试用假模型、假 Agent 和假下游
验证边界；进程级 E2E 验证 HTTP、跨进程回调和数据库；真实数据验证比较 PyTorch、Python
ONNX、C++ ONNX 和 Adapter 在 1489 个样本上的概率、标签、cluster、树叶和路径。

此外实际测试了队列满、慢下游、客户端断开、MySQL 重启、Token 重放和并发刷新，而不是只
覆盖成功路径。

## A9. 如果继续完善，你会优先做什么【P1】

**参考回答：**

先做能直接影响正确性和面试完整度的内容：模型质量审计、RAG/MCP、Skill 和 Agent 评测；
再补全链路 tracing、指标、端到端 deadline、入口大小限制和限流熔断；最后根据压测决定
是否引入批处理、缓存或更复杂的部署方案。优先级来自故障风险和测量结果，不是为了堆技术。

# B. HTTP 框架、TCP 与 Reactor

## B1. 一个 HTTP 请求在你的服务中怎样被处理【P0】

**参考回答：**

TCP 字节先进入连接缓冲区，HTTP 解析器分阶段处理请求行、Header 和 body。完整请求交给
Router，根据 method 和静态或动态 path 找处理器，再经过中间件完成 CORS、认证等横切逻辑。
轻量接口可以同步返回；预测、数据库和 Agent 接口只在 I/O 线程完成解析和投递，真正工作
由对应工作池执行，最后回到连接所属 EventLoop 发送。

## B2. TCP 半包和粘包在 HTTP 中怎样处理【P0】

**参考回答：**

TCP 是有序字节流，不保留一次发送对应一次接收的边界。请求行、Header 或 body 都可能分多
次到达，也可能一次收到多条请求。解析器必须保留跨读取状态，根据 CRLF 和明确长度逐段消费；
数据不足只表示继续等待，不能把半包交给业务。

当前能正确等待 Content-Length body，但不把 HTTP pipelining 宣称为完整能力；多个连续请求
的循环消费仍是后续框架改进点。

## B3. Content-Length 和 chunked 有什么区别【P1】

**参考回答：**

Content-Length 预先给出 body 总字节数；chunked 由多个长度块组成，适合发送前不知道总长度
的场景。当前业务 JSON 只支持 Content-Length，不支持 chunked。生产实现还要严格处理重复、
冲突长度和 Transfer-Encoding 优先级，否则前后端解析不一致可能导致请求走私。

## B4. keep-alive 和 pipelining 是一回事吗【P1】

**参考回答：**

keep-alive 表示多次请求复用一条连接；pipelining 表示客户端不等前一个响应就连续发送多个
请求，还要求服务端正确消费多条消息并维护响应顺序。当前支持基本持久连接，但不宣称完整
pipelining。持久连接减少握手成本，也带来空闲连接、文件描述符和慢客户端治理问题。

## B5. Router 为什么要区分同步和异步处理器【P0】

**参考回答：**

健康检查读取少量内存状态，可以在当前 I/O 回调内完成；推理、SQL 和 Agent 调用可能阻塞，
必须明确表达“稍后响应”。异步处理器复制任务所需数据并立即释放当前调用栈，Worker 只生成
响应内容，网络发送仍回到 EventLoop。若把二者混在一个同步接口里，很容易保存栈指针或阻塞
网络线程。

## B6. 动态路由怎么匹配，为什么静态路由优先【P1】

**参考回答：**

动态模板把某一段声明为参数，例如预测 ID；匹配后把参数名和值放入当前请求副本。静态路由
优先，避免 `/health` 等固定路径被 `/:id` 误吞。注册阶段拒绝重复或非法模板，减少运行时
歧义。路由只决定请求交给谁，不承载业务权限和数据库查询。

## B7. 400、401、403、404、409、429、500、502、503、504 怎么区分【P0】

**参考回答：**

- 400：请求 JSON、字段、长度或数值非法。
- 401：没有身份或 Access Token 无效。
- 403：身份已知，但角色或 Capability 明确不允许该动作。
- 404：路由不存在，或资源不属于当前主体而需要隐藏存在性。
- 409：幂等键冲突、Run 仍在执行或 Session 并发冲突。
- 429：登录频率或账户锁定等调用方限速。
- 500：本地未分类错误或推理执行失败。
- 502：依赖服务连接失败或返回非法响应。
- 503：有界队列、连接池或数据库当前无容量。
- 504：下游调用超过超时。

稳定错误码用于程序判断，安全 message 用于用户理解，内部 SQL、路径和异常正文不能回传。

## B8. 如何防止超大请求和慢客户端拖垮服务【P1】

**参考回答：**

应对请求行、Header 总量、body、单连接缓冲和连接数分别设上限，并为 Header/body 读取设置
deadline。只限制业务 JSON 字段不够，因为攻击流量可能在解析完成前就耗尽内存和文件描述符。
当前项目已经限制消息和下游响应大小，但公网入口还应由成熟反向代理承担 TLS、连接上限和
Slowloris 防护，业务服务仍要保留自己的上限。

## B9. 什么是 Reactor，为什么适合这个项目【P0】

**参考回答：**

Reactor 用少量线程监听大量连接的就绪事件，再把读写事件分发给回调。它适合连接数多、单次
I/O 操作短的网络服务。前提是回调不能执行长时间推理或数据库等待，否则同一 EventLoop 上
其他连接也会被拖住，所以项目把阻塞工作移入独立 Worker Pool。

## B10. epoll 相比 select、poll 的特点是什么【P0】

**参考回答：**

select 有文件描述符数量和每次复制、扫描集合的问题；poll 去掉固定上限，但仍线性扫描；
epoll 在内核维护关注集合，只返回就绪事件，适合大量连接中少量活跃的场景。复杂度优势不
代表业务一定更快，回调耗时、锁竞争和下游才可能是真正瓶颈。

## B11. LT 和 ET 有什么区别【P1】

**参考回答：**

LT 在条件仍满足时会继续通知，编码更稳健；ET 主要在状态变化时通知，必须使用非阻塞 I/O
并持续读写到 EAGAIN，否则可能遗漏数据。ET 不天然比 LT 快，减少通知次数的收益要和更高的
实现复杂度、错误风险一起衡量。

## B12. 为什么响应必须回到原连接的 EventLoop【P0】

**参考回答：**

连接对象和 socket 写事件属于特定 EventLoop，Worker 直接写会破坏线程归属，并与关闭、缓冲
管理竞争。Worker 只产生轻量响应构造动作，再排入原 EventLoop；若连接已断开则丢弃结果，
不访问失效连接。

## B13. TCP 三次握手、四次挥手和 TIME_WAIT 与项目有什么关系【P1】

**参考回答：**

三次握手用于确认双方收发能力并同步序列号；TCP 是全双工，两个方向通常分别关闭，因此常见
四次挥手。主动关闭方进入 TIME_WAIT，用于吸收旧报文并保证最后 ACK 可重传。短连接过多会
增加握手开销和 TIME_WAIT，项目采用 HTTP keep-alive 复用连接，但仍需空闲超时和连接上限。

## B14. TCP keepalive 和 HTTP keep-alive 有什么区别【P1】

**参考回答：**

HTTP keep-alive 是应用层复用连接；TCP keepalive 是操作系统在连接长时间空闲时发送探测包，
用于发现失效对端。两者解决的问题和时间尺度不同，都不能替代业务请求超时。

# C. 异步、多线程、超时与过载

## C1. 为什么模型推理不能直接放在 EventLoop【P0】

**参考回答：**

EventLoop 串行处理一组连接的 I/O 事件，推理或同步 HTTP 一旦阻塞，该 Loop 上的读写、定时器
和健康请求都会排队。项目只在 EventLoop 解析、校验和投递，把阻塞调用放入固定 Worker，
因此慢推理不会直接冻结网络线程。

## C2. 为什么预测、数据库、Agent 和密码计算使用不同工作池【P0】

**参考回答：**

它们的耗时和故障模式不同。Agent 可能等待 LLM 数十秒，数据库可能等待连接，Argon2 是高
CPU/内存计算，预测则使用 ONNX。若共用一个池，某一依赖拥塞会占满所有线程，让本来健康的
接口也饥饿。独立有界池形成舱壁，代价是需要分别做容量规划和监控。

## C3. 为什么线程池和任务队列必须有界【P0】

**参考回答：**

固定线程只限制同时执行数，无界队列仍会在持续过载时无限积压，占用内存并让排队时间超过
客户端超时。客户端超时重试后又增加流量，形成重试风暴。有界队列把资源上限显式化，满时
快速返回 503，让上游退避，而不是把故障变成进程 OOM。

## C4. 大量请求突然涌入时，系统会发生什么【P0】

**参考回答：**

先消耗空闲 Worker，再进入有界队列；队列满后新请求快速失败。预测、查询和 Agent 相互隔离，
所以 Agent 洪峰不会直接占满预测 Worker；`/health` 仍由 EventLoop 快速返回。客户端应采用
指数退避、jitter 和重试预算，不能无条件立即重试。更完整方案还包括入口令牌桶、按用户
配额、熔断和优先级调度。

## C5. Worker 数和队列容量怎么确定【P1】

**参考回答：**

先区分 CPU 密集和 I/O 等待。ONNX 线程数通常接近可用 CPU，并限制 ORT 内部线程避免乘法
过度订阅；I/O 型池可略大，但受数据库连接数和下游容量约束。队列按照可接受排队时间、单
任务耗时和突发流量计算，再用 1/2/4 Worker 压测观察 QPS、p95/p99、CPU 和拒绝率。不是越大
越好，队列过大只会把快速失败变成慢失败。

## C6. 如何保证一个异步请求最多响应一次【P0】

**参考回答：**

正常完成、异常、超时和连接关闭可能竞争结束同一请求。项目用共享的原子完成门统一收口，
只有第一个状态转换成功的路径能提交响应；后续完成会被忽略。这个机制解决重复发送，不代替
连接有效性检查和对象生命周期管理。

## C7. 客户端提前断开怎么办【P0】

**参考回答：**

已开始的推理或 Agent Run 可能继续完成，但响应回投时先通过弱连接句柄确认连接仍存在，断开
则丢弃网络响应，不访问悬空对象。已经提交成功的数据库事务不会因为客户端断开而回滚。
当前没有让 ONNX 或所有下游协作取消，后续可传播 cancellation token 来节省无效计算。

## C8. 为什么不能把栈上的请求或响应指针交给 Worker【P0】

**参考回答：**

异步任务执行时原网络回调早已返回，栈对象生命周期结束，继续访问会产生悬空指针。项目只
复制任务真正需要的数据；Worker 返回拥有自己数据的响应构造器，最终在 EventLoop 的有效
响应对象上执行。面试时要把“数据所有权”和“执行线程”同时讲清。

## C9. 项目里有哪些超时，为什么还需要总 deadline【P0】

**参考回答：**

有连接超时、下游单请求超时、数据库连接池获取超时、Agent 总执行超时和短期 Token 过期。
单跳超时只限制某一步；一个 Agent Run 可能依次经历排队、LLM、多个 Tool 和重试，如果没有
总 deadline，各步骤相加仍会产生很长尾延迟。总 deadline 应向下游传播剩余预算，而不是每一
跳重新获得完整时间。

## C10. 哪些请求可以重试，哪些不能【P0】

**参考回答：**

只读 GET 在连接中断且总预算允许时可以有限重试；创建预测等有副作用操作不自动重试，除非
有明确幂等键和服务端去重。LLM 的连接失败、429 或 5xx 最多重试一次。重试必须同时考虑错误
类型、操作幂等性、退避、jitter 和总预算，不能只因为“超时”就统一重试。

## C11. 限流、熔断、降级、舱壁分别解决什么【P1】

**参考回答：**

限流控制进入系统的速率；熔断在依赖持续失败时暂时停止调用；降级返回较弱但可接受的能力；
舱壁隔离线程、连接或队列，限制一个故障的传播范围。当前已经实现有界队列、独立工作池和
ONNX 到 Python fallback；完整令牌桶、动态熔断和租户配额仍可后续增加。

## C12. fallback 为什么可能放大故障【P1】

**参考回答：**

当主链大面积失败时，所有流量会同时转向备用链。如果 Python 只按平时小流量配置，会被瞬间
压垮并进一步占用 Agent 或网络资源。因此 fallback 只对本地运行异常触发一次，非法用户输入
和损坏 Bundle 不触发；生产还要给备用链预留容量、限流和熔断。

## C13. 怎样避免 Python Agent 回调 C++ 时产生死锁【P0】

**参考回答：**

C++ 等待 Agent 的线程与处理 Agent Tool 回调的预测池、数据库池分开，EventLoop 也不等待
这些依赖。这样 Agent Worker 可以阻塞等待 Python，而 Python 回调仍有其他 Worker 可执行。
若共用一个很小的池，所有线程都可能在等自己产生的新任务，形成线程饥饿死锁。

## C14. 优雅停机怎么做【P1】

**参考回答：**

先停止接收新任务并让 readiness 失效，再停止各工作池接单，等待已接任务完成或达到排空期限，
最后关闭 HTTP 和依赖对象。销毁顺序必须保证异步任务引用的模型、存储和客户端仍然存活。
如果直接释放对象或使用 detached 线程，停机时很容易出现 use-after-free。

## C15. 如何降低死锁和数据竞争风险【P1】

**参考回答：**

缩小共享可变状态，让请求级输入、Tensor 和 Tool Context 私有；只读 Bundle 和 Session 可并发
共享；锁只保护必要容器，不在持锁时执行 SQL、网络调用或用户代码；多个锁固定顺序；连接
和文件等资源用 RAII。线程测试连续运行多轮并配合 sanitizers，但测试通过不能证明不存在
所有竞态。

# D. Serving Bundle、ONNX 与模型部署

## D1. 为什么训练产物不能直接拿来上线【P0】

**参考回答：**

训练产物往往依赖源码、原始 CSV、运行时重新划分数据和动态重建 Scaler，这会让同一权重在
不同环境得到不同输入语义。Serving Bundle 把推理所需权重、特征顺序、预处理参数、决策树、
模型版本和 checksum 固化，使部署可以独立启动、验证和回滚。

## D2. Bundle 中保存哪些内容，为什么【P0】

**参考回答：**

包含 manifest、49 个字段的 Schema、Scaler mean/scale、必要神经网络权重、跨语言决策树、
黄金输出和可选参考输入。manifest 记录文件名、大小、SHA-256、模型版本和维度。它不保存
训练代码、decoder 或随机采样路径，因为 Serving 只需要确定性预测子图。

## D3. 标准化和反标准化如何保证一致【P0】

**参考回答：**

Scaler 只在 Bundle 导出时根据可信训练划分拟合，Serving 不再读取原 CSV。原始输入按照固定
字段顺序计算 `(x-mean)/scale`；解释中的标准化阈值和值再用 `z*scale+mean` 转回原始尺度。
通过原始到标准化、再反变换的误差测试验证。单位没有权威数据字典时保持未知，不猜测。

## D4. 为什么 ONNX 只导出确定性网络子图【P0】

**参考回答：**

线上预测只使用编码器均值、分类头和 cluster head，不需要 VAE 随机采样、decoder、dropout
和训练期缓冲。裁剪后图更小、输出契约更清楚，也避免随机路径造成不一致。树解释保留为独立
确定性阶段。

## D5. 为什么决策树由 C++ 原生执行【P1】

**参考回答：**

神经网络适合 ONNX Runtime；sklearn 树还要暴露叶节点、重要特征和完整路径。把树转为简单
跨语言数组后，C++ 能按标准化输入逐节点比较，同时计算原始阈值。这样解释语义清楚，也能
逐项与 sklearn 的叶节点和路径做 100% 对比。

## D6. ONNX Session 如何支持多线程【P1】

**参考回答：**

Session 在启动时创建一次并作为只读推理对象共享，每个请求单独创建输入 Tensor、输出和
临时缓冲，不共享请求级内存。多个 Worker 可以并发调用。ORT 内部 intra-op 和 inter-op 默认
各设 1，避免“业务 Worker 数乘 ORT 内部线程数”导致 CPU 过度订阅，再通过压测调参。

## D7. 如何验证 Python 与 C++ 结果一致【P0】

**参考回答：**

在全部 1489 个参考样本上同时比较 PyTorch 黄金实现、Python ONNX Runtime、C++ ONNX Runtime
和 Python Adapter。连续值检查最大绝对误差；label、cluster、树叶、决策路径和重要特征顺序
要求完全一致。不能只看平均误差，因为少量跨过分类阈值的样本也会改变业务结果。

## D8. 部署一致性和模型质量有什么区别【P0】

**参考回答：**

部署一致性回答“C++/ONNX 是否复现当前 Python 模型”；模型质量回答“当前模型对医学任务是否
有效”。前者看数值误差、label 和路径一致；后者看数据划分、类别不平衡、F1/AUC、阈值、
校准和外部验证。当前 Serving 链可继续使用，模型质量可以单独重新审计和更换 Bundle。

## D9. remote、onnx、fallback 和 shadow 四种模式有什么用【P0】

**参考回答：**

remote 只调用 Python，适合兼容和调试；onnx 严格走本地主链；fallback 先走 ONNX，发生运行
异常时调用 Python；shadow 同时调用两边，对外返回 ONNX，只记录安全的差异摘要。shadow
用于灰度验证，fallback 用于可用性，两者目标不同。

## D10. 模型版本、checksum 和回滚怎么设计【P1】

**参考回答：**

模型版本由数据集、seed 和可信 artifact 哈希确定，Bundle 每个业务文件都有 checksum，服务
启动时 fail fast。发布时新旧 Bundle 并存，先做离线 parity，再用 shadow 采样，最后切主链；
异常时通过配置回到旧 Bundle 或 remote。哈希能发现损坏和错配，防恶意替换还需要签名和
可信发布链。

## D11. 后续怎样修正模型质量而不推翻工程架构【P0】

**参考回答：**

先复核论文的数据清洗、划分、标签、随机种子和指标口径，再处理类别不平衡、阈值和概率
校准；训练出新模型后导出新版本 Bundle，重复 parity、回归和 shadow。业务层只依赖稳定模型
接口，因此模型质量迭代不需要修改 HTTP、Session、Agent 或数据库主架构。

# E. MySQL、Session 与业务一致性

## E1. 为什么要保存预测快照，而不是查询时重新推理【P0】

**参考回答：**

查询时重新推理会受到模型版本、预处理和解释算法变化影响，历史结果不再可复现。项目把完整
结构化预测和解释快照与 model version 一起保存，查询、历史和比较都读取当时事实，不重新
调用模型。

## E2. 为什么推理完成后才开启数据库事务【P0】

**参考回答：**

推理远慢于数据库写入，如果先开启事务并锁 Session，长时间占锁会降低并发并增加死锁概率。
项目先完成推理，再开启短事务，锁定 Session、检查状态、插入 Prediction、更新当前预测和
过期时间后提交。插入和指针更新要么都成功，要么都回滚。

## E3. 两个并发预测如何更新同一 Session【P0】

**参考回答：**

提交阶段对 Session 行加锁，串行完成插入和 current prediction 更新，并递增版本。最终指向
最后成功提交的预测，而不是最先开始推理的请求。推理期间不持有数据库锁，所以慢模型不会
阻塞同一 Session 的其他查询。

## E4. 为什么 MySQL 连接池必须有界并有 acquire timeout【P0】

**参考回答：**

数据库连接是有限资源，无界建连会在故障时进一步压垮 MySQL；无限等待连接则占满 Worker。
固定连接数限定数据库并发，获取超时后返回 503。每条连接同一时刻只属于一个线程，Lease
析构时回滚未完成事务、恢复 autocommit，再归还或淘汰坏连接。

## E5. 为什么选择 READ COMMITTED【P1】

**参考回答：**

业务主要依靠显式行锁和唯一约束保证写一致性，不需要 REPEATABLE READ 的快照语义；READ
COMMITTED 能减少不必要的版本保持和部分间隙锁影响。隔离级别不是万能开关，关键仍是事务
边界、访问顺序、唯一约束和冲突处理。

## E6. Session、Cookie 和登录身份是什么关系【P0】

**参考回答：**

Session 保存会话上下文和当前预测，Cookie 只是浏览器传递 Session ID 的载体，都不能单独
证明用户身份。认证后，Access Token 表示 actor，Session 进一步绑定 owner 和 subject：患者
操作自己时两者相同，医生为患者操作时 owner 是医生、subject 是患者。

## E7. 为什么历史查询使用 keyset pagination【P1】

**参考回答：**

大 offset 会扫描并丢弃前面的行，并发插入时还可能出现重复或遗漏。项目按创建时间和唯一 ID
倒序分页，cursor 记录上一页最后一个复合键，下一页查询小于该键的记录。唯一 ID 用于时间
相同情况下稳定排序，cursor 对客户端保持 opaque。

## E8. 幂等键是怎么做的【P0】

**参考回答：**

同一业务上下文和幂等键建立唯一约束，同时保存规范化 payload 的 SHA-256。相同 key、相同
payload 返回原结果；相同 key、不同 payload 返回 409。Agent Run 正在执行时也返回明确冲突，
失败 Run 不伪造成功结果。幂等的核心是识别同一次业务意图，不是简单吞掉重复请求。

## E9. MySQL 宕机时系统怎样表现和恢复【P1】

**参考回答：**

`/health` 仍快速表示进程和模型存活；`/ready` 和依赖数据库的接口返回 503。坏连接归还时被
销毁，后续请求在池容量允许时补建连接，不在单个 Worker 内无限重试。MySQL 恢复后新请求
可以继续，持久化历史仍存在。

## E10. 为什么当前不急着加入 Redis【P1】

**参考回答：**

MySQL 已满足当前容量，先把事务真相源和权限语义做清楚。增加 Session cache 会引入缓存失效、
双写和过期一致性，当前没有压测证据证明值得。若将来 Session 读取成为热点，可使用
cache-aside，但当前预测指针更新仍以数据库事务为准。

# F. M5 医疗 Agent Core

## F1. 为什么这个项目需要 Agent，而不只是聊天接口【P0】

**参考回答：**

普通聊天接口只让 LLM 生成文本，无法可靠获取当前患者的预测、解释和历史。Agent Loop 让
模型在受控协议中选择 Tool，获得业务事实后再回答，从而支持“预测样本、解释刚才结果、查看
历史、比较两次预测”等多步任务。LLM 负责理解和表达，C++ 服务仍负责事实、权限和计算。

## F2. Agent Loop 的主流程是什么【P0】

**参考回答：**

每次 Run 组装系统边界、最近 12 条消息、当前预测摘要和用户新消息；LLM 返回 final answer
或结构化 Tool Call；Registry 校验参数并执行 Tool，把受限结果注回临时上下文；循环直到得到
最终回答或触发保护条件。Run 是短生命周期状态机，不把模型自由文本当成完成协议。

## F3. Agent 怎么判断任务完成，怎么防止死循环【P0】

**参考回答：**

正常终止是 LLM 返回合法 final answer。保护性终止包括最多 5 个 step、8 次 Tool、25 秒总
deadline、连续两次完全相同 Tool Call，以及上游取消。step 限循环，Tool 次数限单轮调用
膨胀，deadline 限整体资源消耗，重复检测处理模型卡住的常见模式。

## F4. Tool 系统是怎么设计的【P0】

**参考回答：**

Tool Registry 是名称白名单、Schema 校验和错误边界。每个 Tool 有独立输入输出 Schema，只
能执行预测、查询预测、获取解释、查看历史和比较结果。Session、actor 和 subject 不由 LLM
提供，而由 Run Context 注入，避免模型通过参数切换到其他患者。

## F5. 为什么概率差、路径变化等不让 LLM 自己算【P1】

**参考回答：**

这些是确定性业务事实，交给 C++ 比较服务能保证精度、字段语义和可测试性。LLM 只解释 Tool
结果，不能成为概率、标签、路径和历史的事实源，否则同一输入可能产生不同计算，也无法稳定
回归和审计。

## F6. Tool 调用失败时怎么处理【P1】

**参考回答：**

未知 Tool、参数错误和业务错误被转换为有限的结构化 Tool Error 注回 LLM，允许模型修正；
不会把异常栈、原始下游正文或患者数据交给模型。相同错误重复、超出调用预算、下游持续不可
用或总 deadline 到达时终止 Run，并返回稳定错误。

## F7. Agent 中哪些调用可以重试【P0】

**参考回答：**

查询类 GET 在连接中断时最多重试一次；创建预测是有副作用的 POST，不自动重试。LLM 遇到
连接失败、429 或 5xx，在总预算内最多重试一次。客户端重放 Chat 由幂等键处理，而不是让
Agent 猜测前一次是否执行成功。

## F8. 如何降低 Agent 幻觉【P0】

**参考回答：**

目标不是宣称消灭幻觉，而是缩小事实生成面。提示词规定预测事实只能来自 Tool；Tool 失败时
不得猜测；最终回答引用的 prediction ID 必须来自本轮成功 Tool Result；没有 Tool 的回答只能
是使用说明或一般说明。更完整的回答内容安全性仍需要离线集和人工复核。

## F9. 为什么只取最近 12 条上下文【P1】

**参考回答：**

固定窗口限制 token、延迟和成本，也避免历史无限增长。当前预测摘要以结构化字段单独提供，
不要求 LLM 从很长对话中寻找。后续若加入摘要和长期记忆，需要评估信息遗漏、错误记忆和
权限隔离，而不是简单扩大窗口。

## F10. Agent 保存哪些内容，为什么不保存完整中间轨迹【P1】

**参考回答：**

保存用户消息、助手最终回答、Run 状态，以及 Tool 名称、成功状态、耗时和引用 ID 的摘要；
不保存思维链、完整 Tool 参数、完整 Tool Result 和临床特征。中间推理不是业务事实，保存会
扩大隐私、提示词泄露和攻击面；当前摘要已足够做历史查询和基础可靠性分析。

## F11. Agent Run 的持久化和幂等怎么保证【P1】

**参考回答：**

用户消息与 Run 创建在一个短事务，助手消息与 Run 完成在另一个短事务。相同 Session 和
幂等键重放时，payload 相同返回原结果，不同返回冲突；运行中的 Run 不重复执行；失败 Run
保留失败状态但不写伪造助手消息。客户端要重试失败任务时使用新 key。

## F12. 为什么没有直接使用 LangChain 或 LangGraph【P1】

**参考回答：**

当前只有短循环、五个 Tool 和清晰的预算，直接实现更容易展示协议、终止条件、重试和状态
边界，也减少框架隐式行为。若未来出现复杂有向图、人工中断、长任务恢复和大量集成，再评估
成熟框架。当前选择只适合这个规模，不把它说成普遍更优。

## F13. MCP 和 Skill 为什么没有在 M5 一起做【P1】

**参考回答：**

当前五个 Tool 都属于同一业务域，直接调用受控内部 API 更简单。MCP 更适合把独立医疗知识
服务作为标准外部工具接入；Skill 用于沉淀可复用的任务流程和提示资产。先把内部 Tool 强行
包装为 MCP 会增加协议层但不提升能力，因此分别放在后续 RAG/MCP 和 Skill 模块。

## F14. 如何评价 Agent 是否真的有效【P0】

**参考回答：**

确定性测试先验证 Tool 选择流程、参数校验、终止条件、重试和错误语义；真实 Agent 质量应看
任务完成率、Tool 选择正确率、参数正确率、grounding 引用率、拒答安全性、平均步数、p95
延迟、成本和人工医生复核。不能只挑几条看起来流畅的回答作为证据。

# G. M6 身份、权限与安全

## G1. 匿名 Session 和认证用户有什么区别【P1】

**参考回答：**

匿名 Session 只表示一次业务上下文，不能证明用户是谁；认证用户由密码登录和 Access Token
确定。M6 把 Session 绑定 actor/subject，并让预测、聊天和历史记录保存主体归属。开发模式可
保留匿名演示，正式模式的公开业务 API 必须认证。

## G2. 为什么 Access Token 用 JWT，Refresh Token 用随机不透明值【P0】

**参考回答：**

短期 Access JWT 适合在请求入口快速验证 issuer、audience、subject、role 和过期时间；长期
Refresh Token 需要撤销、轮换和重用检测，因此使用 256 bit 随机值，并在数据库只保存 SHA-256。
两种 Token 生命周期和安全目标不同，不应混成一种。

## G3. Refresh Token Rotation 和重用检测怎么做【P0】

**参考回答：**

刷新事务锁定旧记录，只有未消费、未撤销、未过期的 Token 能生成 replacement；并发刷新只有
一个成功。旧 Token 再次出现可能表示被窃取，系统撤销整个 Token Family，包括已经生成的
最新 Token，要求重新登录。Logout 同样撤销 Family 并清理 Cookie。

## G4. 为什么密码选择 Argon2id【P0】

**参考回答：**

Argon2id 是内存困难型密码哈希，增加 GPU/ASIC 批量破解成本。项目使用随机盐、64 MiB 内存、
3 次迭代和单并行度，并把计算放到独立有界 Auth Worker，避免阻塞 EventLoop。参数需要根据
目标机器延迟和并发压测，不是盲目调得越大越好。

## G5. RBAC 为什么不能只检查角色【P0】

**参考回答：**

角色只能说明 Doctor 有访问患者的能力，还必须验证该医生和目标患者存在 active assignment，
资源 subject 与患者一致，Session 属于当前 actor/subject。只检查“是不是 Doctor”会导致典型
IDOR 横向越权。授权必须在服务端基于资源事实判断，不能相信请求体中的 role 或 patient ID。

## G6. Patient、Doctor、Admin 的边界是什么【P1】

**参考回答：**

Patient 只能操作自己的预测、历史和聊天；Doctor 只能操作已分配患者，并能提交服务端标记的
实名反馈；Admin 创建医生、管理分配和查看审计元数据，但默认不能读取临床内容。Admin 不等于
超级医疗用户，这是最小权限和职责分离。

## G7. 为什么越权访问资源时常返回 404，而不是 403【P1】

**参考回答：**

如果“存在但不属于你”返回 403，而不存在返回 404，攻击者就能枚举有效资源 ID。因此资源
不存在和资源不可见统一返回 404；角色本身不允许某类操作，例如 Patient 访问 Admin API，
可以明确返回 403。

## G8. Capability Token 解决什么问题【P0】

**参考回答：**

它是 C++ 为单次 Agent Run 签发的短期最小权限委托，绑定 actor、role、session、subject、
run ID、允许的 Tool 和两分钟过期时间。Python 不能自己选择患者，也不能用它访问 Admin API
或未授权 Tool。C++ 还检查 Run 仍在执行、Session 一致和医生分配仍有效。

## G9. 为什么还需要 Agent service secret【P1】

**参考回答：**

service secret 证明“发起 Agent Run 的是 C++ Gateway”；Capability 证明“Python 在这次 Run
中能代表谁调用哪些 Tool”。一个是服务身份认证，一个是请求级授权，作用不同，并且与用户
Access JWT 使用不同 secret 和 audience，避免不同 Token 被混用。

## G10. 安全审计记录什么，为什么要最小化【P1】

**参考回答：**

审计只记录谁、何时、对哪个资源 ID 执行什么动作、允许还是拒绝以及原因码；不复制临床特征、
预测 JSON、聊天正文、邮箱、密码或 Token。这样能够追责和排查越权，又不会把审计库变成一份
新的敏感业务数据副本。

敏感写操作和临床访问需要先确保审计可持久化；审计不可用时返回 503，而不是业务成功但留下
不可追踪窗口。生产上应为审计存储单独做容量、告警和高可用。

## G11. CORS、CSRF、Cookie 和 Authorization Header 是什么关系【P1】

**参考回答：**

CORS 约束浏览器是否能读取跨源响应，不是身份认证，也阻止不了 curl。Access Token 通过
Authorization Header 显式发送，Refresh Token 使用 HttpOnly、SameSite=Strict Cookie；刷新
和退出对浏览器 Origin 做精确白名单校验。Cookie 的 Secure 在生产环境必须开启，TLS 通常由
成熟反向代理终止。

## G12. 如何降低账户枚举和暴力登录风险【P1】

**参考回答：**

不存在用户和密码错误返回相同文案；未知邮箱也执行一次 dummy Argon2，缩小时序差异；连续
失败锁定账户；未知邮箱使用有界限流表；密码计算在独立 Auth 池中，队列满快速拒绝，避免
攻击拖垮网络线程和无限占用内存。

## G13. JWT 被篡改、过期或使用错误算法时怎么办【P1】

**参考回答：**

验证端固定接受 HS256，严格校验签名、issuer、audience、subject、iat、exp、jti 和 role，
拒绝 `alg=none`、未知算法和错误 audience。Access JWT 与 Capability JWT 使用不同 audience
和 secret，因此一种凭证不能拿到另一条链路使用。

## G14. 账户禁用和权限撤销怎样尽快生效【P1】

**参考回答：**

Refresh 和高风险操作会查询账户状态；Capability 每次 Tool 调用还检查 Run 和 assignment；
撤销医生分配后，后续 Tool 会立刻失败。普通 Access JWT 是 15 分钟短期令牌，若所有请求都
不查库，账户禁用最多存在该窗口。要求即时撤销时可引入 token version cache 或每次查库，
但会增加一致性和可用性成本。

## G15. 如何处理并发刷新和并发撤销【P1】

**参考回答：**

Refresh 通过数据库行锁和状态条件保证只有一次轮换成功；旧 Token 重用触发 Family 撤销。
Doctor assignment 在每次敏感访问和 Agent Tool 回调时重新检查，而不是只在会话创建时检查，
因此撤销后不会继续沿用旧上下文。并发测试需要反复运行，验证不存在双成功和越权窗口。

# H. 测试、压测、容量与故障排查

## H1. 你的测试为什么要分层【P0】

**参考回答：**

单元测试快速验证解析、状态机、权限和确定性算法；隔离测试用 Fake LLM、假模型和假客户端
验证组件契约；集成测试启动 C++/Python/MySQL 验证跨进程行为；全链路测试覆盖真实 Bundle、
数据库重启和 1489 个样本一致性。分层能让失败快速定位，也避免所有 CI 都依赖外部服务。

## H2. 做过哪些故障注入【P0】

**参考回答：**

包括非法 JSON、维度和非有限值；队列满；Python 连接失败、5xx、慢响应和非法响应；ONNX
运行异常和 Bundle checksum 损坏；客户端提前断开；Worker 抛异常；MySQL 停止和恢复；连接
池获取超时；Agent 重复 Tool Call、LLM 429/5xx；JWT 篡改、Refresh 重放、并发刷新和医生
分配撤销。重点不是故障数量，而是每个故障都有稳定状态码且不会拖垮 EventLoop。

## H3. 如何证明 EventLoop 没被阻塞【P0】

**参考回答：**

人为让模型、数据库或 Agent 变慢，同时并发请求 `/health`，观察健康接口仍能及时响应；再用
多个请求确认慢任务只占对应 Worker，队列满后快速 503。代码审查还确认 EventLoop 只解析、
投递和回包，不调用同步推理、SQL、Argon2 或 LLM。

## H4. 压测方案怎么设计【P0】

**参考回答：**

固定机器、Bundle、依赖版本和输入集，先预热，再分别测纯 ONNX、ONNX 加 MySQL、查询和 Agent。
使用不同 Worker 数和并发度，记录 p50/p95/p99、QPS、CPU、RSS、队列等待、连接池等待、拒绝
数和 fallback 次数。还要故意压过容量，确认失败模式是稳定 503 而不是内存持续增长。

## H5. 为什么不能只看平均延迟和 QPS【P1】

**参考回答：**

平均值会掩盖少量极慢请求，用户体验和超时通常由 p95/p99 决定；QPS 高也可能伴随错误率、
CPU 打满或队列无限增长。性能结论至少同时包含吞吐、尾延迟、成功率、资源使用和测试环境，
并区分稳定吞吐与短暂峰值。

## H6. QPS 为什么不会随 Worker 数线性增长【P1】

**参考回答：**

增加 Worker 后会遇到 CPU 核数、内存带宽、ORT 内部线程、数据库连接、锁竞争和上下文切换的
上限。I/O 型任务还受下游容量限制。线程过多可能让 p99 变差，因此应找到饱和点，而不是把
线程数等同于吞吐。

## H7. 如何做容量规划【P1】

**参考回答：**

先测单任务服务时间和每类资源上限，再根据目标 QPS、可接受排队时间和峰值系数估算 Worker、
队列和数据库连接。对 fallback 要按主链故障时的流量单独预算；对 Agent 要考虑一次用户请求
可能产生多个 Tool 调用。最后用压测验证并保留安全余量。

## H8. 线上 p99 突然升高，你怎么排查【P0】

**参考回答：**

先确认错误率和影响范围，再按阶段拆分：EventLoop、队列等待、ONNX、数据库 acquire/SQL、
Python/LLM 和回包。结合 CPU、RSS、连接数、队列深度、fallback、MySQL 慢查询和依赖延迟定位。
先通过限流、降级、关闭 shadow 或回滚 Bundle 止损，再查变更、流量、依赖和资源根因。

## H9. 应该记录哪些日志和指标【P1】

**参考回答：**

日志记录 request/run/resource ID、稳定错误码和阶段耗时，不记录 Token、Cookie、患者特征和
完整聊天。指标包括请求量、状态码、p95/p99、各队列深度和拒绝、Worker 利用率、数据库连接
等待、ONNX/remote 延迟、fallback/shadow mismatch、Agent step/Tool/超时和认证失败。Trace
用于把 C++、Python Agent、Tool 回调和数据库阶段串起来。

## H10. 如何发布和回滚【P1】

**参考回答：**

构建和依赖固定版本，数据库 migration 向前兼容，Bundle 具有确定版本与 checksum。发布前跑
全量测试和 parity，新模型先 shadow，再小流量切换；健康与就绪分离。发生错误率、延迟或模型
差异异常时，优先切回旧 Bundle、remote 模式或上一服务版本，不在故障现场修改产物。

## H11. 线上故障题应该怎样回答【P1】

**参考回答：**

按“确认现象和范围—看指标分段定位—立即止损—复现根因—修复验证—补监控和测试”回答。
例如 Agent 超时上升，先看 LLM 延迟还是 Tool/数据库延迟，再限流或临时关闭 Agent，不影响
普通预测；随后分析依赖变更和容量，最后补超时预算、告警和回归场景。

# I. 与项目强相关的 C++ 八股

## I1. RAII 在项目中解决了什么【P0】

**参考回答：**

RAII 把资源生命周期绑定对象生命周期，适合数据库连接 Lease、事务回滚、锁、ONNX Session
和网络句柄。异常或提前返回时析构仍执行，减少忘记释放和状态未恢复。RAII 不自动解决跨线程
所有权，异步对象仍要通过值、智能指针或明确关闭顺序管理。

## I2. `unique_ptr`、`shared_ptr`、`weak_ptr` 怎么选择【P0】

**参考回答：**

唯一所有者默认用 `unique_ptr`；确实存在多个异步任务共同延长生命周期时才用 `shared_ptr`；
连接等对象不希望被异步结果强行延寿时用 `weak_ptr`，回包前尝试提升。`shared_ptr` 控制块的
引用计数可并发更新，不代表指向对象本身线程安全。

## I3. lambda 捕获在异步代码中最容易出什么问题【P0】

**参考回答：**

按引用捕获局部变量或 `this`，任务执行时对象可能已经销毁；按值捕获裸指针也不能延长生命
周期。异步任务应复制必要小数据、移动独占对象，或捕获有明确生命周期的共享/弱引用；同时
避免无意复制大请求和敏感数据。

## I4. mutex 和 atomic 的边界是什么【P0】

**参考回答：**

atomic 适合一次完成标志、计数器等单变量状态转换；多个字段需要保持整体不变量时用 mutex。
项目的一次响应门适合 atomic，而 Session 容器和连接池状态需要锁。把所有字段都改成 atomic
不会自动获得事务性，反而可能产生难以理解的状态组合。

## I5. 条件变量为什么要带谓词循环【P1】

**参考回答：**

条件变量可能虚假唤醒，而且通知与等待存在竞争。等待方必须在锁保护下反复检查“队列非空或
已停止”等谓词；通知只表示状态可能变化。连接池和工作队列还要在 shutdown 时唤醒等待者，
否则停机可能永久阻塞。

## I6. 移动语义在异步任务中有什么价值【P1】

**参考回答：**

请求副本、JSON 字符串、响应构造器和回调所有权经常跨线程转移，移动可以避免大对象复制并
表达原所有者不再使用。移动后对象仍可析构但状态未指定，不能继续依赖其原内容。

## I7. 为什么模型使用虚接口，输入使用 `variant`【P1】

**参考回答：**

业务层只依赖稳定能力，运行时可选择 ONNX、远程、fallback 或内存/MySQL 实现，测试也能注入
Fake。模型输入则用 `variant` 表达样本下标、标准化数组和原始字段三种互斥类型，比多个可空
字段更容易保证 exactly-one。虚接口的代价是一点间接调用，`variant` 需要显式分支处理，但
都换来了更清楚的类型边界和可测试性。

## I8. `const` 成员函数是否意味着线程安全【P1】

**参考回答：**

不意味着。`const` 只限制通过该接口修改可见成员，内部仍可能访问 `mutable`、全局状态或非
线程安全依赖。项目能并发共享模型服务，是因为 Bundle 和树只读、每个请求缓冲私有，并确认
ONNX Session 支持并发调用，而不是因为接口写了 `const`。

## I9. 异常和错误码怎么选择【P1】

**参考回答：**

基础设施内部用类型化异常把深层失败向上抛，HTTP 边界统一映射为稳定状态码和安全 message；
可预期业务分支也可以用结果类型。异常不能穿出 Worker 导致线程退出，外部错误也不能携带 SQL、
绝对路径或第三方响应正文。

## I10. 静态库、动态库和依赖版本为什么会影响部署【P1】

**参考回答：**

静态库把代码并入可执行文件，部署简单但体积大、许可证和升级需注意；动态库可共享和独立更新，
但依赖搜索路径、ABI 和版本匹配。ONNX Runtime、MySQL Connector 和 Argon2 都需要在 CMake
配置期检查 header/library，缺失时 fail fast；可选开关保证 remote-only 开发构建仍可用。

# J. M7 RAG/MCP 与 M8 Skill

## J1. 为什么这个医疗 Agent 要加入 RAG，而不是让大模型直接回答【P0】

大模型参数中的知识无法保证版本、来源和适用对象，也很难证明某句话依据了哪份资料。我的做法是把预测事实和知识事实分开：概率、标签和解释仍来自 C++ 领域 Tool，医疗知识只来自人工登记的 RAG 语料。检索结果带 source、章节、页码和内容 checksum，最终回答只能引用本轮真正返回的 citation ID。证据不足时返回无答案，而不是让模型补全。这样不能消除所有幻觉，但显著缩小了事实生成面，也让回答可以追踪和评测。

## J2. 你的 RAG 检索链路是怎么设计的，为什么要混合检索【P0】

离线阶段按标题或 PDF 页切 chunk，同时建立 SQLite FTS5/BM25 和 FAISS 向量索引。在线阶段两路各自召回候选，用 RRF 融合，再用轻量 Cross-Encoder 重排。BM25 擅长模型字段、缩写和精确术语，Dense 更适合中文问法、英文资料和语义同义，二者互补。RRF 不要求两种分数处在同一尺度，工程上比直接加权更稳定。一路故障时可以降级，两个召回都失败才明确返回不可用。

## J3. 文档怎样切块，chunk 太大或太小分别有什么问题【P1】

Markdown 按标题和段落切，PDF 不跨页和章节，目标约 400 token、重叠 60 token。太大会混入多个主题，重排和引用都不精确，还浪费上下文；太小会丢失定义与限定条件，召回片段难以独立理解。Overlap 用于保留边界语义，但过大会制造重复候选和索引膨胀。chunk 参数属于索引版本的一部分，调整后必须重建并重新评测，而不是在线随意变化。

## J4. 怎样处理“检索到了但其实不相关”的情况【P0】

不能因为 top-k 总能返回结果就默认有答案。我准备了正例、同义词、跨语言、无关问题和越界治疗问题。实践中单一阈值无法同时保留弱相关的专业问题并拒绝所有越界问题，因此明确 model/clinical 查询与默认 all 查询分别校准阈值，再对提示注入、个体处方、确定性诊断和患者数据探测做安全 abstain；这些规则和阈值都可版本化、可测试。当前 42 题基线 Recall@5 为 0.9375、MRR@10 为 0.9271、无答案准确率为 1.0。低于阈值或命中边界就返回空结果，Agent 明确说没有可靠资料。

## J5. 如何保证引用不是 LLM 编出来的【P0】

Knowledge Server 为每个 chunk 生成稳定 citation ID，并随 Tool Result 返回。Agent 只收集本轮成功 MCP 调用产生的 ID，最终答案声明的 citation ID 必须与这个集合一致；不存在、跨 Run 或只写在正文但未声明的引用都会被策略拒绝。C++ 再校验引用元数据与 ID 集合一一对应，数据库只保存引用快照和 index version。幂等重放返回原快照，不重新检索，因此历史回答不会悄悄换依据。

## J6. 为什么用 MCP，为什么原来的预测 Tool 不一起改成 MCP【P0】

MCP 适合把独立知识服务以标准 Tool discovery、Schema 和传输协议接入 Agent，便于以后替换检索实现。预测、历史和比较是本项目自己的核心业务能力，已经通过 C++ Internal API 具备事务、Session 和授权语义，强行改造只增加一层适配。我的边界是“原生 Tool 负责业务事实，MCP 负责外部知识能力”。这样既能讲清 MCP 的价值，也没有为了使用协议而破坏已有合理架构。

## J7. MCP 服务怎么做权限隔离，为什么不能让 LLM 传 audience【P0】

C++ 根据已认证 actor 和本次 Agent Run 签发独立 Knowledge Capability JWT，绑定 role、session、subject、run、allowed scopes 和唯一 Tool。Patient 只有公开模型知识和患者教育资料，Doctor 才增加技术与专业指南 scope。LLM 只能提供 query、知识大类和 top-k，不能提供 audience 或扩大 scope。Knowledge Server 只信任签名后的 claim，再对每个候选做 audience 与 scope 过滤，从而防止提示词诱导模型检索越权知识。

## J8. RAG 中的 Prompt Injection 怎么处理【P0】

检索片段被当作不可信 Tool Data，而不是 System Prompt。系统规则明确片段里的命令没有控制权，Tool 权限和 Capability 也不会因文档内容改变。最终 grounding 只证明引用存在，并不自动证明结论推导正确，所以评测中还要放入带恶意指令的语料和问题。工程上同时限制 excerpt 长度、总响应大小和可调用 Tool，减少攻击内容进入上下文后的影响面。

## J9. Knowledge Server 变慢或宕机时系统怎样表现【P1】

知识计算使用自己的有界执行器，不占 C++ EventLoop、预测 Worker 或 Agent 的原生 Tool Worker。单次 MCP 有连接和请求超时，只读传输失败最多重试一次，并受 Agent 总 deadline 限制。队列满快速返回过载错误，Agent 可以回答“当前无法取得可靠资料”，但不能猜知识答案。C++ `/ready` 不依赖 MCP，因此知识服务故障不会让 ONNX 预测主链摘流，这属于舱壁和可控降级。

## J10. Tool、MCP 和 Skill 的区别是什么【P0】

Tool 是一个原子能力，例如查询解释；MCP 是外部能力如何被发现和调用的标准协议；Skill 是完成一类任务时怎样组合多个 Tool、知识和回答规范的方法。Skill 本身不执行网络请求，也不提供新权限。例如“解释预测”Skill 会规定先取预测事实、再取解释、必要时查模型知识，并提醒不能把重要特征说成因果关系。三者分别解决能力、接入和复用流程问题。

## J11. 为什么 Skill 要渐进加载【P0】

如果把所有 Skill 的完整说明长期塞进 System Prompt，会增加 token、干扰简单问题，还容易让互不相关的流程发生冲突。启动时只放 ID、用途、意图示例和 Tool 摘要；选中后才加载一个角色对应的完整 instructions。激活后 Tool 列表收窄到该 Skill 声明的集合。这样既降低上下文成本，也把“当前任务能做什么”变得更明确。

## J12. Skill 怎样避免变成任意代码插件【P0】

第一版只接受可信本地声明式包，manifest 只能声明版本、角色、意图、已有 Tool、知识 scope 和说明文件。Loader 拒绝符号链接、目录穿越、未知 Tool、非法 scope、超大文件和重复 ID；不允许 Python、Shell、SQL、URL、环境变量或依赖入口。Skill 只能收窄既有 Tool，执行入口还会再次验证，不能靠伪造 Tool Call 绕过。它也不能扩大 C++ 或 MCP Capability，所以权限上限仍由 Gateway 决定。

## J13. RAG 和 Skill 应该怎样评测【P0】

RAG 先做离线检索评测：Recall@5、MRR@10、无答案准确率、citation 有效性和跨 audience 泄漏；当前固定集的四项结果分别为 0.9375、0.9271、1.0 和 0。Skill 使用 Fake LLM 做确定性流程测试，当前三个 Skill 各 8 个场景，验证是否激活正确 Skill、是否只调用声明 Tool、grounding 是否有效以及角色说明是否正确。真实 LLM 再做人工 smoke test，观察路由、表达与安全边界。不能只挑几段流畅回答截图，因为那无法证明稳定性和失败行为。

# K. M9～M11 可观测性、部署与模型治理

## K1. 一次 Agent 请求跨了多个进程，你怎么定位问题【P0】

Gateway 为入口生成 request ID 和 W3C Trace，上游有合法 `traceparent` 时继续同一 Trace；调用 Python Agent、回调领域 Tool 和 MCP 时分别创建子 Span。每段只记录稳定 operation、耗时、结果和错误码。我先用 trace ID 还原单请求时序，再用 Metrics 判断它是个例还是系统性问题。例如总耗时高而模型 Span 正常、Agent Tool Span 长，就继续看 Agent 调度队列和 MCP/LLM 分段，而不是只看一条“请求慢”日志。

## K2. Trace、日志和 Metrics 各解决什么问题【P0】

Metrics 回答“系统整体是否异常、异常规模多大”，适合告警和趋势；Trace 回答“一次请求在哪一跳耗时或失败”；日志补充离散事件和安全错误原因。三者通过稳定 operation 和 trace ID 关联，但 request ID、用户 ID、Prediction ID 只进入 Trace/日志，不能进入 Metrics label。否则每个请求都会创建新时序，Prometheus 内存和查询成本失控。

## K3. 异步框架里为什么容易把 Trace 上下文弄丢【P1】

请求从 EventLoop 进入 Worker，再通过回调回到连接所属 Loop，线程本地变量不能自然跨越这条边界。我的做法是把不可变请求上下文放入请求副本，并让一次性 responder 捕获这个副本。中间件必须先生成上下文，再构造 responder；否则 after middleware 看到的是注入前副本。下游只传显式 header，不依赖隐式线程局部状态。

## K4. 线上 p99 上升时你具体看什么【P0】

先按固定路由和状态码确认影响范围，再拆成 EventLoop、调度排队、执行、数据库连接等待、模型、LLM 和检索。队列深而执行时间正常是容量/突发问题；数据库 acquire 上升是连接池或 SQL 问题；Agent 总耗时高但 Tool 正常通常看 LLM；只有单一 Trace 慢可能是长尾依赖。止损优先限流、快速 503、关闭非核心 shadow/RAG 或回滚，之后再用同口径压测复现。

## K5. Agent 为什么要分 Fake LLM 和真实 LLM 两套评测【P0】

Fake LLM 能固定 Tool 顺序、错误恢复和边界条件，适合作为 100% CI 硬门槛；它证明 Agent 工程协议正确，但不能证明真实模型会稳定选 Tool。真实 LLM 评测覆盖路由、参数、no-answer、表达和多次波动，保存模型与 Prompt/Skill/Index 版本。grounding、citation、跨角色泄漏和关键医疗边界仍是硬门槛，不能为了提高总体成功率而放松。

## K6. 突发十倍请求时系统怎样避免雪崩【P0】

模型、数据库、Agent 和认证使用隔离有界池，队列满立即返回不同语义的 503，避免无限占用内存；连接池获取和所有下游调用有超时，总 deadline 限制重试。健康检查不进入慢依赖，所以 EventLoop 仍能响应。客户端还应做带抖动的有限退避，避免失败后立即重试形成放大。压测除了 p99/QPS，还要观察队列、拒绝、RSS、连接等待以及负载停止后是否恢复。

## K7. 为什么项目没有为了“技术栈丰富”引入 RabbitMQ【P0】

即时预测和交互式 Chat 都要求同步结果，MQ 不会减少 ONNX 或 LLM 的实际耗时，只会新增任务状态、重复消费、幂等、重试、死信和补偿。当前有界调度池已经建立容量和背压边界。只有批量离线任务、超过 HTTP 生命周期、重启续跑或跨机器扩容 Worker 出现时，MQ 的持久任务价值才超过复杂度。这是根据业务语义和压测作出的 ADR，而不是否定 MQ 本身。

## K8. Docker 化时怎样避免把模型、数据和密钥打进镜像【P1】

构建上下文通过 `.dockerignore` 排除 Artifact、原始数据、报告和 `.env`；镜像只含程序与固定依赖。Bundle、知识索引和模型缓存在运行时只读挂载，Secret 由环境注入且日志脱敏。C++ 使用多阶段构建缩小运行镜像，所有服务非 root，数据库和内部服务只在 Compose 内网，外部只访问 nginx Gateway。

## K9. `/health`、`/ready` 和 Compose `depends_on` 有什么区别【P1】

`/health` 只表示进程和主线程还活着，不能同步探测所有依赖；`/ready` 表示当前是否适合接流量，例如 Backend 能从数据库池执行 `SELECT 1`。Compose 的健康依赖只解决本地启动顺序，不替代运行期 readiness、重试和故障恢复。Knowledge 下线不会让 C++ 核心 `/ready` 失败，因为 RAG 是可降级能力；Bundle/ONNX 损坏则启动直接失败。

## K10. 如何证明 ONNX 部署正确，又如何评价模型质量【P0】

部署正确看同一输入在 PyTorch、Python ORT 和 C++ ORT 的数值及 label、cluster、tree path parity；当前 1489 样本最大概率差约 `1.79e-7`。模型质量看带真实标签的 Accuracy、F1、AUC、AUPRC、Sensitivity、Specificity 和校准。Parity 好只能说明迁移没改模型，不能说明模型医学上足够好。两者必须使用不同的验收问题和证据。

## K11. 为什么这个数据不能只看 Accuracy【P0】

测试集混淆矩阵是 `[[1390,40],[14,45]]`，负类远多于正类，所以 `0.9637` Accuracy 会掩盖正类表现。Positive F1 是 `0.625`，Sensitivity 约 `0.763`，AUPRC 约 `0.739`，它们更能反映少数正类的召回、精确率折中和排序质量。AUC 可用于整体排序，但类别极不平衡时还要看 AUPRC；Brier/ECE 用来观察概率是否校准。

## K12. 怎样防止数据版本或划分变化造成“指标对不上”【P0】

Bundle v2 同时记录原 CSV、Artifact、Feature Schema、Scaler checksum，label 编码以及 train/test index fingerprint。Exporter 按 Artifact 的 seed、stratify 和 test size 重建划分，对全部 1489 个样本推理，并把复算指标与 Artifact 快照比较；标签数、顺序或核心指标不一致直接拒绝导出。训练 commit 无法确认时显式写 null，不能猜一个版本来制造可追溯假象。

## K13. 多 seed 怎么评估，为什么不能挑测试集最好的 seed【P1】

固定同一实验配置运行 19/21/42/60/99，报告均值、标准差、bootstrap 区间、校准和特征选择稳定性。它反映结果对随机初始化和数据划分的敏感程度。候选模型与阈值只能根据训练/验证规则选择，测试集用于最终一次报告；从五个测试结果挑最好 seed 会把测试集变成调参集，指标产生乐观偏差。

## K14. 模型怎样发布和回滚，为什么不做热更新【P1】

候选必须经过 Bundle checksum、标签指标、Python/C++ parity、shadow 和全量业务安全回归，再更新 Bundle 配置并重启。发布记录保存 current、previous 和 manifest SHA；分类、cluster、路径、Schema、延迟或内存异常就回滚上一目录。单机面试项目没有必须零停机热切换的需求，重启方案减少 Session 竞争、半数请求使用不同模型和资源释放等复杂状态，更容易证明正确。

# M. 简历表述、高风险说法与自测

## 1. 推荐项目表述

可以按下面四点组织简历，不要把所有技术栈堆成一段：

- 基于 Kama/Muduo 二次开发 C++ HTTP 服务，将预测、数据库和 Agent 调用隔离到独立有界
  Worker Pool，支持过载快速失败、跨线程安全回包和优雅排空。
- 设计 treeSem Serving Bundle，将确定性网络导出 ONNX，并在 C++ 实现预处理和决策树解释；
  通过 1489 个样本验证 Python/C++ 结果一致，支持 fallback 与 shadow 灰度。
- 使用 MySQL 短事务持久化 Session、预测快照、历史、比较和幂等医生反馈，区分健康检查与
  数据库就绪检查。
- 实现医疗 Agent Loop 和五个受控领域 Tool，并通过 Access/Refresh Token、Patient/Doctor/
  Admin 资源授权和短期 Capability 限制跨患者访问。
- 使用 BM25/FAISS/RRF/rerank 构建版本化医疗知识索引，通过官方 MCP 接入 Agent，并实现
  citation grounding、角色知识隔离和三个声明式渐进 Skill。

## 2. 高风险说法修正

| 不建议这样说 | 推荐表述 |
|---|---|
| 从零写了高性能 HTTP 框架 | 基于 Kama/Muduo 二次开发，并补充异步业务链和验证 |
| 用了异步所以性能很高 | 异步避免阻塞 I/O；吞吐仍由 CPU、Worker 和依赖容量决定 |
| 线程池能扛高并发 | 固定 Worker 限执行并发，有界队列和快速拒绝建立过载边界 |
| 超时就自动重试 | 只对幂等且可恢复错误有限重试，并受总 deadline 和预算限制 |
| fallback 保证高可用 | fallback 增加可用路径，也可能把故障流量转移到备用服务 |
| ONNX 一定比 Python 快 | 当前固定环境有收益，其他模型和机器需重新压测 |
| ONNX 一致说明模型可用 | 一致性证明部署正确，医学质量需要独立指标和验证 |
| `shared_ptr` 是线程安全的 | 引用计数可并发更新，不代表被管理对象线程安全 |
| Session 就是用户身份 | Session 是业务上下文，身份来自认证 Token 和账户状态 |
| Doctor 角色可以看所有患者 | 还必须验证 active assignment 和资源 subject |
| LLM 会判断什么时候结束 | Agent 由协议 final answer 和 step/tool/deadline 预算终止 |
| Tool Calling 能消除幻觉 | Tool 与 grounding 缩小事实生成面，仍需评测和人工复核 |
| PreparedStatement 解决了数据库安全 | 它主要防 SQL 注入，授权、加密和审计需要单独设计 |
