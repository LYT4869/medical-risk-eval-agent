# 独立场景：真实 Router 与 legacy rule 对照

## 执行范围

复用 `test/composite-response-semantics` 隔离工作区，在当前执行预算、最终回答协议和比较方向治理代码上，比较 `structured_llm` 与 `legacy_rule`。不改主目录、默认路由、部署或远程仓库。

1. 固定 48 条新场景、独立预期和合成业务记录。
2. 校验数据一致性和评测入口，运行单元回归与只读审查。
3. 两种模式同模型、同消息和同 Tool 数据顺序执行，每条交替先后顺序。
4. 保留首轮输出，人工检查比较方向、约束和医疗因果表述。
5. 报告分层结果、实际成本与延迟；根据证据建议下一步，不自动晋级或合并。

## 计分边界

Router：Schema、Intent/Target、实际 dispatch、修复次数和耗时。

执行：必须能力覆盖、具体目标绑定、显式比较顺序、引用在正文出现、拒绝越界调用；独立只读能力不按任意固定调用顺序判失败。

自动成功仅代表执行、绑定和最低回答契约通过；特征／路径裁剪、数字方向、否定要求和医疗因果含义仍必须人工核验。Safety 自动通过只认可实际确定性策略响应，其他模型拒绝另行审阅。

完整回答：比较方向、数字和原始要求由人工审阅补充。自动 Task Success 不是整体语义正确率。

基础设施：本轮使用合成 Tool 传输，不证明真实 C++ RBAC、MySQL、ONNX 或整个部署栈回归；既有主链测试结果也不冒充本轮实测。

## 预算与保护

- 模型配置复用本地未提交 `.env`，不输出密钥。
- 估计约 20万～40万 Token，首轮共 96 Run。
- 45万 Token／350 个物理 API 请求为 **Run 间准入保护**，最后一个已准入 Run 可能越过门槛；不是计费侧硬上限。
- 每个 Run 后写入忽略目录中的局部结果；上游不可用或预算到达时保留已完成记录，不自动充值或切换付费模型。
- 最终报告分别呈现实际物理 API 请求、Token 与端到端延迟，不将逻辑 Step 数当 API 次数。
- 修正计量：HTTP 发起前计入尝试；先记录响应 usage，再解析 Tool arguments。取消、失败和无 usage 请求增加 `unknown_usage_request_count`；已知 Token 是用量下界，费用以平台账单为准。

## 晋级判断

不追求 48/48 的表面分数。关注安全边界、真实 ID／目标绑定、比较方向和稳定性，同时看是否减少开放规划与总体成本。Schema 长尾、歧义和安全 Slice 若仍有实质失败，维持默认方案并记录具体失败；不得针对已揭晓集合微调后宣称独立提升。

## 9 月 14 日执行前校准记录

初次配对在完成 14 Run 后暂停：七条 Structured 路由都在基础设施预算阶段失败，尚不能测量语义质量。初版评测还共享主 LLM 客户端（1024 输出 Token、客户端重试），并非正式 Router 的 384 Token／单次客户端尝试配置，因此该局部运行只保留为预算诊断，不作为正式方案对照。

另外使用 12 条无语义标准答案的短请求、20 秒单次且不重试的预算测量延迟：合法 Schema 12/12，均值 3.652 秒，经验 p95 4.605 秒，最大 5.355 秒，24,469 Token；此前独立探针另用了 2,037 Token。输出均不足 384 Token，但探针配置上限是 1024；这是小样本延迟诊断，不是生产 p95/p99 或语义准确率。

据此完整对照仅在评测中使用 6 秒单次、13 秒总预算，并通过正式 `build_intent_routing_runtime` 创建独立 Router 客户端，保留模型、384 Token 上限、关闭思考和客户端不重试。正式配置不改。两种客户端的实际请求和已知用量合并计量。

语料、Router Prompt、执行器和评分预期不变。首次七条已见输出，后续完整结果必须标为“预算校准后同一冻结集合对照”，不能宣称整组全新未揭晓 Heldout。新版完整运行设置 40万已知 Token／300 物理请求的 Run 间准入预算；仍不是计费硬上限。

## 执行收口
